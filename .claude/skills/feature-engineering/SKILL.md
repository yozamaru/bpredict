# 特徴量の実装規約

定義の一覧は `docs/design-detail.md` 2章、採否の区分は `docs/requirements.md` 6.2 にある。**このスキルは判断基準と禁止事項を扱う。数値やキー名は文書を正とする。**

## 最重要原則

**特徴量は「試合開始時点で確定している情報」のみで構成する。**

違反すると、検証上の的中率だけが不自然に上がり、実運用でまったく当たらないモデルになる。しかもテストは通り、開発中は気づけない。このプロジェクトで最も起こりやすく、最も致命的な失敗である。

## 実装規約

```python
def build_features(game_id: str, as_of: datetime, ds: Dataset) -> dict[str, float]:
    """as_of 時点で確定している情報のみから特徴量を生成する。"""
```

1. **必ず `as_of` を引数に取る。** 省略可能にしない
2. **絞り込みは `finished_at <= as_of` で行う。`tipoff_at` ではない。** `tipoff_at` で絞ると、17:05開始・19:05終了の試合が19:05開始の試合の確定情報として混入する
3. **`status = 'SCHEDULED'` の試合を集計に含めない。** `home_score` が NULL のまま敗戦扱いされるか、例外になる
4. **対象試合自身を参照しない。** `team_game_stats` / `player_game_stats` / `games.attendance` の当該 `game_id` に触らない
5. **チーム所属の判定に「現在の所属」を使わない。** `player_game_stats.club_id`（実績）または `player_seasons`（当該シーズン断面）を使う
6. 試合後にしか判明しない値は、過去試合の集計に変換する
7. **欠損時は None を返す。** 関数内で0埋めしない。既定値への変換は呼び出し側で行う
8. **`competition` で絞らない。** `REGULAR` と `PLAYOFF` の両方を集計に含める

### 規約8の理由

DB に入っているのはこの2区分だけで（オールスター・プレシーズン・入替戦は取り込まない）、どちらもクラブ同士の公式戦である。プレーオフを除外すると、**その期間だけ当季勝率と得失点差が止まったまま Elo だけが動く**不連続が生じる。区分で絞る必要が出たら、`docs/design-detail.md` 2.1 の規約7を先に書き換える（`team_games.competition` は絞れるように持たせてあるが、v1 では絞らない）。

### 規約5を守らないと何が起きるか

`players` の現在の所属で「そのチームの主力」を判定すると、**移籍した選手が過去の所属チームから消え、新チームに過去の出場時間ごと移動する**。`minutes_lost` や `top_players_out` が静かに誤る。`as_of` 規約には違反しないため、リークテストでも検出されない。

### D1 を読まない

**特徴量生成の入力は `batch/snapshot/*.parquet` のみ。** 全量をメモリにロードして結合・フィルタする。試合8,000件・選手スタッツ20万行は数十MBに収まる。

**`team_ratings`（Elo）もスナップショットから読む。** `elo_home` / `elo_away` が参照するのは `team_ratings.parquet` であって D1 ではない。書き出しの順序は「Elo を再計算 → `team_ratings.parquet` へ書き出し → 同じ値を `/internal/ratings` で D1 にも送る」に固定されており、D1 側は公開APIの表示用の複製である。**その場で Elo を計算する実装にしない**（全試合を走査する過程で対象試合を含めてしまう事故が起きる）。

D1 からの「一括エクスポート」経路も作らない。**禁止されるのは「入力データとしての読み取り」**であり、backfill の再開判定・結果照合・モデル artifact の読み出しといった運用上の読み取りは `/internal/*` の GET で行う（`docs/design-detail.md` 3.4）。特徴量生成はそのどれも使わない。逐次クエリ方式では `games` の全件スキャンを試合ごとに繰り返し **1日150万〜1,450万行**（D1 読取上限500万行per日）に達し、学習時は億行規模になる。超過すると課金されず停止するため**公開APIも同時に落ちる**。一括エクスポート方式でも読取枠を消費し、特徴量生成が Cloudflare の可用性に依存する。

**スナップショットを唯一の入力と決めることで、この経路が構造的に消える。** 「バッチは D1 を読んでよい」という例外を一度でも許すと、逐次クエリへの退行を設計で止められなくなる。

読み込み前に `MANIFEST.json` の行数と SHA256 を照合する。不一致なら処理を中止する（`test_snapshot_manifest_hashes` / `test_training_reads_no_d1`）。

### 「試合後の値」の正しい使い方

| 使ってはいけない | 正しい変換 |
|---|---|
| 当該試合の観客数 | チーム別・会場別・曜日別の**過去**平均動員数／動員率 |
| 当該試合の得点 | 直近N試合の平均得点、Elo |
| 当該試合の選手スタッツ | 当該選手の直近N試合の平均 |

## 命名規則

`{カテゴリ}_{内容}_{対象}`。対象は `home` / `away` / `diff`。

**可能な限り `diff` に集約する。** 列数が半減し、対称性の事前知識がモデルに入る。特徴量は展開すると60〜70列になり、8,000行（初期 fold は1,600行）に対して過剰になる。

`is_home` を特徴量にしない。ホーム視点固定で学習するため常に1の定数列になり、分割に使えない。

## 採否の判断

`docs/requirements.md` 6.2 に全30項目の振り分けがある。**勝手に区分を変えない。**

見送り項目を実装したくなったら、まず理由を読む。以下は技術ではなく方針の問題である。

- **天候**: 屋内競技で効果量が検出限界未満。実装コストは #19（主力の出場可否）に振り向ける
- **直接対戦成績**: 年4〜6試合しかなくロスターも毎年入れ替わる。Elo からの増分はほぼゼロで、SHAP が拾うと「直接対戦3勝0敗」という説得力はあるが統計的に無意味な根拠が表示される
- **標高**: 日本のアリーナは低地に集中し分散がない
- **ブックメーカーのオッズ**: 賭博と一線を引く方針

### 新しい特徴量を追加するとき

1. その値が**試合開始時点で確定しているか**検証する
2. `docs/requirements.md` 6.2 と `docs/design-detail.md` 2.2 に追記する
3. 実装し、`pytest batch/tests/test_leakage.py` を通す
4. 寄与度（SHAP / gain）と**欠損率**を測定する
5. 効果がなければ削除する。「念のため残す」をしない

**一度に全部入れない。** `elo_diff` と日程系と欠場系の10〜15列で基礎モデルを作り、1つずつ追加して walk-forward Brier の改善を測る。**入れることより、効かないものを落とすことに労力を使う。**

欠損率30%超の特徴量があるとモデルは採用されない（`passes_criteria`）。元データが未投入のまま追加すると、Brier が偶然良ければ採用され、**新特徴量が機能していないどころか既存特徴量の重みが劣化していることに誰も気づかない**。

## リーク検証（最重要）

**検証の向きは「DBを撹乱する」。「`as_of` をずらす」ではない。**

```python
def test_target_game_mutation_does_not_change_features(db, game):
    f1 = build_features(game.id, as_of=game.tipoff_at, ds=export(db))
    mutate_game_result(db, game.id, home_score=200, away_score=0, attendance=99999)
    f2 = build_features(game.id, as_of=game.tipoff_at, ds=export(db))
    assert all(approx_equal(f1[k], f2[k]) for k in f1)     # 本命

def test_as_of_is_actually_applied(db, game):
    """as_of を前にずらすと結果依存の特徴量が変化すること（陽性確認）。"""
```

`as_of` を後ろにずらすと参照できる過去試合が増えるため、**正しい実装なら値は変わるのが正常**である。「変わらないこと」を assert するテストは、正しい実装を落とし、`as_of` を一切見ない実装だけを通す。

`sql_spy` はクエリ文字列だけでなく**バインドパラメータも記録する**こと。プレースホルダを使えば `game_id` はクエリ文字列に現れない。

意図的にリークさせた実装でテストが**落ちること**も CI で確認する（テストのテスト）。

```bash
pytest batch/tests/test_leakage.py -v
```

特徴量を追加・変更したら必ず実行する。CI でも強制される。

## 異常に高い精度を疑う

| 的中率 | 判断 |
|---|---|
| 〜65% | 妥当。ベースライン近辺 |
| 65-68% | 良好。現実的な到達点 |
| 68-75% | 優秀。リークがないか確認する |
| 75%〜 | リークを疑う |
| 85%〜 | **ほぼ確実にリークがある。** 喜ばずに原因を探す |

設計時点の見立ては Brier 0.200〜0.212 / 的中率 64〜68%（`docs/requirements.md` 付録B）。これを大きく超えたら、まずリークを探す。

## 特徴量スナップショット

生成した特徴量ベクトルは `predictions.feature_snapshot` に、参照した情報の鮮度は `data_as_of` に保存する。

`data_as_of` が必要な理由: 本番の日次推論は最大7日前の情報で予測するが、バックテストでは全試合が揃っているため開始直前の情報が使える。同じ関数を呼んでいても入力が違い、**検証スコアが体系的に過大評価される**。これは「リーク」と呼ばれずに見逃される種類のバイアスであり、記録しないと後から検証できない。
