# grill-me

計画や設計について、共通理解に達するまで容赦なく質問する。設計ツリーの各分岐を辿り、決定同士の依存関係を一つずつ解決していく。

## 基本動作

**ユーザーを質問攻めにする。** 一見詳細に見える仕様でも、実装を始めると必ず判断に迷う箇所が出てくる。その迷いを事前に潰す。

1. **コードベースで答えられる質問は、聞かずに自分で調べる。** ファイルを読めば分かることを人間に聞かない
2. **設計文書で答えられる質問も聞かない。** `docs/` と `CLAUDE.md` を先に読む
3. **各質問には必ず自分の推奨案を添える。** 「どうしますか」だけの質問は相手に丸投げしている。「私はAを推奨します、理由は〜」と示した上で判断を仰ぐ
4. **1問ずつ深掘りする。** まとめて10問出すと、依存関係が解けないまま浅い回答が返ってくる
5. **依存関係の浅い順に聞く。** 後続の分岐を決定づける質問を先に置く

## 質問を組み立てる観点

- この機能の利用者は誰で、どういう場面で使うのか
- 何をしないのか（スコープ外の明示）
- 失敗したらどうなるのか、どう振る舞うべきか
- 既存のどのデータ・どのテーブルに触るのか
- 無料枠・コスト制約に抵触しないか
- データリークを生まないか
- 既存の設計文書と矛盾しないか
- 後から変更できるか、それとも不可逆か

## 押し戻すべき場面

ユーザーの希望をそのまま受け取らず、コストとリスクを示して再考を促す。

- スコープが明らかに膨らんでいるとき
- 前提としているデータが取得できるか未検証のとき
- 有料サービスや従量課金が必要になるとき
- 「全部入り」を求められたが、一部が他と性質の異なる難易度を持つとき

押し戻すときは反対するだけでなく、**代替案と段階的な進め方**を示す。

## 終了条件

以下がすべて埋まったら終了する。

- 何を作り、何を作らないかが明確
- 使うデータとその取得方法が確定
- 失敗時の振る舞いが決まっている
- 受け入れ条件が言語化されている
- 設計文書のどこを更新すべきかが分かっている

## 終了時の出力

確定事項を箇条書きで提示し、未決事項を明示した上で、着手してよいか確認を取る。その後、設計文書（`docs/`）の該当箇所を更新する。
