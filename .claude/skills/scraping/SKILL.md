# データ取得の実装規約

法務の評価は `docs/requirements.md` 4.5 と 5.1、実装の詳細は `docs/design-detail.md` 4.3〜4.4 にある。

## 法務上の線引き

2026年9月時点の調査結果（**スナップショットであり、相手方は予告なく変更できる**）。

- `robots.txt` に `User-agent: *` の記述はなく、一般クローラーへの制限はない
- 利用規約にスクレイピングを名指しで禁止する条項はない
- 利用規約の著作権条項に「複製、公衆送信その他の利用をすることはできません」とある
- サイトは「基本的にリンクフリー」

| 扱い | 対象 |
|---|---|
| 取得・表示してよい | 試合日程、対戦カード、スコア、スタッツの数値、会場名、入場者数 |
| 取得・表示してはならない | 記事本文、写真、ロゴ、エンブレム、選手の肖像 |
| してはならない | 生データの一括配信、公開API化、**取得したレスポンス本文のリポジトリへのコミット** |

**これは適法性の保証ではない。** データベースの著作物（著作権法12条の2）、不法行為（民法709条）、30条の4ただし書、包括禁止条項という論点が残存リスクとして存在する（`docs/requirements.md` 4.5.3）。判断に迷う取得対象が現れたら、実装せずに確認する。

## 取得した本文の扱い（最重要）

**取得したレスポンス本文をリポジトリにコミットしてはならない。** HTML でも、その中に埋め込まれた JSON でも同じである。

個々のスコアに著作物性は認められにくい一方、**ページそのものは事実データではない**。テキスト表現・見出し・ナビゲーション文言・レイアウト構造を含む一体としてのページは著作物として保護されうる。これを public リポジトリに置くことは、「事実データだから」という本プロジェクトの立論が**一切通用しない唯一の行為**である。

埋め込みJSONも、審判名やプレイバイプレイを含む**ページの構成要素一式**であり、「抽出した数値データ」とは別物である。抜き出した後の数値だけを保存する。

- 取得した本文は `batch/cache/`（gitignore 対象）にのみ置く
- テスト用フィクスチャは、**構造のみを模し、値をダミーに置換した合成データ**とする。実サイトの文言・記事・画像参照を残さない。埋め込みJSONを読むようになっても方針は同じ
- 審判名とプレイバイプレイは **fixture にも含めない**（抽出対象外であることをテストで固定する）
- `.gitignore` に `**/fixtures/**/*.html` と `**/fixtures/**/*.raw.json` を含める
- CI で fixtures に実サイト由来の文字列が混入していないことを検査する

## アクセス作法

| ルール | 内容 |
|---|---|
| 間隔 | 最低3秒 + ジッタ。**短縮しない** |
| 並列 | 禁止。並列取得を提案しない |
| 日次上限 | 3,000リクエスト。クライアント側で強制する |
| サイズ上限 | 5MB。超過で `ResponseTooLarge` |
| UA | 識別名と連絡先URLを必ず含める |
| 429 / 503 | `AbortedByRemote` を送出。**スクレイピング区間のみ中止**し、同日中に再試行しない |
| 事前確認 | `robots.txt` と利用規約をハッシュ照合。変更検知でジョブ中止 |
| 範囲 | 必要なページのみ。サイトマップ巡回や全ページクロールをしない |
| backfill | 1日1シーズンずつ。**再開可能にする**（取得済みIDをスキップ） |

3秒間隔は仕様であり、短縮して解決する問題ではない。

**`AbortedByRemote` の捕捉範囲をスクレイピング区間に限定する。** try で処理全体を覆うと、前日結果が取れないだけで照合・Elo・推論・静的JSON書き出しまですべてスキップされ、その日の予測更新が止まる。

**backfill を再開可能にする。** 55分経過時点で 429 を食らった際に翌日また全ページを取り直すのは、相手サイトへの負荷を二重にかけることになり、遵守事項の趣旨に反する。

## 責務の分離

```
batch/scraper/   HTTPのみ。URLを受けて本文の文字列を返す。本文を解釈しない
batch/parser/    レスポンス本文の解釈と値域検証のみ。HTTPを知らない
  ├ extract.py       <script> 内の埋め込みJSONの取り出し
  ├ fields.py        サイトのフィールド名 → DB列 の対応表
  └ validators.py    値域・恒等式の検証
batch/loader/    Workers /internal/* への書き込み
```

**サイト構造が変わったとき、`parser/` の修正だけで復旧できる状態を保つ。**

### 入力は HTML の表ではなく埋め込みJSON（Phase 0 で確認）

試合詳細ページのボックススコアは **`<script>` 内に埋め込まれた JSON** として配信される。
列見出しは JavaScript のテンプレート文字列の中にあり、実行時に組み立てられるため、
**DOM を辿る実装では取れない**。JS で別途取りに行くのではなく初回のレスポンスに入っているので、
`httpx` で1回取れば足りる。

対応表は `docs/design-detail.md` 4.4 にある。主なものだけ挙げると、
`fd` ← `FOULON`、`fg2m/fg2a` ← `PT2M/PT2A`、`minutes` ← `PlayTime`（`"MM:SS"`）、
`attendance` ← `Attendance`。

**取り込み前に必ず通す4つの正規化。** どれも放置すると静かに壊れる。

0. **試合一覧を大会区分（`event`）で絞る。** 取り込むのは `2`（リーグ戦 → `REGULAR`）と
   `3`（チャンピオンシップ → `PLAYOFF`）だけ。`4` 残留プレーオフ / `5` オールスターゲーム /
   `11` 入替戦 / `20` アーリーカップは入れない。**ラベルではなく値で分岐する**
   （`2` のラベルは 2026-27 で「B1リーグ」から「B.PREMIER」に変わった）
1. **`PeriodCategory` が 18（試合通算）の行だけを取る。** 1〜4 はクォーター別、15 / 16 は前後半。
   全部入れると行数が7倍になり、集計がすべて狂う
2. **`PlayerID` が空のチーム集計行を選手行から分離する。** 混ぜると `player_game_stats` と
   `team_game_stats` の両方が汚染される
3. **空文字と 0 を区別する。** 数値が `0` ではなく `""` で入ることがある。`int("")` は例外になり、
   `0` と誤ると「記録なし」が「0回」になる。値域検証の**前に** None へ正規化する

**オールスターゲームを取り込むと Elo が壊れる。** 選抜チーム同士の対戦であり `clubs` に存在しない
チームが現れる。入替戦は相手が B2 のクラブで対戦相手を解決できない。区分は `games.competition` と
`team_games.competition` に保持し、取り込みの絞り込みだけで済ませない（区別を捨てると特徴量 #17 が
算出できず、復元には backfill のやり直しが必要になる）。

**JSON 全体を保存しない。** 同じレスポンスに審判名（特徴量 #30 は見送り）とプレイバイプレイ
（1試合700件規模）が含まれる。要件 5.3 に従い、対応表にある列だけを抜き出す。

### クラブの名寄せと名称（Phase 0 で確認）

**`TeamID` はシーズン・改称・リーグ再編をまたいで不変。** `club_source_ids` は本ソースでは1:1に
なるが、ID体系が変わったときの継ぎ目として維持する。取り込み時に `club_id` へ解決する規約も
変えない。

**過去シーズンの正式名称は `TeamNameJ` から取る。** この値はその試合の時点の名称である
（`703` は 2016-17 で `栃木ブレックス`、現在は宇都宮ブレックス）。年度別のクラブ一覧ページは
存在しないため、**`club_seasons` は `seed_master` ではなく backfill が試合データから作る**。
短縮表記は試合一覧ページのクラブ選択肢から取る。

## パーサと値域検証

```python
class ParseError(Exception):      """必須項目が抽出できない。構造変更の可能性"""
class ValidationError(Exception): """値域外。当該試合をスキップ"""
```

- 必須項目が欠けたら `ParseError`。欠損を握りつぶさない
- 任意項目（入場者数など）は欠損を許容し None を返す
- **値域検証を必ず通す**: `pts` 0–250、`minutes` 0–60、`fg2m <= fg2a`、`fg3m <= fg3a`、`ftm <= fta`、`pf` 0–6、`attendance <= capacity × 1.2`、`possessions` 50–120
- **恒等式も検証する**: `pts = fg2m×2 + fg3m×3 + ftm`、`fga = fg2a + fg3a`、`reb = oreb + dreb`、チーム集計 = 所属選手の合計。違反は当該試合をスキップする
- 取得対象の選手スタッツは**フルボックススコア**（2FGM/2FGA、3FGM/3FGA、FTM/FTA、OR/DR、AS、TO、ST、BS、F、**FD（被ファウル数）**、＋/－、MIN）。**すべて取得可能であることを Phase 0 で確認済み**（P0-9）
- 数値パースは全角数字、カンマ、`"-"`（未出場）、`"MM:SS"` 形式、`"DNP"`、空文字を考慮する
- 選手・チーム・試合のIDは**公式サイトのID**を使う。氏名での突合は表記ゆれで壊れる

### 値域検証が必要な理由

スクレイピングは**入力が信用できないパイプライン**である。攻撃者が相手サイトを侵害する必要すらなく、一時的な障害ページが「パース可能だが異常な数値」を返すだけでよい。`pts=99999` が `team_game_stats` に入ると、Elo の `log(margin + 1)` に流れ込んで**全チームのレーティングが破壊される**。しかも冪等な再実行では汚染データが再投入されるだけで復旧しない。

## 構造変更への対応

1. `ParseError` が連続3件でジョブを中止し、`PARTIAL` で記録して **exit 1** する
2. ログには**対象URLのホストとパスのみ**を残す（クエリ文字列とID部分はマスク）
3. 修正時はサンプルを取得し、**合成 fixture に落としてからテストを書いて**直す。本番アクセスで試行錯誤しない

**`PARTIAL` を exit 0 で終えない。** GitHub Actions の失敗通知に乗らず、誰も気づかないまま数日放置される。

**fixture はサイト構造の変更を検知できない**（スナップショットであるため、古い構造に対して永遠にグリーンであり続ける）。検知は `parser-canary`（日次、実サイトの日程ページ1枚のみ取得してパースし、失敗で Actions を fail）が担う。カナリアは**埋め込みJSONが取り出せること・必須フィールドが揃っていること・`PeriodCategory` に 18 があること**まで見る。

## 例外をそのままログ・DBに入れない

**このリポジトリは public であり、Actions のログも全世界から閲覧できる。**

`str(e)` を `ingestion_logs.error_message` に保存すると、URLに含まれるIDやトークン断片がDBに入り、`/api/v1/health` で公開される可能性がある。**型名（`type(e).__name__`）と自前の短いメッセージに限定する。**

## 取り込みの冪等性

- 試合は**公式試合IDを主キー**に upsert する。自然キーに `game_date` を含めない（延期で日付が変わると別レコードになり、旧行が `SCHEDULED` のまま残ってゴースト試合になる）
- **エントリー情報は取得ごとに全行を洗い替える**（DELETE → INSERT）。追加のみの upsert では、推定で作った「出場するはず」の行のうち実際には登録外だった選手の行が残り続け、`is_provisional` が永久に解除されない
- スコア訂正を検出したら `result_revision` を進め、`prediction_results` の再評価をトリガする
- 同じジョブを再実行しても結果が変わらないこと

## 書き込み経路

**D1 への書き込みは Workers の `/internal/*` 経由に一本化する。** D1 REST API を直接叩かない。REST 直叩きを許すと、Zod 検証・認可・tipoff ガード・`is_final` 保護がすべて迂回可能になる。

## Phase 0 の検証状況

結果は `verification/RESULTS.md` にある。取得できないと判明した項目は、該当特徴量を無効化して先に進む（工程を止めない）。

**確認済み**

- 入場者数（P0-1）: 取得可。埋め込みJSONの `Attendance`
- 旧B1と新リーグのクラブ対応（P0-5）: **`TeamID` が不変**。トップリーグに現れるのは11シーズンで30クラブ、2026-27 B.PREMIER は26クラブ
- ポゼッション算出の項目（P0-2）: 取得可。`PT2A` / `PT3A` / `FTA` / `RB_OFF` / `TO` が揃う
- `FD` と `2FGM/2FGA`（P0-9）: 取得可。`FOULON` / `PT2M` / `PT2A`

**未確認**

- **エントリー情報が試合前に公開されるか、確定タイミングはいつか**（P0-3。F-05・F-06 の前提）
- 1試合あたりの取得ページ数（P0-4。backfill の総リクエスト数と所要日数の算定）
- 統計データの有償提供の有無（P0-6）
- ポゼッション係数 0.44 の妥当性（P0-7）。サイト側の `POSS` と自前計算の突き合わせで判断する
