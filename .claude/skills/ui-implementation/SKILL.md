# UI 実装規約

トークンの実体は `docs/design-basic.md` 6.1、画面構成は同 5.2、コンポーネント仕様は `docs/design-detail.md` 5章にある。

## デザイン方向

データ系のレイアウト。**数値が主役**で、情報密度は高く保つ。装飾より可読性を優先する。

## デザイントークン

**2026-09-29 に方向性A「データ密度型」を採用した。** 旧トークン（単一の緑アクセント
`--accent` / `--text-4` / カードの影）は**廃止した**。出典は `docs/design-basic.md` 6.1。

```css
:root {
  --paper:#F7F5EF; --panel:#FFFFFF; --tint:#F2EFE6;
  --ink:#15181D; --ink-2:#4B515B; --ink-3:#676D78;
  --home:#134A83; --away:#8E3A12;
  --warn:#7A4A12; --warn-bg:#FBF1E2;
  --rule:#D9D3C5; --rule-soft:#E7E2D6;
  --axis:#736B5A; --band:#E3DBC4;
  --f-serif:"Hiragino Mincho ProN","Yu Mincho",YuMincho,"Noto Serif JP",serif;
  --f-sans:-apple-system,BlinkMacSystemFont,"Hiragino Sans","Noto Sans JP","Yu Gothic UI",system-ui,sans-serif;
  --f-mono:ui-monospace,SFMono-Regular,"SF Mono",Menlo,Consolas,"Liberation Mono",monospace;
}
:root[data-theme="dark"] {
  --paper:#0B0D11; --panel:#12151A; --tint:#161A20;
  --ink:#E9ECF2; --ink-2:#A9B2BF; --ink-3:#8D97A5;
  --home:#79B2F7; --away:#F2966C;
  --warn:#E0A458; --warn-bg:rgba(224,164,88,.12);
  --rule:#242A33; --rule-soft:#1C212A;
  --axis:#788395; --band:#252D38;
}
```

**コンポーネントに色を直接書かない。** 必ずトークン経由で参照する。

### 単一のアクセント色を戻さない

`--home`（藍）と `--away`（弁柄）は**対等な2つの側**である。1色に戻すと、塗られた側が
「良い」と読まれる。赤＝危険 / 緑＝安全 の連想は、勝敗予測では誤った価値判断になる。

**方向は色だけで示さない。** バーの向き・H/A のラベル・数値の3つが併存する。

### 線は3つに分かれている。「意味を持つ線」だけに 3:1 を課す

| トークン | 意味 | 要求 |
|---|---|---|
| `--axis`（勝率バーの50%軸・**較正グラフの対角線**） | **意味を持つ**。判定基準そのもの | **3:1 以上** |
| `--rule` / `--rule-soft` | 装飾的な仕切り。図の枠の軸線もこちら | 課さない |

**`--axis` は使われる場所ごとの背景に対して測る。** 1つのトークンが2か所で別の地の上を
通る（基本設計 6.1）。

| 使う場所 | 背景 | ライト / ダーク |
|---|---|---|
| 勝率バーの50%軸 | **`--band`**（必ず互角帯の上を通る） | 3.82 / 3.63 |
| 較正グラフの対角線（`/accuracy`） | **`--paper`** | 4.84 / 5.07 |

制作時に `#8E8676` を置いたところ、紙には 3.31:1 あったが**帯の上では 2.61:1** しか
なかった。**目視では気づけない。** 逆に、帯だけを検査すると較正グラフの対角線に
検査が当たらない。**どちらが厳しいかではなく、使う場所をすべて挙げる。**

### 図（SVG）でも線とテキストの系列を混ぜない

**SVG は `stroke` と `fill` で塗るため、系列の区別が効いていないと気づきにくい。**

| 図の要素 | トークン |
|---|---|
| 判定基準の線（較正の対角線・勝率の50%軸） | **`--axis`** |
| 枠の軸線・目盛りの線 | `--rule` |
| データの点・マーク | **`--ink`**（図の主役。主数値と同じ） |
| 目盛りのラベル・軸名 | `--ink-3` |

**データの点に `--home` / `--away` を使わない。** あの2色はホーム側／アウェイ側という
対等な2つの側を指す対であり、較正の点にその意味はない。**無い区別を読ませることになる。**

**判定基準の線と枠を同じ濃さで描かない。** 比べる相手がどちらか分からなくなる。

### `--text-4` は廃止した

テキスト（`--ink` / `--ink-2` / `--ink-3`）と線（`--rule` / `--rule-soft` / `--axis`）を
別の系列に分けてある。**「テキスト色の系列に非テキスト専用の値を混ぜる」構造そのものが
混同の原因だった。**

敗者側の確率には `--ink-2` を使う。勝敗の差は色の濃淡ではなく、**バーの向きと数値**で伝える。

### コントラストは CI で検証する

**両テーマで本文 4.5:1 以上。トークン単体テストで自動検証する。** 目視のスナップショット確認では必ず見落とす（旧版のトークンは 2.88:1 しかないまま「4.5:1 以上」と規約に書かれていた）。

**`--axis` は `--band` と `--paper` の両方に対して 3:1 以上**を検査する（上記の表）。
本文の最小はライト 4.53:1（`--ink-3` が `--tint` の上）、ダーク 5.91:1。

**廃止したトークンの走査は `stroke-` と `fill-` を必ず含める。** 2026-10-02 に較正グラフが
`stroke-text-4` / `fill-accent` のままで描かれていないことが判明した。走査は既にあったが
前置が `text-` / `bg-` / `border-` だけで、**SVG の塗りに当たっていなかった**。
Tailwind の橋渡しに無い名前は `stroke` が無色・`fill` が既定の黒になり、
**壊れても画面はエラーを出さない。**

ダークのアクセント（ライム）をライト背景に使わない。小さな文字（10px のチップ等）でも基準を満たすことを確認する。

## テーマ切替

- **既定はライト。** OS設定への追従は行わない
- ヘッダーのボタンで `<html data-theme>` を切り替える
- 選択は `localStorage` に保存する
- 初回描画のフラッシュを防ぐため `<head>` 内の inline script で適用する

```html
<script>
  try { var t = localStorage.getItem('theme');
        if (t) document.documentElement.setAttribute('data-theme', t); } catch (e) {}
</script>
```

`localStorage` へのアクセスは必ず try/catch で囲む。このスクリプトのハッシュを CSP に登録する。

## 数値表示

```css
.num { font-variant-numeric: tabular-nums; }
```

**すべての数値に等幅数字を適用する。** 桁が揃わないと一覧での比較ができない。

| 値 | 表記 |
|---|---|
| 勝率 | 整数の百分率（`68%`）。**両チーム分を必ず表示** |
| 予想スコア | **整数**（`84 – 78`）。MAE 8〜10点に対し小数第1位は精度の誤認を招く |
| 個人スタッツ（カウント） | 小数第1位（`18.4`）。期待値なので整数にしない |
| 個人スタッツ（成功/試投） | `6.4 / 13.1` の分数。率は括弧で併記 |
| 率（FG% 等） | 小数第1位の百分率。**試投数の予測値が閾値未満なら表示しない** |
| 出場時間 | 小数第1位＋単位（`31.2分`） |
| 的中率 | 小数第1位＋**母数**（`68.2%（312試合）`） |
| Brier | `0.204`（小数点前のゼロを省略しない）。的中率ページの折りたたみ内のみ |

**`%` は勝率専用に予約する。** SHAP の寄与度をパーセントで表示しない。SHAP はログオッズ空間の値であり確率への加算ではないため、「寄与 +12%」は「勝率を12ポイント押し上げた」と誤読される。

Brier をトップ画面に出さない。

## 勝率の表示

**圧縮カードでも両チームの勝率を省略しない。**

```
ホームB 55% — 45% アウェイB
ほぼ互角 ・ 17:05
```

片側のみだと誰の55%か判別できない。また 55% と 81% が同じ見た目だと、**このツールで最も伝えるべき差**（ほぼ互角か一方的か）が失われる。45〜55% は「ほぼ互角」と併記する。

## 個人スタッツの表示

**段階開示とする。** 20項目 × 最大10人を一度に出すとモバイルでは読めない。

| 段階 | 表示内容 |
|---|---|
| 初期 | 出場時間 / 得点 / リバウンド / アシスト の4項目 |
| 展開 | フルボックススコア（2P・3P・FT の成功/試投、OR/DR、TO、ST、BS、F、FD、EFG%、TS%） |

規約

- **率は分数と併記する。** 単独で `48.9%` と出さない。`6.4 / 13.1（48.9%）` の形にする
- **試投数の予測値が閾値未満なら率を出さず分数のみ**（FG は `a >= 4`、2P/3P/FT は `a >= 3`）
- 誤差（`±`）は主要4項目にのみ併記する。全項目に出すと画面が埋まる
- **`＋/－` は試合前に表示しない。** 予測していない。結果画面で実績のみ出す
- ST / BS は誤差が平均値と同水準であることを詳細画面に1行注記する
- 展開状態は `localStorage` に保存しない（毎回たたんだ状態で開く）
- 展開は `<details>` 相当にし、キーボードで操作できるようにする
- `P(出場) < 0.5` の選手は表示しない
- 得点や率をクライアント側で計算しない。**サーバが導出した値をそのまま表示する**（実装ごとにずれるため）

## 判断根拠の表示

- **要因グループ単位**（チーム力 / 日程・疲労 / 選手 / 会場）で4〜5件
- 「ラベル / 値 / 有利な側」の3要素。主語を必ず入れる
- 数値の代わりに3〜4段階のバーで強さを示す
- 生の特徴量名（`elo_diff` 等）を画面に出さない
- 冒頭に一行の要約文を置く

```
チーム力の差        ＋82ポイント          → ホーム有利
アウェイの休養      中0日（ホームは中2日） → アウェイ不利
アウェイの主力欠場  平均28分の選手が1名    → ホーム有利
```

**選手個人の能力・資質への評価を含む表現を使わない。**

- 可: 「直近5試合の平均得点」「出場時間の減少」「欠場による影響」
- 不可: 「不調」「衰え」「戦力外」「期待できない」「使えない」

個人スタッツ予測の近傍に固定注記を置く。

> 個人予測は過去の公式記録から算出した統計的推定値であり、選手の能力や評価を示すものではありません。

## 状態の明示

ユーザーに対して予測の確からしさを隠さない。**配置まで決める。**

| 階層 | 対象 | 形式 |
|---|---|---|
| アプリ全体 | 更新遅延 | ヘッダー直下の全幅バナー |
| 試合カード | 暫定 / 確定 / 序盤 | メタ行の右端にバッジ |
| 試合詳細 | 同上 | 勝率ブロック直下に理由の説明文 |

| 状態 | 文言 | トークン |
|---|---|---|
| 暫定 | 暫定 ／ 詳細では「出場選手が未発表のため、直近5試合の出場傾向から推定しています。試合当日の午前中に更新されます。」 | `--warn` の**枠線と文字**（塗らない） |
| 確定 | 確定 | `--tint` の地 + `--ink-2` |
| 序盤 | 「両チームとも今季4試合しか消化していないため、この予測はまだ精度が安定しません」 | `--warn-bg` / `--warn` |
| 更新遅延 | 「表示中の予測は9月21日 6:02時点のものです。その後の欠場情報は反映されていません。」 | `--warn-bg` / `--warn` |

序盤の文言は主語と根拠の数字を必ず入れる。

**暫定の文言に具体時刻を書かない。** エントリー情報の確定タイミングは未確定（U-06 / P0-3）で、`gameday_update` のスロット（JST 11:00 / 13:00 / 16:00）とも一致する保証がない。「当日10時ごろ」のような時刻は、確定するまで書かない。

## 結果画面（試合後）

**このプロダクトで最も信頼が揺れる場面であり、専用の構成を持つ。**

```
実際のスコア   88 – 81（ホーム勝利）
予測          ホーム 68% / 予想スコア 84 – 78
判定          予測どおりでした（得点差の誤差 3点）
位置づけ      68%と予想した試合は、これまで42試合中29試合（69.0%）が的中しています
```

外れた場合の文言:

> この試合は予測を外しました。ホーム68%と予想しましたが、アウェイが勝ちました。**68%と予想した試合は、これまで42試合中29試合（69.0%）が的中しています。**

外れを認めた上で、較正が取れていること自体を信頼の材料として示す。**赤などの強い否定色を使わない。**

## 的中率ページ

一般向けから専門向けへ、この順で並べる。利用者の大半は統計の専門家ではない。

1. ベースライン比較を最初に置く: 「312試合中 223試合を的中（71.4%）。『ホームが必ず勝つ』と予想した場合は 60.1% でした。」
2. シーズン別の推移
3. **較正の言い換え（表）**: 「70%くらいと予想した試合 88件 → 実際に勝ったのは 63.6%。予想よりやや勝てていません。」
4. 較正曲線（グラフ）— 軸は日本語（横「予想した勝率」／縦「実際に勝った割合」）。対角線に「この線に近いほど、数字どおりに当たっている」と注記
5. 暫定/確定の内訳
6. 詳しい指標（折りたたみ）— Brier / Log Loss。「0に近いほど良い指標です」を併記

## 空状態

**Bリーグは年間の1/3以上がオフシーズン**であり、空状態は例外処理ではなく主要画面の一つである。

| 状態 | 文言 | 次のアクション |
|---|---|---|
| 試合がない日 | 「9月23日（水）に予定されている試合はありません。」 | 「次の試合は 9月24日（木）19:05 です」へのリンク |
| オフシーズン | 「今シーズンの全日程が終了しました。」 | 「シーズン中の的中率を見る →」 |
| 予測未生成 | 「この試合の予測はまだありません。試合前日の朝に公開されます。」 | — |
| エラー | 「予測を読み込めませんでした。時間をおいて再度お試しください。」 | `/about` へのリンク |

技術的なエラーコードを出さない。

## マークアップ

意味構造を持たせる。

| 要素 | 用途 |
|---|---|
| `<article>` | 試合1件 |
| `<h2>` | 日付見出し、対戦名（視覚的に隠してよい） |
| `<h3>` | 「なぜこの予測になったか」「個人スタッツ予測」 |
| `<nav>` + `<a>` | タブ。最低高さ44px、`aria-current="page"` |
| `<button aria-pressed>` | テーマ切替 |
| `<span>` + class | 装飾 |

**`<s>` `<i>` `<em>` を装飾目的で使わない。** `<s>` は取り消し線＝無効な内容を意味し、支援技術に誤った意味が伝わる。

確率ブロックは `role="img"` と一文の `aria-label` を持ち、内部の数値とバーは `aria-hidden="true"` にする。両方に読み上げ対象があると「68 32 ホーム68パーセント…」と重複する。

```
aria-label="ホーム <チーム名> の勝率68パーセント、アウェイ <チーム名> の勝率32パーセント。予想スコア 84対78"
```

行から試合詳細へ遷移する場合は `<a>` で実装し、`:focus-visible` のアウトライン色をトークン化する。**`--ink` を使う**（`--home` / `--away` を使うと、その色で塗られたバーの上でリングが消える）。

## レイアウト

- モバイルファースト。コンテンツ幅の上限は 440px 程度
- 左右 16px のガター。**375px 幅で横スクロールを発生させない**
- **カードを積まない。** 1試合 = 1レコードの表（`<tbody>` に `<tr>` 2本、時刻・バー・状態を `rowspan`）
- **影を使わない。** 影は「1件ずつ」に見せる装置であり、一覧性を最優先する方向性では逆に働く
- 角丸は 2px まで（実質の直角）。囲いは 1px の罫線だけで作る
- **密度の下限はタップ対象 44px が決めている。** 可読性ではない

## フォントとチャート

**書体は3系統。見出しのみ明朝、ラベルと本文はサンセリフ、数値はすべて等幅。**
いずれもシステムフォントで、**Web フォントは一切読み込まない**（旧版が許していた
「数字用の1ウェイト」も、数値を等幅システムフォントで組むため不要になった）。

```css
font-family: var(--f-sans);   /* 本文・ラベル */
font-family: var(--f-serif);  /* 見出しのみ */
font-family: var(--f-mono);   /* 数値はすべて。tabular-nums と併用 */
```

明朝が無い環境（一部の Android）ではゴシックに落ちる。**落ちても情報は失われない**
（明朝が担うのは見出しの格であって、数値でもラベルでもない）。

日本語 Web フォントを4ウェイト読むと初期表示分だけで数百KB〜1MB級になり、4G での LCP 2.5秒が
成立しない。**旧版は「数字とラテン文字のみを `unicode-range` で切り出した1ウェイト（60KB以内）」を
許していたが、数値を等幅システムフォントで組むことにしたため全廃した**（要件 8.1 / 基本設計 6.2）。

ロゴ・選手写真を使わないため LCP 要素はテキストになる。この優位をフォントで潰さない。

**チャートはライブラリを使わずインライン SVG で実装する。** 表示するのはシーズン数十点と較正バケット5〜10点で、Recharts や Chart.js は `/accuracy` だけで gzip 後100〜300KB 増える。

## 性能予算

| 項目 | 上限 |
|---|---|
| 初期 JS | **180KB（gzip）**。Next 16 + React 19 のベースラインが 169KB（要件 4.2） |
| 初期 CSS | 20KB |
| フォント | **0**（Web フォントを読み込まない） |
| 総転送量（初回） | 250KB |

CI で超過を検出する。

## データ取得

**ISR を使わない。** 今日の予測は Pages の静的アセット `/data/today.json` をクライアントで読む。Workers も D1 も消費しない。

`generateStaticParams` は**直近3シーズンの範囲のみ**を生成し、範囲外は `notFound()` を返す。日付が自由入力のままだと URL 空間が無限になり、クローラの総当たりで無料枠が枯渇する。

## ルーティング

| 画面 | パス |
|---|---|
| 今日の予測 | `/` |
| 日付別 | **`/schedule/[date]`** |
| 試合詳細 | `/games/[id]` |
| 結果 / チーム別 / 的中率 / このサイトについて | `/results` `/teams/[slug]` `/accuracy` `/about` |

**日付別を `/games/[date]` にしない。** 同一階層に `[date]` と `[id]` の2つの動的セグメントは置けず、ビルドエラーになる。仮に回避しても `/games/2026-09-22` と `/games/12345` の区別がパス形状に依存し、試合IDが日付形式を取った瞬間に破綻する。

## Next.js 16 の非互換

- **`params` / `searchParams` は Promise。** `const { date } = await params`。同期アクセスは型エラー
- **`next lint` は削除された。** `eslint .` を直接呼ぶ。`next build` はリントしない
- ESLint は **Flat Config**（`eslint.config.mjs`）。`.eslintrc.json` を作らない
- Node.js 20.9+ / TypeScript 5.1+ が必須
- Turbopack が既定。`output: 'export'` との組み合わせは Phase 0（P0-14）で確認する

```ts
// app/schedule/[date]/page.tsx
export async function generateStaticParams() {
  return listDatesInRecentSeasons(3).map((date) => ({ date }));
}

export default async function Page({
  params,
}: {
  params: Promise<{ date: string }>;
}) {
  const { date } = await params;
  if (!isWithinRecentSeasons(date, 3)) notFound();
  ...
}
```

## 静的生成の範囲

Pages の1デプロイあたりファイル数上限は **20,000**。**1ルートにつき5ファイル**が出る
（`index.html` + RSC ペイロード4本。工程11a の実測。要件 8.2）。**旧版は「HTML と RSC の
2ファイル」としていたが、実測はその2.5倍だった。**

| 範囲 | 推定ファイル数 | 上限に対して |
|---|---|---|
| 全10シーズン | 約50,000 | **250%（超過）** |
| 直近5シーズン（旧版） | 約25,200 | **126%（超過）** |
| **直近3シーズン（採用）** | **約15,100** | **76%** |
| 今季のみ | 約5,500 | 28% |

3シーズンより古いデータは Workers API からのクライアント fetch で表示する。**CI で `out/` のファイル数を検査し、18,000 を超えたら fail させる**（A-14）。1ルートあたりのファイル数は Next.js のバージョンで変わるため、この検査を省略しない。

```bash
find web/out -type f | wc -l
```

## 免責・出典

**全ページ共通フッター**に免責・出典・`/about` へのリンクを常設する。受け入れ基準 A-07 はこれで判定される。

## 禁止事項

- コンポーネント内での色のハードコード
- `--rule` / `--rule-soft` を本文に使うこと（テキストではなく線のトークンである）
- ダークのアクセント色をライト背景で使用すること
- 等幅数字の省略
- 片側だけの勝率表示
- 予想スコアの小数表示、的中率の母数省略
- 率を分数なしで単独表示すること
- 試投数が閾値未満の率を表示すること
- 個人スタッツ20項目を初期表示で全部出すこと
- 試合前に `＋/－` を表示すること
- 得点・率をクライアント側で計算すること
- SHAP 寄与度のパーセント表示
- `localStorage` の try/catch なしのアクセス
- 装飾目的の `<s>` `<i>` `<em>`
- `dangerouslySetInnerHTML`
- 375px 幅での横スクロール発生
- 免責・出典・的中率の表示省略、外れた試合を隠すこと
- チームロゴ、選手写真、公式サイト画像の使用
- 選手個人への評価表現
- ISR の使用
- **`/games/[date]` と `/games/[id]` を同一階層に置くこと**
- **`params` を同期でアクセスすること**（Next.js 16 では Promise）
- **`next lint` を使うこと**（Next.js 16 で削除。`eslint .` を使う）
- 直近3シーズンより広い範囲を静的生成すること
