# 設計文書

| 文書 | 内容 |
|---|---|
| `requirements.md` | 要件定義。スコープ、制約、特徴量の採否、法務、受け入れ基準 |
| `design-basic.md` | 基本設計。構成、データフロー、サブシステム、画面、テスト戦略 |
| `design-detail.md` | 詳細設計。DDL、API仕様、特徴量定義、学習手順、テスト、運用 |

**版数 1.3。** v1.1 で9領域レビューの指摘30件を反映、v1.2 で個人スタッツをフルボックススコアに拡張、**v1.3 で実装前検証（12件、うち9件実行）の結果を反映した**。

## 文書の優先順位

矛盾を見つけたときの判断材料。**低い側を黙って上書きしてよいという意味ではない。**

1. `../CLAUDE.md` の絶対ルール
2. `requirements.md`
3. `design-basic.md`
4. `design-detail.md`
5. `../.claude/skills/*/SKILL.md`

**文書間に矛盾を見つけたら、実装を止めて報告する。** 上位が正しいと判断した場合でも、下位文書を先に直してから実装する。

## 更新ルール

- 設計と異なる実装をしない。設計を変えるべきなら、先に文書を更新する
- 実装と文書のずれは `/sync-docs` で検出する
- 未決事項は `design-basic.md` 9章に集約する
- Phase 0 の実機検証項目は `requirements.md` 11章に集約する
- スキル（`.claude/skills/`）は判断基準と禁止事項を扱い、数値やキー名は本文書を正とする
- 設計にない仕様を推測で埋めない。止めて確認する

## 確定事項

grill-me（19問）と9領域レビューにより確定した主要な決定。

| 決定 | 内容 |
|---|---|
| プロダクト性格 | モデル予測型（ユーザー入力なし） |
| リリース順序 | Web先行 → iOS、Android は PWA のみ |
| データ調達 | 公式サイトを低頻度スクレイピング（日次上限3,000） |
| モデル | LightGBM。勝敗 + 得点差/合計 + 個人（ハードルモデル） |
| 配信 | **主要導線は静的JSON。Workers/D1 を経由しない** |
| 書き込み | **Workers の /internal/* に一本化**（REST直叩きを作らない） |
| 対象 | B.PREMIER のみ・全シーズン蓄積 |
| 出力 | 勝敗・勝率・予想スコア・**個人フルボックススコア**・根拠（v1全部入り） |
| 的中率 | モデルバージョン別に公開。**外れた試合も結果画面で対比表示** |
| UI | ライト既定＋ダーク切替 |
| コスト | 年額ゼロ〜5,000円、従量課金なし。独自ドメインのみ例外 |
| リポジトリ | public（機密は Secrets、生HTMLはコミット禁止） |

## v1.2 での変更（個人スタッツの拡張）

| # | 変更 |
|---|---|
| 1 | 予測項目を14カウント（2FGM/2FGA・3FGM/3FGA・FTM/FTA・OR/DR・AS・TO・ST・BS・F・**FD**）に拡張 |
| 2 | **率（FG%等）は予測せず導出**。試投数が少ないと離散値しか取りえないため |
| 3 | **PTS / FGM / FGA / TR は恒等式で導出**。独立に予測しない |
| 4 | **＋/－ と EFF は予測しない**（MAE 9〜12点規模で情報量がない）。実績のみ表示 |
| 5 | **チーム予測への整合化を第4段として追加**。独立予測のままだと合計が予想スコアと一致しない |
| 6 | レートは per-minute で学習（カウントだと出場時間の分散に支配される） |
| 7 | 表示を段階開示に（初期4項目 → 展開でフルボックススコア） |
| 8 | `monthly_train` を120分に延長、選手モデルの fold 数を3に制限 |
| 9 | 受け入れ基準 A-13〜A-15（整合性・率の非表示・恒等式）を追加 |

## v1.3 での変更（実装前検証の反映）

設計段階で12件の数値検証を試み、9件を実行した（3件は外部レジストリへのアクセス制限により Phase 0 へ送った）。**うち2件で設計の誤りが見つかった。**

| # | 変更 | 根拠 |
|---|---|---|
| 1 | **整合化アルゴリズムをロジット空間シフトに全面変更。** 倍率スケール方式は収束しない | 1,500ケースの実測で項目誤差最大24.7%・得点誤差4.42点。失敗の73%がFT成功率のクリップ。ロジット方式で得点誤差ゼロ・制約違反ゼロ |
| 2 | **個人・チームとも「成功数」ではなく「試投数 + 成功率」を予測する構造に変更**（DDL含む） | 独立生成では約2%の確率で `FT成功数 > FT試投数` という実行不能な目標が生じ、整合化が原理的に成立しない |
| 3 | **`prediction_team_targets` テーブルを新設**し、チーム目標に CHECK と恒等式を課した | 同上 |
| 4 | **ECE の閾値を n 依存のノイズフロア基準へ**。`n < 500` では ECE をゲートに使わない | 完全較正モデルの ECE 95%点は n=200 で 0.116、n=1,200 で 0.048 |
| 5 | **A-09 を Brier ベースに書き換え、n の下限を500に**。Accuracy を表示専用に降格 | 理想モデルとベースラインの Accuracy 差の SD は n=200 で 0.041。`+0.03` はノイズと区別できない |
| 6 | **静的生成の範囲を直近5シーズンに限定**し、CI にファイル数検査を追加 | 全10シーズンでは 20,184 ファイルで Pages の20,000上限を超過 |
| 7 | **バッチサイズをテーブルごとに算出**（`floor(100/列数)×40`） | D1 Free の「1呼び出し50クエリ」を9テーブル中6つで超過していた。`player_predictions` は500件で167文 |
| 8 | **`artifact_text` に1.5MB上限チェック**を追加、`num_boost_round` を1,200に | D1 の1行上限は2,000,000バイト。`num_leaves=15`・1,500本で 2.56MB |
| 9 | **学習入力をスナップショットに一本化**（D1 からの一括読み出し経路を廃止） | 読取枠の消費と可用性依存を構造的に排除 |
| 10 | **子テーブル（`player_predictions` / `prediction_reasons` ほか）にも凍結トリガ**を例外なく追加 | 根拠だけ後から書き換えられるなら不変性の主張が成立しない |
| 11 | **勝率の導出を2経路とも実装**し、Phase 0 で比較する方針に | どちらが優るかは実データでしか決まらない |
| 12 | **`/games/[date]` → `/schedule/[date]`** | 同一階層に `[date]` と `[id]` は置けない |
| 13 | **Next.js 16 に確定。** `next lint` 廃止 → ESLint CLI、`params` は Promise | Next.js 16 の公式リリースノート |
| 14 | **`gameday_update` を「固定cron 3スロット + 対象絞り込み」に**（動的起動は実現不能だった） | GitHub Actions の `schedule` は動的に変更できない |
| 15 | **WAF レートリミットを無料枠の実仕様に**（10秒カウント / 10秒ブロック） | 無料プランでは1分単位の設定ができない |
| 16 | **Workers CPU 10ms を Critical → Medium に下方修正** | 500行の JSON パース＋検証は実測1.34ms。制約は CPU ではなくクエリ数だった |
| 17 | 受け入れ基準を A-18 まで拡張、品質ゲートに Phase 0 実機検証の完了を追加 | — |
| 18 | `CLAUDE.md` に作業規約を追加（仕様補完の禁止、マイグレーション追記のみ、時刻の扱い、依存追加の手順、止まるべき条件） | — |

検証スクリプトは `../verification/` にある。実データに差し替えれば Phase 0 でもそのまま使える。
