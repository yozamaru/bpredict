## 1. システム全体像

### 1.1 構成方針

3つの実行環境に役割を分離する。

| 環境 | 役割 | 言語 |
|---|---|---|
| GitHub Actions | データ取得、特徴量生成、学習、推論、**静的JSONの書き出し** | Python |
| Cloudflare Workers | 書き込みの関門、動的クエリの配信 | TypeScript |
| Cloudflare Pages | 画面の描画、**予測データの静的配信** | TypeScript（Next.js 静的出力） |

重い処理を GitHub Actions に閉じ込め、**主要導線は Workers も D1 も経由させない**。これにより無料枠の消費を構造的にゼロに近づけ、枠が枯渇しても当日の予測が表示され続ける状態を作る。

### 1.2 構成図

**重要な設計判断**

1. **D1 への書き込みは Workers の `/internal/*` 経由に一本化する。** D1 REST API を直接叩く経路は設けない。REST 直叩きを許すと、Zod 検証・認可・「tipoff 経過後は拒否」というガードがすべて迂回可能になり、予測の不変性という中核価値を守る関門が存在しなくなる。
2. **今日の予測・試合一覧は静的JSONで配信する。** バッチが `web/public/data/*.json` を書き出し、Pages の静的アセットとして配信する。Workers リクエストと D1 読取を消費しない。
3. **ISR を使わない。** Cloudflare Pages 上の Next.js は ISR が成立しない（要件7章）。
4. **バッチは D1 を「入力データ」として読まない。学習・特徴量生成・推論は自前のスナップショットを参照する。** バッチが取得・正規化したデータは、Workers 経由で D1 に書き込むのと同時に、リポジトリ配下の Parquet スナップショット（`batch/snapshot/`）にも書き出す。特徴量生成・学習・推論はこのスナップショットのみを読む。

   **なぜ D1 からの一括読み出し経路を設けないのか。** D1 は「書き込み先」であって「学習データの供給元」ではない。一括エクスポート経路を残すと、(a) 読取行数の上限（500万行per日）を学習が消費する構造が残り、(b) 学習時のデータ取得が Cloudflare の可用性に依存し、(c) 「バッチは D1 を読んでよい」という例外が一度でも許されると、逐次クエリへの退行を設計で止められなくなる。**スナップショットが唯一の学習入力である**と決めれば、この3つが同時に消える。

   **ただし、禁止するのは「入力データとしての読み取り」であって、運用上の読み取りではない。** backfill の再開判定（取得済みID）、結果照合の対象取得、モデル artifact の読み出し、現行モデルの評価値の取得は、**Workers の `/internal/*` に置いた GET 経由**で行う。いずれも1回あたり数行〜数百行で、読取枠にも可用性にも影響しない。これを禁じると再開可能な backfill も月次学習も実装不能になる。**D1 REST API の直叩きは、区分を問わず全面禁止**である（2.4）。

   スナップショットは決定論的に再生成でき、D1 の内容と一致することをテストで保証する（8.3）。

### 1.3 データフロー

```
試合前日以前（日次 06:00 JST）
  前日結果取得 → 結果照合 → Elo再計算 → 特徴量生成 → 推論
  → predictions 追記 → 静的JSON書き出し → Pages デプロイ

試合当日（固定cron 3スロット。各スロットで tipoff > now+30分 の試合に限定）
  エントリー取得 → 出場者確定判定 → 再推論
  → predictions 追記（旧行を is_active=0）→ 静的JSON更新

試合開始時刻
  freeze（Workers の Cron Trigger が毎時実行、または読み取り時の遅延判定）
  以後 /internal/predictions は当該試合を 409 で拒否

翌日 06:00 JST
  結果取得 → 確定予測と照合 → prediction_results 登録 → 集計テーブル更新

月次 / シーズン開始時
  全データ再学習 → 同一評価ウィンドウで検証 → 基準を満たせば有効化
```

## 2. サブシステム設計

### 2.1 データ取得サブシステム（Python）

```
batch/
├── scraper/          外部サイトへのアクセス。HTTPのみを担当
│   ├── client.py         レート制限・日次上限・サイズ上限・robots照合
│   ├── schedule.py / boxscore.py / roster.py / entry.py
├── parser/           レスポンス本文 → 構造化データ。サイト構造への依存をここに閉じる
│   ├── extract.py        <script> 内の埋め込みJSONの取り出し
│   ├── schedule_parser.py / boxscore_parser.py / roster_parser.py / entry_parser.py
│   ├── fields.py         サイトのフィールド名 → DB列 の対応表
│   └── validators.py     値域検証
├── loader/           Workers /internal/* への書き込み
└── models.py
```

**設計原則**: サイト構造の変更は `parser/` のみの修正で吸収できること。`scraper/` は HTTP の作法だけを持ち、`parser/` は**レスポンス本文の解釈**だけを持つ。

**`parser/` の責務は「HTML の解釈」ではなく「レスポンス本文の解釈」である。** Phase 0 の実地確認（2026-09-21）で、試合詳細ページのボックススコアが **HTML の表としてはレンダリングされておらず、`<script>` 内に埋め込まれた JSON として配信されている**ことが判明した。列見出しは JavaScript のテンプレート文字列の中にあり、実行時に組み立てられる。

したがって `parser/` は次を行う。

1. 試合一覧を**大会区分（`event`）で絞る** — リーグ戦とチャンピオンシップのみ
2. レスポンス本文から**埋め込み JSON を取り出す**（`extract.py`）
3. **必要なフィールドだけを** DB の列に写す（`fields.py` の対応表）
4. 値域と恒等式を検証する（`validators.py`）

**オールスターゲームを取り込むと Elo が壊れる。** 選抜チーム同士の対戦であり `clubs` に存在しないチームが現れる。入替戦は相手が B2 のクラブで対戦相手を解決できない。絞り込みは**ラベルではなく値で**行う（`event=2` のラベルは 2026-27 で「B1リーグ」から「B.PREMIER」に変わっている）。区分は `games.competition` として保持する（要件 5.3、詳細設計 1.3）。

**クラブの判定も名前ではなく公式の `TeamID` で行う（v1.28）。** 日程ページの行は略称を使うことがあり（2020-21 の `千葉J` / `横浜BC`）、クラブ選択肢の正式名称と一致しない。名前で絞ると**実在の試合を落とす** — 実際に128試合が落ちた。`TeamID` は改称・リーグ再編をまたいで不変である（Phase 0）。

この変更の影響は `parser/` に閉じる。`scraper/` は変わらず、取得頻度・法務の立論・値域検証の方針も変わらない。**DOM を辿るより壊れにくい**（クラス名やレイアウトの変更に影響されない）。

**登録選手一覧（`/roster/`）は埋め込みJSONを持たない。** ボックススコアと違い HTML を
読む（2026-10-05 の実測。`_contexts_*` が1つもない）。**`parser/` の責務が
「レスポンス本文の解釈」である**ことがここで効く — 取り出し方が違っても、解釈の
置き場は変わらない。取る項目は選手ID・氏名・ポジション・背番号の4つで、
**`登録区分` は出典が無く、`身長` は取りに行かない**（要件 5.3）。

**JSON 全体をそのまま保存しない。** 同じ JSON には審判名（特徴量 #30 は見送り）とプレイバイプレイが含まれる。要件 5.3「予測に不要な属性は取得対象から除外する」に従い、対応表にある列だけを抜き出す。

**サイトが将来 HTML の表に戻った場合も、`parser/` の修正だけで吸収する。** 取り出し方（`extract.py`）と解釈（`*_parser.py`）を分けてあるのはそのためである。

**アクセス制御**

| 項目 | 値 |
|---|---|
| リクエスト間隔 | 最低3秒 + 0〜1秒のジッタ |
| 並列度 | 1 |
| 日次リクエスト上限 | 3,000（クライアント側で強制） |
| レスポンスサイズ上限 | 5MB（超過で中止） |
| タイムアウト | 30秒 |
| 中止条件 | 429 / 503 受信時は取得区間のみ中止（内部処理は継続） |
| 事前確認 | `robots.txt` と利用規約のハッシュ照合。変更検知でジョブ中止 |
| User-Agent | `<name>/1.0 (+https://<domain>/about)` |

**値域検証**（`parser/validators.py`）

スクレイピングは入力が信用できないパイプラインである。必須項目の有無だけでなく値域も検証し、範囲外は当該試合をスキップする。異常値が Elo 計算に流れ込むとレーティング全体が破壊され、冪等な再実行では復旧しない。

| 項目 | 範囲・条件 |
|---|---|
| `pts` | 0–250 |
| `minutes` | 0–60 |
| シュート | `fg2m <= fg2a`、`fg3m <= fg3a`、`ftm <= fta` |
| `pf` | 0–6 |
| `attendance` | `<= capacity × 1.2` |
| `possessions` | 50–120。**値域外は当該試合をスキップせず NULL にする**（中断・不成立の短い試合が実在する。詳細設計 1.3） |
| 恒等式 | `pts = fg2m×2 + fg3m×3 + ftm`、`fga = fg2a + fg3a`、`reb = oreb + dreb`、得点・シュート数はチーム合計と選手合計を照合。**照合の分母には `Category=2` の行も含める**（得点を持つ `Category=2` 行が実在する。詳細設計 4.4）。リバウンド等はチーム記録を含む公式合計を使う |

### 2.2 特徴量サブシステム（Python）

```
batch/features/
├── base.py           基底クラスと登録機構
├── team_strength.py / schedule_ctx.py / player.py / venue.py
├── dataset.py        スナップショットの読み込みとメモリ内データセット
└── builder.py        as_of 時点の特徴量ベクトル生成

batch/snapshot/       学習入力（Parquet）。バッチが書き、バッチが読む
├── games.parquet / team_games.parquet / team_game_stats.parquet
├── player_game_stats.parquet / game_entries.parquet
├── clubs.parquet / players.parquet / venues.parquet / seasons.parquet
├── club_seasons.parquet / player_seasons.parquet / venue_revisions.parquet
├── team_ratings.parquet  Elo ほかの日次スナップショット（特徴量が参照する）
└── MANIFEST.json     各ファイルの行数・SHA256・生成時刻・最新 finished_at
```

**中核となる設計**: すべての特徴量関数は `as_of` を引数に取り、**その時刻以前に終了した試合の情報のみ**を参照する。絞り込みは `tipoff_at` ではなく `finished_at` で行う（`tipoff_at` で絞ると、17:05開始・19:05終了の試合が19:05開始の試合の確定情報として混入する）。

**特徴量生成と学習は D1 を読まない。** 入力はバッチ自身が保持する Parquet スナップショットのみとする。試合8,000件・選手スタッツ20万行は Parquet で数十MB、メモリ上でも数十MB に収まるため、全量をロードして結合・フィルタする。

この方針はリーク防止と無料枠維持の両方に効く。逐次クエリ方式では、`games` の全件スキャンを試合ごとに繰り返すため **1日150万〜1,450万行**（上限500万行per日）に達し、学習時は億行規模になる。一括エクスポート方式でも D1 の読取枠を消費するうえ、学習が Cloudflare の可用性に依存する。**スナップショットを唯一の入力と決めることで、D1 の読取行数は「公開APIの動的クエリ分」だけになる。**

**スナップショットの整合性保証**

| 項目 | 内容 |
|---|---|
| 書き出し | ファクト・マスタは `daily_ingest` のステップ3（正規化直後、D1 書き込みと同一データから）。`team_ratings` はステップ7（再計算直後） |
| 形式 | Parquet（列指向・圧縮。CSV よりロードが速く型が保存される） |
| コミット | リポジトリに含める。生HTMLではなく事実データの構造化結果であるため 4.5.2 に抵触しない |
| 検証 | `MANIFEST.json` に各ファイルの行数と SHA256 を記録。学習前に照合する。**`team_ratings` を書き出した後に MANIFEST を再生成する**（ステップ3の時点の MANIFEST のままだと `test_snapshot_manifest_hashes` が落ちる） |
| 部分書き出し | `write_snapshot(..., tables=["team_ratings"])` で対象テーブルだけを書き直す。スナップショットはリポジトリにコミットするため、変わっていないファイルを毎回書き換えると差分が無意味に膨らむ。**MANIFEST は書き直さなかったテーブルもディスクの現物から digest を取り直す**（前回の MANIFEST から引き写すと、別経路でファイルが変わったときに MANIFEST だけが正しく見える） |
| 再現性 | スナップショットは D1 から決定論的に再生成できる（`scripts/rebuild_snapshot.py`）。ただし**これは復旧手段であり、日常の学習経路ではない** |
| 一致テスト | **`test_snapshot_reflects_the_master_csvs`**（下記。D1 を要しない）。`test_snapshot_matches_d1`（CI では D1 ローカルに対して実行）は**まだ実装していない** — 行数と主キー集合しか見ない仕様であり、**下記の壊れ方は捕まえられない** |

#### 同じエンドポイントを共有する列は、NULL で上書きされないようにする

**2026-10-05 に、取り込みが会場の座標を消していた。** `POST /internal/games` は
試合の取り込みとマスタの投入の両方が使い、`DO UPDATE SET col = excluded.col` が
**送られてこなかった列を NULL にしていた**。失った10会場は 9/28〜10/4 の試合で
使われた会場と完全に一致した（詳細設計 3.4）。

**この節の規則（スナップショットにも書く）と対になっている。** あちらは
「D1 に書いたものがスナップショットから見えない」、こちらは
「スナップショットにある値が D1 から消える」。**どちらも「2つの置き場のうち
片方だけが正しい」状態であり、気づくのは次に読んだときである。**

#### D1 を更新するジョブは、同じ値をスナップショットにも書く

**2026-10-03 に、スナップショットがマスタの3列で古いまま残っていた。**

| 列 | 出典（リポジトリの CSV） | D1 | スナップショット |
|---|---|---|---|
| `venues.prefecture` / `lat` / `lng` | `venues_geo.csv`（140行） | **140件** | **0件** |
| `club_seasons.primary_venue_id` | `club_primary_venues.csv`（225行） | 未投入 | 0件 |
| `venue_revisions.capacity` | `venue_revisions.csv`（**ヘッダのみ**） | 0件 | 0件 |

**スナップショットは特徴量・学習・推論の唯一の入力である**（絶対ルール3）。したがって
D1 に 140件の座標があっても、**特徴量からは1件も見えない**。#16（移動距離）は
「座標がない」として全件欠損し、#15 と #29 の会場別も同じ道をたどる。

**原因は、ジョブが D1 にだけ送っていたことである。** `recompute_ratings` と
`build_venue_revisions` は「スナップショットを先に書き、同じ値を D1 にも送る」順序を
守っているが、後から足した `resolve_venue_geo` と `derive_primary_venues` は
**D1 にだけ送っていた**。

**順序の規則を、Elo だけのものから全ジョブの規則に広げる。**

| ジョブ | 書くテーブル | スナップショット |
|---|---|---|
| `recompute_ratings` | `team_ratings` | 書く |
| `build_venue_revisions` | `venue_revisions` | 書く |
| **`resolve_venue_geo`** | `venues` | **書く（v1.43 で追加）** |
| **`derive_primary_venues`** | `club_seasons` | **書く（v1.43 で追加）** |

**スナップショットへの反映は D1 を要しない。** 出典はいずれもリポジトリの CSV で
あり、適用は決定論的である。したがって両ジョブに**D1 に送らないモード**を置く
（詳細設計 4.10 / 4.11）。トークンのない手元でも、CI でも流せる。

**`test_snapshot_matches_d1` では捕まらない。** あれは行数と主キー集合を見る仕様で、
**列の値が古いことは見ない**。代わりに `test_snapshot_reflects_the_master_csvs` を置く
— CSV に値がある行では、スナップショットの対応する列も埋まっていること。D1 を
要しないため CI でそのまま走る。

**`test_snapshot_matches_d1` はまだ実装していない。** 基本設計と詳細設計の両方が
名前を挙げているが存在せず、**存在しないことに誰も気づいていなかった**。実装するなら
行数と主キー集合だけでなく**列の値も比べる**（そうでなければ、この壊れ方をもう一度通す）。

**`team_ratings` もスナップショットに含める。** `elo_home` / `elo_away` は `team_ratings` の直前スナップショットを参照する特徴量であり、これが無いと特徴量生成が D1 を読まざるをえなくなる。書き込みの向きは次の順序に固定する。

```
Elo を再計算（入力はスナップショット）
  → team_ratings.parquet へ書き出し（特徴量生成が読むのはこちら）
  → 同じ値を /internal/ratings 経由で D1 にも送る（公開APIの表示用）
```

D1 側は表示のための複製であり、**特徴量生成が D1 の `team_ratings` を読むことはない**。詳細設計 1.4 の「Elo をその場で計算する実装にしない」は引き続き有効で、特徴量関数は必ず書き出し済みのスナップショットを参照する。

スナップショットが破損・欠損した場合、学習を中止して現行モデルを継続使用する（推論は可能。推論に必要な特徴量も同じスナップショットから作るため、欠損時は前回の静的JSONを維持する）。

### 2.3 モデルサブシステム（Python）

```
batch/model/
├── dataset.py         学習行列の構築（時間減衰重み・観客制限フラグを含む）
├── train_winner.py    勝敗（経路A）
├── train_score.py     得点差と合計得点（経路B の σ 推定を含む）
├── train_team_rates.py チームの試投数・成功率（整合化の目標値）
├── train_player.py    出場確率 → 出場時間 → スタッツ
├── reconcile.py       整合化（ロジット空間シフト。要件 6.8.5）
├── calibrate.py       較正（必要性の判定を含む）
├── explain.py         SHAP のグループ集約
├── evaluate.py        walk-forward 検証とベースライン比較
└── registry.py        モデルの保存・読み出し・バージョン管理
```

**モデル構成**

| モデル | 種別 | 出力 |
|---|---|---|
| **Winner** | **全特徴ロジスティック回帰** | ホーム勝利確率（経路A・**採用**）。**v1.44 で LightGBM 二値分類から変えた** — A-09 を満たすのはこの構成だけ（要件 6.1.1） |
| Margin | LightGBM 回帰 | 得点差（ホーム − アウェイ）。**v1.44 以降、予測値は予想スコアに使わない** — 必要なのは**残差 σ** で、それが「勝率 → 得点差」の変換係数になる（要件 6.1.1） |
| Total | LightGBM 回帰 | 合計得点 |
| TeamRates | LightGBM 回帰 × 14 | **チームの試投数・成功率・その他カウント**（選手予測の整合化目標） |
| PlayerAvail | LightGBM 二値分類 | 選手の出場確率 |
| PlayerMinutes | LightGBM 回帰 | 出場時間（出場する場合） |
| PlayerRates | LightGBM 回帰 × 14 | カウント11項目の単位時間レート + 成功率3項目 |

予想スコアは `home = (total + margin) / 2`、`away = (total - margin) / 2` で導出する。各チーム得点を独立に回帰すると、勝率と矛盾した出力が生じ、誤差の分散も過大になる。

**`margin` は Margin 回帰の予測値ではなく、勝率から導く**（v1.44。要件 6.1.1）。

```
margin = σ · Φ⁻¹(p)     p は Winner（ロジスティック回帰）の出力。[0.05, 0.95] にクランプ済み
```

**これで勝率と予想スコアが同じ値から出るため、符号の食い違いが原理的に起きない。**
旧版は経路B（`p = Φ(margin/σ)`）で同じ性質を得ていたが、**経路B は A-09 を満たさなかった**
（+0.0019 / CI が 0 を跨ぐ）。**向きを逆にすることで、A-09 と整合の両方を取る。**

**精度は落ちない**（チーム得点 MAE 8.832 対 8.839。同じウィンドウの実測）。2つの得点差の
相関は 0.97 で、ほぼ同じものを別の経路で出していた。

#### 合計得点（Total）の上積みはほぼゼロである（v1.46 で測った）

**木が4本で止まっている**ことに気づいて平均ベースラインと比べた（2026-10-05。
`verification/RESULTS.md`）。

| 目的変数 | モデル MAE | **平均を出すだけ** | 上積み |
|---|---:|---:|---:|
| 合計得点 | 14.1639 | **14.1713** | **0.05%** |
| 得点差 | 10.2632 | 12.2005 | **15.9%** |

**つまり予想スコアは「リーグ平均の合計（157.6点）を、勝率から出した得点差で
振り分けたもの」である。** 情報はすべて得点差の側にある。

**設計は変えない。** 要件 6.1.1 の「Total 回帰も引き続き必要である（合計得点は
勝率から導けない）」は成立しており、平均より悪くはない。**隠さず記録する** —
第2段（PlayerMinutes）の「上積み 0.60%」と同じ性質の結果であり、
**改善の余地がどこにあるか**を示している（ペース系の特徴量はいまチーム力の
代理になっており、合計得点を当てる設計になっていない）。

**勝率は2経路とも実装し、Phase 0（P0-11）で比較して採用経路を決める。**

| 経路 | 式 | 長所 | 短所 |
|---|---|---|---|
| A: Winner 直接 | `p = Winner(x)` | logloss を直接最適化するため較正が良い | Margin と符号が食い違いうる |
| B: Margin から導出 | `p = Φ(margin / σ)`、σ は残差標準偏差（実測） | 勝率と予想スコアが定義上一致する | 残差が正規でない場合に較正が崩れる |

判定は同一ウィンドウの Brier と ECE で行い、B が A より Brier で 0.003 以上劣る場合のみ A を採用する（要件 6.1）。採用経路は `model_versions.win_prob_source` に記録する。両方を毎回学習するため、チームモデルの学習時間は約1.2倍になる。

**測定した（2026-10-02）。** いったん経路B を採用したが、**2026-10-04 に経路A へ
変えた** — Winner モデルを全特徴ロジスティック回帰にすると A-09 を満たし、
経路B（LightGBM の Margin 由来）は満たさなかった。詳細は要件 6.1.1 と
`verification/RESULTS.md`。

| モデル | Brier | Elo単体との差 | 95%信頼区間 | A-09 |
|---|---:|---:|---|---|
| **全特徴ロジスティック（採用）** | **0.198699** | **+0.004045** | **[0.00182, 0.00617]** | **満たす** |
| LightGBM（経路A） | 0.201241 | +0.001503 | [−0.00076, 0.00370] | 未達 |
| 経路B | 0.200807 | +0.001937 | [−0.00005, 0.00394] | 未達 |

**判定には「A-09 を満たす経路だけを候補にする」段が先に来る**（要件 6.1）。
旧版の規則（差が 0.003 未満なら整合性を優先して B）だけでは、**A-09 を満たさない
経路を強制しうる**ことが実際に起きた（B − A = +0.0021）。

**LightGBM はベースライン3段目に降りた**（要件 6.4）。「2 を超えられなければ
LightGBM を使う理由がない」という旧版の条件に、**LightGBM 自身が当たった**。

**分割器を2つ作らない。** `walk_forward` に目的変数を渡す形にし、勝敗・得点差・合計得点をすべて同じ関数で評価する。P0-11 は「**同一の walk-forward ウィンドウ**で Brier と ECE を測る」ことを要件としており、分割の実装が2つあると**片方だけ直したときに比較が成立しなくなる**。

**回帰の結果に分類の指標を呼べないようにする。** `Evaluation` を分類と回帰で共用する以上、`brier` や `ece` を得点差の評価に対して呼ぶと**意味のない数字が黙って返る**。実測値が 0/1 でないときは落とし、回帰には `mae` と `residual_sigma` を持たせる。

**有意性は「採用する経路」で測る。** 採用経路を先に決めてから Elo単体との差を測る。A に対して測った有意性を B の採用根拠にすると、**判定の対象がずれる**（受け入れ基準 A-09 は「Brier が Elo単体より有意に良い」ことを求める）。

**TeamRates を新設する理由。** 選手予測の整合化（要件 6.8.5）にはチーム側の目標値が必要だが、旧版は「直近N試合平均 × ペース比」という素朴な生成しか定めていなかった。各項目を独立に生成すると**約2%の確率で「FT成功数 > FT試投数」のような実行不能な目標**が生じ、整合化が原理的に成立しない。チーム側も選手側と同じ「試投数＋成功率」の構造で予測すれば、制約が構造的に保証される。

**TeamRates の入力は目的変数ごとに絞る。** 1行は「1試合 × 1クラブ」であり、
勝敗モデル（1行 = 1試合、ホーム視点固定）とは行の単位が違う。**共有3列
（自他のペース・休養）＋ 目的変数ごとの2列（自分の直近10試合の水準・相手が許した
水準）= 1モデル5列**とする。列の定義は詳細設計 2.2.1 にある。

**14本すべてに同じ70列を与えない。** 工程8の実測が「列を増やすと薄まる」と
言っている — Four Factors を4指標すべて入れると Brier が 0.0006 悪化し、
`ortg_diff` の寄与度を 2.89% → 2.32% に薄めた（`verification/RESULTS.md`）。
TeamRate は14本それぞれが1項目を当てるモデルで、`fg3a` を当てるのに `stl` の
履歴は要らない。学習行は11シーズンで約12,500行であり、6列はこの行数に見合う。

**成功率3項目はほとんど当たらない（2026-10-03 の実測）。** 平均ベースラインに
対する改善は `fg3_pct` **0.1%** / `ft_pct` 1.3% / `fg2_pct` 4.1%。1試合の成功率が
ほぼノイズであるという性質がそのまま出ている。一方で**試投の配分はよく当たる**
（`fg3a` 30.7% / `fg2a` 24.2%）。

**この帰結を承知しておく。** 整合化の前段は成功率3項目に**共通の**ロジットシフトを
入れるため、3項目の相対差はモデルの出力が残り、水準は Margin / Total が決める。
したがって保存されるチーム目標は実質「**リーグ平均に近い配分を予想スコアに合わせて
上下させたもの**」である。**「チームのシュート成功率を予測している」とは言えない。**
整合化が成立すること自体は精度とは独立で、「試投数 × 成功率」という持ち方から
構造的に保証される。

**`is_home` は列に入れない。** クラブ視点では定数列ではないため当初は入れていたが、
**実測で効果が検出できなかった**（14本中8本で抜いた方が良く、MAE の変化は
中央値 −0.040%）。ホームアドバンテージは整合化の前段が予想スコアに合わせることで
入る。数値は `verification/RESULTS.md`。

#### 第3段で分かった2つ（v1.54）

**`k`（シュリンクの強さ）を MAE で選べない。** シュリンクは目的変数
`(made + k × prior) / (att + k)` そのものを変えるため、**`k` を上げると分散が
潰れて MAE が必ず下がる**。最初の測定は k=80 を「最良」と出したが、そこでは
目的変数と実現値の相関が 0.52 しかなく、`{pct}_prior` を特徴量に与えている
ためモデルは prior を写すだけで当たっていた。**固定の物差し（実現値
`made / att`）に対して測り直す**（詳細設計 2.3.1）。

**成功率2項目は学習しないベースラインに負ける。** `fg3_pct` −0.15% /
`ft_pct` −1.98%（「直近の水準をそのまま出す」に対して）。2.3 の TeamRate で
見たのと同じ性質（1試合の成功率はほぼノイズ）であり、個人では母数がさらに
小さい。**運営者は承知のうえで「モデルのまま出す」と決め、代わりに画面へ
注記を出すことにした**（要件 6.8.1）。

#### 候補集合に `player_seasons` を使わない（v1.49）

**ロスターが 3,495行入ったが、それを候補にすると絶対ルール1 に違反する。**
取得した断面は**時点を持たない**（`joined_on` が NULL）ため、季中に加入した選手が
加入前の試合の候補に現れる。

**候補は「当季の `finished_at <= as_of` の出場実績 ∪ 前季にそのクラブで出場」**と
する。2案を実データ12,592行で測り、**リークしない案のほうが recall でも上回った**
（0.9871 対 0.9812。`verification/RESULTS.md`）。

**案A（ロスター）には欠陥が2つあった。** 季中の加入が混入するだけでなく、
**季中に離脱した選手が断面から消えている**ため、実際に出場した 2,767件に
学習行が作れない。したがって「リークを承知で精度を採る」取引が成立しない —
`club_seasons.primary_venue_id` で運営者が許容したのは**リークする案だけが
成立した**場合であり、ここは当たらない。

**弱いのは季の1試合目だけである**（recall 0.5449 / 全体の1.9%）。
既にある「序盤」の開示が覆う範囲に収まる（要件 8.4）。

#### 第1段は実際に効いている（2026-10-05 の実測）

| 予測 | Brier | Accuracy |
|---|---:|---:|
| **モデル（LightGBM / 5列）** | **0.042352** | **0.9466** |
| 直近10試合の出場率をそのまま出す | 0.060539 | 0.9177 |

**第2段とは結果の性質が違う。** あちらは上積みが 0.60% しかなかったが、
第1段は **30.0%** 上回る。出場率は **0.5917**（40.8%が出場しない）で、
要件 6.8.4 の「登録選手の3〜4割が0分」とよく合う。

**ただし ECE の採用ゲート（詳細設計 4.6 の条件4）は満たさない**（0.0109 対
閾値 0.0028）。**登録する前に、較正器を入れるか条件を改めるかを決める** —
確率は表示されないが、整合化の期待出場時間（`P(出場) × E[MIN]`）では
配分の重みになる。詳細設計 2.3.1 に選択肢を書いた。

**シュートは「試投数 + 成功率」で予測し、成功数は導出する。** 成功数と試投数を独立に予測すると、整合化の段階で `成功数 > 試投数` が生じ、それを防ぐためのクリップが収束を壊す（実測で失敗ケースの73%が FT 成功率で発生）。試投数と成功率の組で持てば、成功率をロジット空間でシフトするだけで制約が自動的に満たされる。

モデルが出す成功率は「この選手のこの試合における期待成功率」という連続量であり、**画面に出す `FGM / FGA` とは別物**である。表示する率は必ず導出値で、分数と併記する。`FGM` は `2FGM + 3FGM` として導出し、独立に予測しない（恒等式が崩れる）。

**成功率3項目は per-minute にしない。** 率は時間当たりの量ではない。目的変数は過去試合の成功率、学習重みは試投数とし、`(made + k × prior) / (attempted + k)` でシュリンクした値を使う。出力は `clip(0.01, 0.99)`（ロジット変換の定義域確保）。

**＋/－ を予測しない。** チームの結果を個人に帰属させた指標で1試合の分散が極端に大きく、MAE は 9〜12点規模になる。しかも「チーム得点差予測 × 出場時間シェア」以上の情報を持たない。実績のみ表示する。

#### 整合化（第4段）が必須である理由

選手ごとに独立予測した値をそのまま表示すると、**5人の得点合計がチームの予想スコアと一致しない**。同じ画面に矛盾した数字が並ぶ。期待出場時間を200分に正規化し、試投数をチーム目標へ比例スケールし、成功率を**ロジット空間で一律シフト**してチーム成功数に合わせ、最後に得点を恒等式で導出する。手順は `docs/requirements.md` 6.8.5 に定義する。

**単純な倍率スケールは使わない（検証済み）。** 成功率を `[0, 1]` の範囲で一律に掛け算すると、1.0 に張り付いた選手が出た時点で合計を目標に合わせられず振動する。1,500ケースの実測では、2回反復後の項目誤差の最大が 24.7%、得点誤差が 4.42点に達した。ロジット空間シフトに変更した結果、**得点誤差ゼロ・制約違反ゼロ・成功率が [0,1] を出たケースゼロ**になった。

**反復は1回でよい（2026-10-03 に 3回から訂正）。** 手順4で合計を目標に合わせ、手順5は試投数を触らずに成功率だけを動かすため、2回目以降は倍率1・シフト0で何も変えない。旧版が反復3回を定めていた根拠の表は、**検証スクリプトが `pf` を 5.0 でクリップした状態**で測ったものだった（要件 6.8.5 / `verification/RESULTS.md`）。

**チーム目標も制約を満たしていなければならない。** 各項目を独立に生成すると約2%の確率で実行不能な目標（`FT成功数 > FT試投数`）が生まれ、この状態では整合化は原理的に成立しない。TeamRates が「試投数 + 成功率」を出すことで構造的に保証する（3.2）。

**さらに、TeamRates の出力をそのままチーム目標にしない。** TeamRates と Margin / Total は別モデルであり、TeamRates から導出した得点が予想スコアと一致する保証がない。そのまま選手側へ渡すと「選手の合計＝チーム目標」は満たされても「チーム目標＝画面に出る予想スコア」が崩れ、矛盾の位置が一段ずれるだけになる。**予想スコアを正とし、チームの成功率3項目を共通のロジットシフトで寄せる前段を置く**（要件 6.8.5 前段、詳細設計 2.4 `reconcile_team_targets()`）。試投数は動かさない。シフト量は1変数で単調なため `brentq` で一意に解け、反復は不要である。到達不能なら `InfeasibleTargetError` を投げ、当該試合の個人スタッツを破棄する。

**検証方式**: シーズン単位の walk-forward。各 fold で `train = seasons[:i-1]` / `valid（early stopping用） = seasons[i-1]` / `test = seasons[i]` とし、test に一切触れない。ランダムシャッフル分割は禁止。fold 数には上限を設ける（直近5シーズンのみ評価）。設けないとシーズンが増えるたびに学習時間が単調増加する。

**最終モデル**: 各 fold の `best_iteration` の中央値を `num_boost_round` に固定し、early stopping なしで全データを学習する。

**再現性**: `seed` / `bagging_seed` / `feature_fraction_seed` / `deterministic` を固定し、`model_versions.params` に記録する。固定しないと Brier が ±0.003 ぶれ、採用判定が乱数に支配される。

**モデルの保管**: LightGBM の `save_model()` はテキスト形式で数百KB〜数MBに収まるため、**`model_versions.artifact_text` として D1 に格納する**。GitHub Actions の artifact は90日で失効し、別ワークフローからの取得にも run-id 解決が必要なため、日次推論の依存先として成立しない。

**ただし D1 の1行上限は 2,000,000 バイトであり、artifact は常にその内側とは限らない。** テキストモデル書式からの推定は以下のとおり。

| `num_leaves` | 木の本数 | 推定サイズ | 2MB 上限に対して |
|---|---|---|---|
| **7（設計値）** | 300〜800 | **0.27〜0.70 MB** | 13〜35% |
| 7 | 2,000 | 1.75 MB | 88%（危険域） |
| 15 | 1,500 | 2.56 MB | **128%（超過）** |

したがって次を設計に組み込む。

- **登録時に 1.5MB 上限チェックを行い、超えたら登録を拒否して現行モデルを継続使用する**（受け入れ基準 A-18）
- `num_boost_round` に上限（1,200）を設ける。early stopping が効かずに上限まで回るケースを防ぐ
- `num_leaves` を 7 から増やす変更は、artifact サイズの再測定とセットでのみ許可する
- 実サイズは **測定済**（P0-12。2026-10-05。下記）

上限に当たった場合の退避手段は gzip + base64（テキストモデルは圧縮率が高く 1/5 程度になる）。**P0-12 を測った結果、不要である**（2026-10-05。最大は MARGIN の 93,901バイトで上限の 6.0%。`verification/RESULTS.md`）。**上限の判定自体は外さない** — `num_leaves` を増やす変更や `num_boost_round` が上限まで回る事態では桁が変わる。

#### 根拠の寄与を出すために `means` を artifact に持つ

勝敗モデルがロジスティック回帰になったため、寄与は
`係数_i × (特徴量_i − 学習データの平均_i)` で**厳密に**出る（要件 6.9）。
`base_value`（= `切片 + Σ(係数 × 平均)`）と各列の寄与は、どちらも
**学習データの平均**を要する。

**平均は推論時に作り直せない。** 学習行列は全期間の特徴量生成を要し（6,270試合で
数分）、日次推論がそれを毎回やり直す構成にはできない。したがって係数・切片と
並べて `artifact_text` に持ち、**書式の版を 2 に上げた**（詳細設計 1.6 / 2.7.1）。

**重みなしの列平均を使う。** 時間減衰 λ は探索の対象であり（詳細設計 2.5 / 4.7）、
重み付き平均にすると **λ を変えるたびに `base_value` の意味が動く**。重みなしの
列平均は学習行列についての事実であり、λ に依らない。

### 2.4 API サブシステム（Workers / TypeScript）

```
api/
├── src/
│   ├── index.ts
│   ├── routes/
│   │   ├── public/    games / teams / accuracy / health
│   │   └── internal/  書き込み系（Bearer + tipoff ガード）
│   ├── repositories/  D1 クエリ（必ず prepare().bind()）
│   ├── schemas/       Zod（型だけでなく値域も定義）
│   └── middleware/    認証・キャッシュ・CORS・レート制限
└── wrangler.toml
```

**役割**: 書き込みの関門と、静的JSONで賄えない動的クエリの配信、そして**バッチが必要とする運用上の読み取り**。今日の予測は Pages の静的アセットが担うため、Workers を通らない。

**内部エンドポイントには GET も置く。** バッチは入力データとして D1 を読まないが（1.2）、運用上どうしても D1 の現在値が要る場面がある。これらを Workers の `/internal/*` に集約し、D1 REST API の直叩きを作らない方針を保つ。

| 用途 | エンドポイント |
|---|---|
| **マスタの投入（`seasons` / `clubs` / `club_source_ids`）** | **`POST /internal/masters`** |
| backfill の再開判定（取得済み試合ID） | `GET /internal/games/ingested` |
| 結果照合の対象取得（確定済みで未評価の予測） | `GET /internal/predictions/pending` |
| 日次推論が使うモデル一式の取得 | `GET /internal/models/active` |
| 採用判定に使う現行モデルの評価値 | `GET /internal/metrics/active` |
| **座標を解決する会場の一覧** | **`GET /internal/venues`** |
| **登録選手一覧の投入（`players` / `player_seasons`）** | **`POST /internal/rosters`** |
| 学習済みモデルの登録 | `POST /internal/models` |

いずれも Bearer 必須で、返却行数は数行〜数百行に収まる。**特徴量・学習・推論の入力データをここから取らない。**

**書き込みの関門として必ず行うこと**

1. Bearer トークンの定数時間比較
2. Zod による型と値域の検証
3. **`tipoff_at <= now` の試合への予測書き込みを 409 で拒否**
4. `is_final = 1` の行を UPDATE / DELETE しない（DB制約でも二重化）
5. 非活性化と挿入を単一の `batch()` にまとめる（D1 にはリクエストを跨ぐトランザクションがない）

**キャッシュ**: エッジとブラウザで TTL を分離する（`s-maxage` と `max-age`）。`max-age` を長く取るとブラウザキャッシュを消せず、パージしても届かない。Workers の Cache API はコロ単位で、`*.pages.dev` ではゾーンパージも使えないため、**「パージする」という到達不能な手段に依存しない設計にする**。キャッシュキーにデータ世代（最終取り込み時刻）を含めれば、新しい世代が出た時点で別キーになり、パージ自体が不要になる。

**保護**: CORS はブラウザ内の制限でありサーバからのアクセスを防げない。レート制限の代替にしない。Cloudflare WAF のレートリミットルール（無料枠1ルール、独自ドメインが前提）を `/api/v1/*` に設定する。

ISR を使わない。`generateStaticParams` は**直近5シーズンの範囲内の日付・試合のみ**を生成し、範囲外は `notFound()` で即座に404にする。日付が自由入力のままだと URL 空間が無限になり、クローラの総当たりで無料枠が枯渇する。

| 直近5シーズン（旧版） | 約5,046 | 約25,200 | **126%（超過）** |

## 3. データモデル設計

### 3.1 テーブル分類

| 分類 | テーブル | 性質 |
|---|---|---|
| マスタ（恒久） | `clubs` `players` `venues` `seasons` | 不変の識別子 |
| マスタ（断面） | `club_seasons` `player_seasons` | 年度で変わる属性 |
| 名寄せ | `club_source_ids` `venue_source_keys` | 公式サイトIDとの対応 |
| ファクト | `games` `team_games` `team_game_stats` `player_game_stats` `game_entries` | 試合ごとに増える |
| 派生 | `team_ratings` `venue_revisions` | バッチが生成。全期間を再計算して洗い替える |
| 予測 | `predictions` `player_predictions` `prediction_reasons` | 予測の記録 |
| 評価 | `model_versions` `prediction_results` `accuracy_summary` | 精度の記録 |
| **集計** | **`player_stat_summary` `team_stat_summary`** | **実績の集計。バッチが日次で upsert する（下記）** |
| 運用 | `ingestion_logs` | ジョブ実行履歴 |

### 3.2 重要な設計判断

#### 恒久エンティティと断面の分離

**時間で変化するもの（クラブの名称・リーグ・本拠地、選手の所属、会場名・収容人数）を単一行の属性として持たない。**

- `clubs`（恒久）/ `club_seasons`（年度断面）/ `club_source_ids`（公式IDの名寄せ）
- `players`（恒久）/ `player_seasons`（年度断面）
- `venues`（恒久）/ `venue_revisions`（改称・収容人数変更の履歴）

旧版の `teams.legacy_ids`（JSON配列）方式は成立しない。JSON列は SQL で JOIN できず、チーム別集計・Elo・勝率のすべてがインデックスの効かない全展開を通る。また旧IDのまま保存すると `team_ratings.team_id` が分断され、**旧B1の Elo を新リーグへ引き継げず、コールドスタート対策が実装不能になる**。

取り込み時に `club_source_ids` で `club_id` に解決してから保存する。旧IDのまま保存しない。

#### チーム視点の試合行

`team_games`（`team_id` / `opponent_id` / `is_home` / `result` / `margin`）を持つ。`games` 単体だと「そのチームが出場した試合」は `home_team_id = ? OR away_team_id = ?` になり、OR の両辺にインデックスがないと全件スキャンになる。日程系の特徴量はほぼすべてこの経路を通るため、影響が大きい。

#### 予測の世代管理

`predictions` は**追記のみ**。再推論では旧行を `is_active = 0` にし、新しい行を追加する。

- `UNIQUE (game_id, model_version, revision)` — `revision` は世代通番
- `is_active = 1` の単一性は部分ユニークインデックスで担保する
- `is_final = 1` の行は更新・削除を DB 制約で禁止する

旧版の `UNIQUE (game_id, model_version, as_of)` は成立しない。`as_of` を `tipoff_at` 固定にすると、1日3回の再推論がすべて同一キーに衝突し、置換が起きて世代管理が空振りする。**「後から予測を書き換えられない」という主張が制約自身によって否定される。**

#### `as_of` と `data_as_of` の分離

| 列 | 意味 |
|---|---|
| `as_of` | 特徴量が参照してよい情報の上限時刻（= その試合の `tipoff_at`） |
| `data_as_of` | 推論実行時点で DB に入っていた最新試合の終了時刻 |

本番の日次推論は最大7日前の情報で予測するが、バックテストでは全試合が揃っているため開始直前の情報が使える。`data_as_of` を記録しないと、この差（検証スコアの体系的な過大評価）を後から検証できない。

#### 大会区分を列として持つ

`games` と `team_games` に `competition`（`REGULAR` / `PLAYOFF`）を持つ。取り込み対象はこの2区分のみで、オールスターゲーム・プレシーズン・入替戦は DB に入れない（要件 5.3）。

**`team_games` にも持たせる。** この表は `games` への JOIN を消すために作ったものであり、勝率・得失点差・連戦の特徴量はここだけを読む。`games` 側にしか持たないと、区分で絞るたびに JOIN が復活して表の存在理由が失われる。

**取り込み時の絞り込みだけで済ませない。** 区分を列に残さないと `REGULAR` と `PLAYOFF` を区別できず、特徴量 #17（順位・プレーオフ争いの状況）が算出できない。後から分離するには10日規模の backfill をやり直すことになる。

なお v1 の特徴量は**両区分をまとめて集計する**（詳細設計 2.1 規約7）。プレーオフを除外すると、その期間だけ当季勝率が止まったまま Elo だけが動く不連続が生じる。列は「後から絞れる状態を残す」ためにある。

#### `club_seasons` は試合データから作る

公式サイトに年度別のクラブ一覧ページは存在せず、過去シーズンの正式名称をマスタ系ページから取る経路がない。一方でボックススコアの `TeamNameJ` は**その試合の時点の名称**である（`703` は 2016-17 で `栃木ブレックス`、現在は宇都宮ブレックス）。

したがって `seed_master`（工程2）が投入するのは **`seasons` / `clubs` / `club_source_ids` のみ**とし、年度断面である `club_seasons` は backfill（工程6）が試合データから構築する。`name` / `short_name` はともに NOT NULL であり、試合データが入る前には埋められない。

#### マスタの書き込み口と、手で決める値

D1 への書き込みは Workers 経由に一本化されているため、マスタにも口が必要になる。**`POST /internal/masters` を1本置く**（詳細設計 3.4）。**テーブル名を引数に取る汎用エンドポイントにはしない** — 「任意のテーブルへ書ける口」を作ると、Zod 検証と `is_final` 保護という関門の意味が失われる。名前付きの配列で受け、配列ごとに Zod スキーマを持つ。71行すべてが1リクエスト（5文）に収まる。

**公式サイトから取れない値が2つある。**

| 列 | 扱い |
|---|---|
| `clubs.slug` | **手で決めて CSV に持ち、改称でも変えない。** `clubs` は恒久エンティティで、slug は `/teams/[slug]` の識別子である。英語名からの機械導出は、2016-17 の試合で `TeamNameE` が空だった実例があり全クラブで取れる保証がなく、改称のたびに URL が変わる。表示名は `club_seasons.name` が持つ |
| `seasons.start_date` / `end_date` | **当季の9月1日から翌年6月30日を CSV に固定する。** 範囲は上位集合でよく、**狭いと実在する試合日が404になる**。日程一覧から試合日の最小・最大を導出する旧方式は、2016-17〜2018-19 でチャンピオンシップの行を取りこぼし、実際に20日ぶんが範囲外だった。公式の年間スケジュールページは当季のみでガント描画のため出典にならない。試合投入後に求める経路は `games.season_id` の FK で循環する |

どちらも会場の座標（下記）と同じ「1回だけ確定して CSV に固定し、実行時には取得しない」という扱いにする。

#### 会場マスタも試合データから作る

`venues.id` には公式の会場ID（`StadiumCD`）を使う。**会場に公式IDがないという v1.8 までの前提は誤りだった**（Phase 0 で確認）。独自採番も会場名による名寄せも行わず、`venue_source_keys` は `club_source_ids` と同じ「公式ID → 内部ID」の対応表として持つ。

**会場の集合は事前に列挙できない。** クラブは代替会場を多く使い、毎年変わる。したがって `club_seasons` と同じく、会場行は backfill が試合データから作る（未知の `StadiumCD` を見たら `venues` に登録してから試合を入れる）。`seed_master` が投入するのは `seasons` / `clubs` / `club_source_ids` だけになる。

**公式サイトに収容人数がない。** 座標もない。座標は `/arena_detail/` の住所を国土地理院でジオコーディングして**1回だけ解決し CSV に固定する**（実行時に外部サービスへ依存しない）。収容人数は**手入力**で、2026-27 の26クラブのメイン会場から埋め、代替会場は NULL のまま進める。NULL は設計が既に許容している（`spectator_restricted` は NULL となり通常のホームアドバンテージを使うが、**観客制限期間は期間指定で強制的に 1** なのでコロナ期には影響しない）。

**入場者数の最大値を収容人数とみなす自動化を行わない。** 未来の試合から値を作ることになりデータリークの禁止に触れ、観客制限期間では判定が循環する。

**当時の会場名は `games.venue_name_at_game` に事実として保存し、`venue_revisions` はそこからの派生にする。** `venues.name` は初出の名称で固定するため（過去試合の会場表示が遡って変わらないようにするため）、試合行に当時の名称を残さないと**名称履歴を作る入力が取り込みの瞬間にしか存在せず、後から再構築できない**。列を1つ足すことで `venue_revisions` は `team_ratings` と同じ「全期間を再計算して洗い替える派生テーブル」になり、取り込み順序に依存しなくなる（詳細設計 1.2 / 4.9）。

#### 日程変更と結果訂正

`games` の主キーは公式サイトの試合IDとする。自然キー `(season_id, game_date, home_team_id, away_team_id)` を upsert キーにすると、**延期で `game_date` が変わった瞬間に別レコードとして挿入され、旧行が `SCHEDULED` のまま残り続ける**。

- `status` に `POSTPONED` を追加する（中止と延期は予測の扱いが異なる）
- `rescheduled_to` で延期先を指す
- `result_revision` を持ち、スコア訂正時に `prediction_results` の再評価をトリガする
- **上書きされうるファクトテーブル**（`games` / `team_game_stats` / `player_game_stats`）に `updated_at` を持つ（`fetched_at` は「取得時刻」であって「値が変わった時刻」ではない）

`team_games` と `game_entries` は `updated_at` を持たない。**持たせない理由を明示しておく。**

| テーブル | 扱い |
|---|---|
| `team_games` | `games` からの派生であり、独立に更新されない。変更時刻は元の `games.updated_at` で追える |
| `game_entries` | 取得のたびに当該試合の全行を DELETE → INSERT で洗い替える（4.4）。行が「更新される」ことがなく、`fetched_at` が実質の更新時刻になる |

派生テーブルと洗い替えテーブルに `updated_at` を足すと、**実際には更新されていない行の時刻だけが毎回動き**、「値が変わった時刻」という列の意味が失われる。

#### 集計層

`accuracy_summary` を日次で洗い替える。`/api/v1/accuracy` は overall / bySeason / byModel / calibration / byProvisional の5系統を返すが、`prediction_results` に `season_id` と予測確率がないと毎回3テーブルの全件走査になる。日次バッチが既に走っているのだから、そこで畳んでおく。

**主キーに NULL を含めない。** `model_version` はモデル横断の集計（`OVERALL` / `SEASON` / `BUCKET` / `PROVISIONAL`）では該当がないが、**NULL ではなく空文字 `''` を入れる**。SQLite は主キー列の NULL 重複を許すため、NULL 許容のままだと同一キーの行が何行でも入り、`ON CONFLICT` も衝突を検出しない。実測で、同じ `('OVERALL','all',NULL)` を2回 INSERT すると2行入り、`ON CONFLICT` 付きの3回目でさらに1行増えることを確認した。

洗い替え（DELETE → INSERT）を厳密に守れば事故は起きないが、**主キーが保護になっていない状態を残さない**。`model_versions.target TEXT NOT NULL DEFAULT ''` と同じ書き方に揃える。

#### 実績の集計も畳む（`player_stat_summary` / `team_stat_summary`。v1.57）

戦績・スタッツの閲覧（要件 F-10 / F-15）で**実行時に集計しない。**

1選手の通算を `player_game_stats` から引くと、索引 `idx_pgs_player` が効いても
**その選手の行（最大613行）＋ `games` への JOIN** を読む。1ページあたり約1,200行で、
**D1 の読取枠（500万行/日）は1日4,000ページ閲覧で尽きる**。要件 4.2 が
「主要導線を静的配信にして枠を守る」と定めた趣旨に反する。

畳んでおけば**1ページ2クエリ・数十行**になる。`accuracy_summary` と同じ型であり、
**新しい型を発明しない。**

**洗い替え（DELETE → INSERT）をしない。upsert だけで更新する。**

| | `accuracy_summary` | `player_stat_summary` |
|---|---:|---:|
| 行数 | 約20 | **約4,650** |
| 1リクエストの上限 | 400 | **160**（23列） |
| 必要なリクエスト数 | **1** | **約30** |

**1リクエストに収まらないものを「全件 DELETE してから INSERT」にはできない。**
分割すると後のリクエストの DELETE が前のリクエストで入れた行を消す — `/internal/ratings`
が「同じ `as_of_date` を2リクエストに分けない」と警戒しているのと同じ形である
（詳細設計 3.4）。

**upsert で足りる根拠は、入力が追記しかされないことである。** 取り込みは試合を
`id` で upsert し、**削除しない**（詳細設計 1.3）。したがって「集計すると行が1つ減る」
経路がなく、**古い行が取り残されることがない**。

**途中で失敗したときの挙動も upsert のほうが良い。** 書き換えられなかったキーには
**前回の値が残る**（消えてから入れ直す方式では、失敗した範囲が空になる）。
`meta.lastSuccessAt` を引き継ぐのと同じ考え方である（9章 U-09）。

**選手の季の行はクラブ別に持つ。** 主キーは `(player_id, scope, scope_key, club_id)`
で、`CAREER` の行は `club_id = ''` とする（上の「主キーに NULL を含めない」と同じ作法）。
理由は2つある。

1. **季中の移籍が2行で出る。** 1行に畳むと「どのクラブでの成績か」が消える
2. **クラブページの選手一覧がこの表の1クエリで引ける。**
   `WHERE scope = 'SEASON' AND scope_key = ? AND club_id = ?` で約16行

**チームは母数を2つ持つ。** `games`（`team_games` 由来。勝敗と得点の母数）と
`stat_games`（`team_game_stats` 由来。ボックススコアの母数）である。**取り込みが
スタッツまで届いていない試合が実在する**ため（詳細設計 4.8 の再開判定がこれを見ている）、
1つに畳むと**母数が嘘になる**。要件 8.3 は母数の併記を求めており、嘘の母数を併記しない。

**`plus_minus` を集計しない。** 旧年度のレスポンスは `PLUSMINUS` のキーを持たず
NULL になる（詳細設計 4.4）。合計すると**欠けた試合が黙って無視される**。
要件 6.8.3 も「チーム得点差 × 出場時間シェア以上の情報を持たない」と述べている。

#### チーム目標値にも恒等式を課す

`predictions` はチームレベルの目標値（試投数・成功率・リバウンド等）を保持するが、**これらは個別に保存できる値ではなく、相互に制約を満たさなければならない**。

| 制約 | 内容 |
|---|---|
| 成功数 ≤ 試投数 | 試投数と成功率（0〜1）の積で持てば構造的に成立する |
| `得点 = 2FGM×2 + 3FGM×3 + FTM` | 得点を独立に保存せず、恒等式で導出する |
| `FGA = 2FGA + 3FGA` | FG を独立に保存しない |

**この制約を課さないと整合化が原理的に成立しない。** 各項目を独立に生成すると約2%の確率で `FT成功数 > FT試投数` のような実行不能な目標が生まれ、どんなアルゴリズムでもその目標には到達できない。DB の CHECK 制約と `test_team_targets_are_feasible`（A-16）の両方で担保する。

#### 子テーブルの凍結は例外を設けない

`is_final = 1` による凍結は `predictions` だけでなく、**`player_predictions` と `prediction_reasons` にも同じ強さで適用する**。

旧版は `predictions` にのみトリガを置いていたが、それでは「勝率は変えられないが、個人スタッツと根拠は後から書き換えられる」状態になる。根拠は「なぜその予測になったか」の記録であり、試合後に差し替えられるなら予測の不変性という主張そのものが成立しない。

- 親の `is_final = 1` に紐づく子行の UPDATE / DELETE をトリガで禁止する
- **例外は設けない**。表示上の誤り（ラベルの誤字など）が見つかった場合も、過去の行は修正せず、以後の生成ロジックのみを直す
- 再推論による追加は、親が `is_final = 0` の場合に限り、親の非活性化と同一 `batch()` の中でのみ許される

**freeze は親子をまとめて単一の `batch()` で行う。** `is_final` 列を持つのは `predictions` と `player_predictions` の2つで、残りの子テーブル（`prediction_reasons` / `prediction_team_targets` / `prediction_model_bundle`）は列を持たない。

**4つの子テーブルすべてに親参照トリガを置く。** `player_predictions` は自身の `is_final` に加えて親の確定でも守る。自テーブルの列だけで守ると、`finalize` が子への UPDATE を取りこぼした場合に「親は確定済みなのに子は書き換えられる」状態が残り、**トリガが関門として機能しない**。

`batch()` 内の文の順序は **子（`player_predictions`）→ 親（`predictions`）** に固定する。親を先に確定させると子の `0 → 1` が親参照トリガに拒否され、**freeze 自体が失敗する**。順序は任意ではなく必須である。

## 4. 処理設計

### 4.1 バッチジョブ一覧

| ジョブ | スケジュール | 処理 |
|---|---|---|
| `daily_ingest` | 21:00 UTC（06:00 JST） | 前日結果取得、照合、**スナップショット更新**、Elo再計算、推論、静的JSON書き出し |
| `gameday_update` | **固定 cron 3スロット**（02:00 / 04:00 / 07:00 UTC = 11:00 / 13:00 / 16:00 JST）。各スロットで対象を絞り込む | エントリー取得、再推論、静的JSON更新 |
| `finalize` | 毎時（Workers Cron Trigger） | 開始時刻を過ぎた予測の freeze（親子を単一 `batch()` で凍結する） |
| `monthly_train` | 毎月1日 19:00 UTC（= JST 2日04:00） | 全データ再学習、同一ウィンドウで検証（タイムアウト120分。選手モデルは16本あり fold 数を3に制限） |
| `parser_canary` | 日次 | 終了済み試合詳細1枚のみ取得してパース（埋め込みJSONの取り出しまで）。失敗で Actions を fail |
| `backfill` | 手動 | 過去シーズンの一括取得（再開可能） |
| **`rebuild_derived`** | 手動 | 派生テーブル（`team_ratings` / `venue_revisions`）を全期間洗い替えて D1 へ書き戻す。外部アクセスなし |
| **`resolve_venue_geo`** | 手動 | 会場の座標を1回だけ解決して CSV に固定し、`mode=load` で D1 へ送る（詳細設計 4.10） |
| **`ingest_rosters`** | 手動 | 登録選手一覧を取り込む（`players` / `player_seasons`）。クラブ×シーズンの実在する238組を辿る。**1回だけ**（詳細設計 4.13） |

**`gameday_update` は「固定 cron ＋ 対象の絞り込み」で実現する。** 旧版の 17:00 JST 単発では、土日2連戦で常態化している日曜14:05開始の試合が**すでに終了した後に再推論される**。

ただし GitHub Actions の cron は**動的に起動時刻を変えられない**（`schedule` は静的な記述であり、ワークフロー自身が次回実行時刻を指定する手段がない）。旧版の「当日の最小 `tipoff_at` を読んで N 時間前に動的起動する」という記述は実現不能だった。

代わりに次の構成をとる。

1. **固定 cron で1日3スロット起動する**（11:00 / 13:00 / 16:00 JST）。B.LEAGUE の開始時刻は概ね 14:05 / 15:05 / 17:05 / 19:05 に集中するため、このスロットで大半の試合の「2〜3時間前」を捕捉できる
2. 各スロットの先頭で当日の試合を読み、**対象を `tipoff_at > now + 30分` の試合に限定する**。すでに開始した試合・開始直前の試合は処理しない
3. 当日に試合がなければ、スクレイピングを行わずに即座に終了する（外部アクセスを発生させない）
4. cron 遅延で `tipoff_at` を過ぎていた場合、Workers 側の tipoff ガードが 409 を返す。**遅延しても壊れない**

スロット数を増やすほど捕捉率は上がるが、スクレイピング回数とワークフロー実行数が増える。3スロットに抑えるのは、要件5.2 の「取得は必要最小限のページに限る」「1日あたりの総リクエスト数に上限（3,000）を設ける」を満たしたうえで、開始時刻の分布を実用上カバーできる最小のスロット数だからである。

**`finalize` を `daily_ingest` から切り出す。** 旧版では翌朝06:00の `daily_ingest` 内で実行され、試合開始から約11時間 freeze されない状態が毎日生じていた。しかも外部スクレイピングの後段にあるため、429 で中止されると freeze ごと巻き添えになる。freeze は外部アクセスを必要としない純粋な D1 操作なので、独立させる。

**cron は UTC で記述する。** JST から9時間引く。日付をまたぐ場合は曜日指定もずらす。GitHub Actions の cron は数十分〜数時間遅延しうるため、遅延しても壊れない設計（tipoff ガード）を前提とする。

### 4.2 日次取り込みの流れ

```
1. robots.txt / 利用規約のハッシュ照合 → 変更があれば中止
2. 前日の試合一覧（大会区分で絞る）とボックススコアを取得（3秒間隔・値域検証）
3. games / team_games / team_game_stats / player_game_stats を upsert
   → 同一データから batch/snapshot/*.parquet を書き出し MANIFEST を更新
3b. **当月（7日窓が月をまたぐなら翌月も）の日程を取得し、未実施の試合を upsert する**
   → ステップ8 が回す「向こう7日間の試合」はここで DB に入る
4. スコア訂正を検出したら result_revision を進め、再評価キューに載せる
5. 確定予測と実績を照合 → prediction_results 登録（中止・延期は除外）
6. accuracy_summary を洗い替え
6b. **実績の集計（`player_stat_summary` / `team_stat_summary`）を upsert する**
7. Elo・各種レーティングを再計算（対象期間を洗い替え）
   → `team_ratings.parquet` を書き出し、`/internal/ratings` で D1 にも送り、MANIFEST を再生成
8. 向こう7日間の試合について特徴量を生成（**スナップショットを参照。D1 は読まない**）
9. 有効なモデル一式を取得（`GET /internal/models/active`）し推論
   → チーム目標を予想スコアへ整合化 → 選手予測を整合化
   → predictions / prediction_team_targets / player_predictions を追記（旧行を is_active=0）
10. SHAP をグループ集約 → prediction_reasons 登録
11. 静的JSON（today.json ほか）を書き出し、リポジトリへコミットする
11b. **コミットが行われた回だけ `next build` して Pages へ配る**（`CF_PAGES_TOKEN`）
   → 配らないと本番は最後に配ったものを返し続け、毎日更新遅延バナーが出る
12. ingestion_logs に結果を記録
```

**外部アクセスの失敗が内部処理を巻き添えにしないこと。** 429 で中止するのはステップ2のみで、ステップ5〜11b（照合・Elo・推論・書き出し・配り直し）は実行して `PARTIAL` で終わる。旧版は try が処理全体を覆っていたため、前日結果が取れないだけでその日の予測更新が止まっていた。

ステップ9でチーム目標が到達不能（`InfeasibleTargetError`）だった試合は、**チーム予測のみを保存して個人スタッツを破棄し、次の試合へ進む**。ジョブ全体は止めない。

各ステップは冪等とする。

**ステップ3b を後から足した（v1.45）。** 旧版はステップ2で「前日の試合」を取得し、
ステップ8で「向こう7日間の試合について特徴量を生成」と書いていたが、
**その7日間の試合をいつ DB に入れるのかが書かれていなかった**。backfill は
`FINISHED` 以外を書き込まないため（詳細設計 4.8）、**未実施の試合は1件も入っていない**
（実測で 0件）。これではステップ8 が回す対象がない。

**日程は月単位で取れる。** 取得URLは `mon` パラメータを持ち（`batch/scraper/schedule.py`）、
当月だけを辿れる。シーズン全体（29ページ）を毎日取り直す必要はない — 要件 5.2 の
「取得は必要最小限のページに限る」を満たす。

**未実施の試合には会場IDが付かない。** 日程ページは会場名しか持たず、公式の
`StadiumCD` はボックススコア（試合後）にしかない。`games.venue_id` は NULL のまま
upsert し、試合後にステップ3が埋める。**この帰結として検証区分 #15 を落とした**
（詳細設計 2.2）。

### 4.3 エラー処理方針

| 事象 | 対応 |
|---|---|
| 個別試合の取得失敗（**非200・通信失敗**） | スキップしてログに記録。ジョブは継続 |
| **D1 への書き込み失敗**（書き込み枠の枯渇ほか） | **その場でジョブを中止し、`PARTIAL` で記録を残す。** 継続しない（枠が尽きた状態では残りも全部失敗する）。取り込んだ分は残り、翌日は残りから再開する |
| 値域検証エラー | 当該試合をスキップ。ログに記録 |
| パース失敗（構造変更の疑い） | 連続3件でジョブ中止。`PARTIAL` で記録し **exit 1**（通知に乗せる） |
| **取得失敗とパース失敗を合わせて連続3件** | 同じ counter で数え、ジョブ中止。非200が続くのは遮断の疑いであり、叩き続けるのは絶対ルール6に反する |
| 429 / 503 | スクレイピング区間のみ中止。内部処理は継続 |
| `robots.txt` 変更検知 | ジョブ中止。人間の確認を待つ |
| D1 書き込み失敗 | 3回まで再試行。失敗時は異常終了 |
| 推論失敗 | 前回の静的JSONを維持。画面に更新遅延を表示 |
| 学習の検証基準未達 | 新モデルを有効化せず、現行を継続使用 |

`PARTIAL` を exit 0 で終えると、GitHub Actions の失敗通知に乗らず**誰も気づかないまま数日放置される**。

**1試合の取得失敗でジョブ全体を落とさない。** 公式サイトはたまに非200を返す
（2026-09-25 までに4回。値は不明だった）。backfill はこれを捕まえておらず、
300試合目で1回起きればその日の D1 書き込み枠ごと失われる状態だった。

**例外の「型名だけ」を出さない。** 自前の文言を持つ例外（`LoaderError` /
`ScraperError` / `ParseError` / `ValidationError`）は、設計上 URL・応答本文・
元の通信例外を含まない。型名だけを出すと原因の切り分けに本番の再実行が必要になり、
**同じ誤りを3箇所（内部API・個別試合・日程）で順に踏んだ**。非200のステータスは
数値1つであり、伏せる理由がない（絶対ルール4に触れない）。想定外の例外
（`Exception`）だけは型名のみとする。

### 4.4 冪等性

- 試合は公式試合IDを主キーとして upsert
- エントリー情報は取得ごとに全行を洗い替える（追加のみだと推定行が残り `暫定` が解除されない）
- 予測は追記型。同一ジョブ run 内のリトライのみ置換を許し、ジョブを跨ぐ再推論は必ず追記する
- Elo は差分更新せず、対象期間を再計算して洗い替える。**`backfill` で過去データを追加した後は全期間の洗い替え（`--full`）を実行する**
- 原子性が必要な操作は単一 `batch()` にまとめる: (a) 予測の非活性化＋挿入、(b) `team_ratings` の期間 DELETE＋INSERT、(c) `model_versions` の切替
- `ingestion_logs` のみ冪等でない（意図的）

### 4.5 更新遅延の判定

`stale` は「**`status = 'SUCCESS'` の最新レコードの `finished_at` から24時間以上経過**」と定義する。

旧版の「最終取り込みから24時間」では、ジョブが毎日失敗しても最新レコードの時刻は毎日更新されるため、`stale = false` のまま古い予測が「正常」として表示され続けた。24時間監視をしない前提だからこそ、この自己申告が唯一の検知手段になる。

`PARTIAL` / `ABORTED` / `FAILED` が直近にあれば別バッジを出す。`gameday_update` は試合がある日のみを判定対象にする。

### 5.2 主要画面の構成

#### 今日の予測（`/`）

```
┌──────────────────────────────┐
│ <ブランド>         [テーマ]   │
├──────────────────────────────┤
│ [更新遅延バナー（該当時のみ）] │
├──────────────────────────────┤
│ 今日の予測 | 結果 | 的中率    │
├──────────────────────────────┤
│ 9月22日 (火) の試合           │
│ ┌──────────────────────────┐ │
│ │ B.PREMIER 19:05    [暫定] │ │
│ │ ホームA   68% ── 32% アウェイA │
│ │ ████████████░░░░░         │ │
│ │ 予想スコア  84 – 78        │ │
│ │ 今季的中率 68.2%（312試合） │ │
│ └──────────────────────────┘ │
│ ┌ 圧縮カード ───────────────┐│
│ │ ホームB 55% — 45% アウェイB ││  ← 両チーム分を必ず表示
│ │ ほぼ互角 ・ 17:05          ││
│ └───────────────────────────┘│
├──────────────────────────────┤
│ [フッター：免責・出典・about] │
└──────────────────────────────┘
```

圧縮カードでも両チームの勝率を表示する。片側だけだと誰の55%か判別できず、要件8.3に違反する。45〜55% は「ほぼ互角」と表現し、一方的な試合と見た目で区別する。

#### 試合詳細・試合前（`/games/[id]`）

1. 対戦と勝率（両チーム、大きく表示）
2. 予想スコア（整数）
3. 状態表示（暫定 / 序盤）と、その理由の一文
4. なぜこの予測になったか — 要因グループ別、有利な側を日本語で明示
5. 個人スタッツ予測 — 出場確率50%以上の選手。**段階開示**（初期は MIN / PTS / TR / AS、行をタップでフルボックススコアを展開）。誤差の目安は主要4項目に併記
6. 両チームの直近成績
7. 使用モデルのバージョンと、そのモデルの通算精度（母数つき）

#### 試合詳細・試合後

**このプロダクトで最も信頼が揺れる場面であり、専用の構成を持つ。**

1. 実際のスコアと勝敗
2. 予測との対比
3. この予測の位置づけ

文言例（的中時）: 「予測どおりでした（予想 84–78 / 実際 88–81・得点差の誤差 3点）」

文言例（外れた時）: 「この試合は予測を外しました。ホーム68%と予想しましたが、アウェイが勝ちました。**68%と予想した試合は、これまで42試合中29試合（69.0%）が的中しています。**」

外れを認めた上で、較正が取れていること自体を信頼の材料として示す。外れた試合に強い否定色を使わない。

#### 的中率（`/accuracy`）

一般向けから専門向けへ、この順で並べる。

1. 「312試合中 223試合を的中（71.4%）。『ホームが必ず勝つ』と予想した場合は 60.1% でした。」— ベースライン比較を最初に置く
2. **予想スコアの誤差**（v1.53。下記）: 「予想スコアは1チームあたり平均 8.8点ずれています。」
3. シーズン別の推移
4. 較正の言い換え（表）: 「70%くらいと予想した試合 88件 → 実際に勝ったのは 63.6%。予想よりやや勝てていません。」
5. 較正曲線（グラフ）— 軸は日本語。対角線に「この線に近いほど、数字どおりに当たっている」と注記
6. 暫定/確定の内訳: 「出場選手が未発表の段階で出した予測 68.0%（120試合）／確定後 73.0%（192試合）」
7. 詳しい指標（折りたたみ）— Brier。「0に近いほど良い指標です」を併記
8. **モデルバージョン別**（受け入れ基準 A-05。下記）

Brier をトップ画面に出さない。`.186` のような小数点前ゼロ省略は使わず `0.186` と書く。

#### 予想スコアの誤差を通算で出す（v1.53。運営者の判断）

**勝敗の的中率だけを出していた。** 得点の誤差は1試合ごとに記録・表示していたが
（`prediction_results.score_mae` → 試合詳細と結果画面の「得点差の誤差 3点」）、
**通算が出ていなかった** — `accuracy_summary` に列が無かったためである。

**`score_mae` 列を1つ足す**（詳細設計 1.6。マイグレーションは追記のみ）。

| 項目 | 扱い |
|---|---|
| 単位 | **1チームあたりの平均絶対誤差**（1試合は両チームの平均）。得点差の MAE と混同しない（要件 6.4） |
| 表記 | **小数第1位＋単位**（`8.8点`）。予想スコア自体は整数で出すが（要件 8.3）、**誤差は集計値であり整数では粗すぎる** |
| 母数 | **`n` と同じであることを集計側が保証する**（下記）。別の母数を持たない |
| 出す場所 | ベースライン比較の直後。シーズン別・モデル別の表にも同じ列が入る |

**ベースライン比較は置かない。** 勝敗には「ホームが必ず勝つ」という自明な比較相手が
あるが、得点にはない（「リーグ平均得点で予想した場合」は計算できるが、実績の平均得点を
集計側が持ち回る必要があり、列が増える）。**運営者が「列を1つ」を選んだ**（2026-10-05）。

**母数を2つ持たない。** `score_mae` は `VOID`（中止・延期）と予想スコア未保存の行で
NULL になりうるため、素朴に平均すると**表示の母数（`n`）と実際の母数が食い違う**。
`VOID` は `n` から既に除かれているが、予想スコア未保存は除かれていない。

したがって**集計側で「`n` の全行に予想スコアがあること」を確認し、欠けていたら
`score_mae` を NULL にして件数を報告する**（詳細設計 4.12）。
**欠けた行を黙って除いて平均しない** — 母数の違う数字が「312試合」の隣に並ぶ。

#### Log Loss は画面に出さない（**v1.55 で解決した**）

**旧版はここに「Brier / Log Loss」と書いていたが、`/accuracy` は Log Loss を
返せない。**

| 文書 | 記述 |
|---|---|
| 本節（旧版） | 詳しい指標に **Brier / Log Loss** を出す |
| 詳細設計 1.6 | `accuracy_summary` の列は `n` / `accuracy` / `brier` / `actual_rate` / `baseline_accuracy`。**logloss の列が無い** |
| 詳細設計 3.3 | `/accuracy` は **`accuracy_summary` を単一テーブルから読む**。応答の形にも logloss が無い |

**`model_versions.cv_logloss` を流用しない。** あれは**学習当時の評価ウィンドウ**で
測った値であり、画面に出る通算 Brier とは別の量である。並べて出すと
「同じ母集団の2指標」と読まれる（詳細設計 3.4 が `/internal/metrics/active` の
`cvBrier` を比較に使わないと定めているのと同じ理由）。

**`prediction_results` から導く案も採らない。** `home_win_prob` と
`actual_home_win` があるため計算はできるが、**`/accuracy` が単一テーブルを読む
設計を崩す**（3.3 は「`prediction_results` の全件走査をしない」と定めている）。

**画面は Brier だけを出す。** 解決は **(b) 本節から Log Loss を落とす**とした
（v1.55。運営者の委任により決めた。2026-10-05）。

**根拠は上位文書である。** 要件 6.4 の指標の表は Log Loss の用途を
**「学習時の目的関数」**と定めており、**表示指標として挙げていない**。
公開するのは Accuracy（表示専用）・Brier（主要な改善指標）・ECE（採用ゲート）で、
Log Loss は学習の内部にある。要件 F-07 と受け入れ基準 A-05 も Log Loss を求めて
いない。**この節だけが表示を要求していた** — 上位文書が正しく、下位文書を直す
（CLAUDE.md「文書の優先順位と矛盾時の扱い」）。

**(a)（列を足す）を採らない理由は費用ではなく重複である。** 二値の結果に対する
Log Loss と Brier は**同じ予測の質をほぼ同じ向きに測る**。折りたたみの中に2つ
並べても、読者が得るものは「0に近いほど良い指標」が1つ増えるだけで、**判断が
変わらない**。一方で払うのは、マイグレーション1本・`evaluate` の改訂・
`score_mae` と同じ母数の扱い（4.12）である。

**学習側では引き続き使う。** `model_versions.cv_logloss` は残し、LightGBM の
目的関数も変えない（要件 6.4）。**落とすのは画面だけである。**

#### 単一のアクセント色をやめた理由

旧 `--accent`（緑）は「1つの強調色」を前提にした設計で、**ホームとアウェイという対等な2つの側を
同時に示せない**。片側だけを塗れば、塗られた側が「良い」と読まれる。藍と弁柄の2色に分けたのは、
対等だが混同しない色相の組で、**どちらも「良い／悪い」を含意しない**ためである
（赤＝危険 / 緑＝安全 の連想は、勝敗予測では誤った価値判断になる）。

**方向は色だけで示さない。** バーの向き・H/A のラベル・数値の3つが併存する（要件 8.6）。

#### 罫線を3段に分け、「意味を持つ線」だけに 3:1 を課す

旧版は `--border` 1本きりだった。罫線が主役の版面では、同じ太さ・同じ濃さの線が並ぶと格子が
騒がしくなり、**どれが意味のある線か分からなくなる**。

| トークン | 意味 | 要求 |
|---|---|---|
| `--axis`（50%軸） | **意味を持つ**。互角かどうかの判定基準 | **3:1 以上** |
| `--rule` / `--rule-soft` | 装飾的な仕切り。同じ情報を余白と見出しが伝える | 課さない |

**`--axis` のコントラストは「地に対して」ではなく「帯に対して」測る。** 50%軸は必ず互角帯
（`--band`）の上を通るためである。制作時に `#8E8676` を置いたところ、紙には 3.31:1 あったが
**帯の上では 2.61:1** しかなく、意味を持つ線として不足していた（`#736B5A` に変更して 3.82:1）。
**目視では気づけない種類の誤りであり、CI の単体テストで防ぐ。**

#### `--text-4` を廃止した

旧版は `--text-3` を本文用、`--text-4` を非テキスト専用としていたが、**同じ「テキスト色」の
系列に非テキスト専用の値を混ぜる**構造そのものが混同の原因だった。新トークンでは
テキスト（`--ink` / `--ink-2` / `--ink-3`）と線（`--rule` / `--rule-soft` / `--axis`）を
別の系列に分けてある。

敗者側の確率には `--ink-2` を使う。勝敗の差は色の濃淡ではなく、**バーの向きと数値**で伝える。

**コントラスト検証を CI のトークン単体テストに組み込む。** 目視のスナップショット確認では
必ず見落とす。

**`--axis` は使われる場所ごとの背景に対して検査する。** 1つのトークンが2か所で
別の地の上を通るためで、両方を `GRAPHIC_PAIRS` に入れる。

| 使う場所 | 背景 | 実測（ライト / ダーク） |
|---|---|---|
| 勝率バーの50%軸 | **`--band`**（必ず互角帯の上を通る） | 3.82 / 3.63 |
| 較正グラフの対角線（`/accuracy`） | **`--paper`** | 4.84 / 5.07 |

旧版は「`--band` に対して検査する（地に対してではない）」と書いていた。帯の上の方が
厳しいという意図だったが、**較正グラフの対角線は帯の上を通らない**ため、片方だけでは
検査が当たらない場所が残る。**どちらが厳しいかではなく、使う場所をすべて挙げる。**

### 6.2 タイポグラフィ

| 用途 | サイズ | ウェイト | 書体 |
|---|---|---|---|
| 勝率（詳細の主役） | 38px | 600 | **等幅** |
| 予想スコア（詳細） | 28px | 600 | **等幅** |
| 画面の見出し | 19-21px | 600 | **明朝** |
| セクション見出し | 16px | 600 | **明朝** |
| 本文 | 12.5-13px | 400 | サンセリフ |
| 一覧の数値 | 12-13px | 400-600 | **等幅** |
| ラベル | 9.5-11px | 700 | サンセリフ、字間を広げる |

**書体を3系統に分ける。** 見出しのみ明朝、ラベルと本文はサンセリフ、**数値はすべて等幅**。

```css
--f-serif:"Hiragino Mincho ProN","Yu Mincho",YuMincho,"Noto Serif JP",serif;
--f-sans:-apple-system,BlinkMacSystemFont,"Hiragino Sans","Noto Sans JP","Yu Gothic UI",system-ui,sans-serif;
--f-mono:ui-monospace,SFMono-Regular,"SF Mono",Menlo,Consolas,"Liberation Mono",monospace;
```

**Web フォントを一切読み込まない（旧版から変更）。** 旧版は「数字用の1ウェイトのみ（60KB以内）」を
許していたが、数値を等幅システムフォントで組むことにしたため**不要になった**。要件 4.2 の
総転送量 250KB と LCP 2.5秒に対する余裕がそのぶん増える。

**明朝はシステムフォント依存である。** Hiragino / Yu Mincho / Noto Serif JP のいずれも無い環境
（一部の Android）ではゴシックに落ちる。**落ちても情報は失われない**（明朝が担うのは見出しの
格であって、数値でもラベルでもない）ことを前提に採用する。

すべての数値に `font-variant-numeric: tabular-nums` を適用する。

### 6.3 レイアウト原則

- モバイルファースト。コンテンツ幅の上限は 440px（一覧）/ 560px（詳細）
- 左右 16px のガター。375px で横スクロールを発生させない
- **カードを積まない。** 1試合 = 1レコードの表（`<tbody>` に `<tr>` 2本、時刻・バー・状態を `rowspan`）
- **影を使わない。** 影は要素を浮かせて「1件ずつ」に見せる装置であり、一覧性を最優先する
  この方向性では目的と逆に働く
- 角丸は 2px まで（実質の直角）。囲いは 1px の罫線だけで作る
- **余白は列間ではなく「行グループ間の罫線」で作る**

#### 密度の下限はタップ対象が決めている

1試合の行は 44px + 第2行で、**これ以上は詰められない**（タップ対象 44×44px の制約）。
可読性ではなくタップ対象が密度の上限を決めている、というのが工程11a 以降で分かったことである。
空いた縦は第2行（アウェイ）に使い切る。

### 6.4 チャート

**ライブラリを使わずインライン SVG で実装する。** 表示するのはシーズン数十点と較正バケット5〜10点で、Recharts や Chart.js を入れると `/accuracy` だけで gzip 後100〜300KB 増える。デザイントークンによる配色統一とも相性がよい。

#### 図の中でも、線とテキストの系列を混ぜない

**SVG は `stroke` と `fill` で塗るため、6.1 の系列の区別が効いていないと気づきにくい。**
較正グラフ（`CalibrationChart`）は 2026-10-02 まで廃止済みのトークン
（`stroke-text-4` / `stroke-text-3` / `fill-accent` / `fill-text-3`）を使っており、
**Tailwind の橋渡しに無い名前のため軸線と対角線が1本も描かれず、点と目盛りが既定の
黒になっていた**。CI の走査は `text-` / `bg-` / `border-` だけを見ており、
**`stroke-` と `fill-` が対象外だった**。

| 図の要素 | トークン | 理由 |
|---|---|---|
| 判定基準の線（較正の対角線・勝率の50%軸） | **`--axis`** | **意味を持つ線。** 3:1 を課す |
| 枠の軸線・目盛りの線 | `--rule` | 装飾。同じ情報をラベルが伝えるため基準を課さない |
| データの点・マーク | **`--ink`** | 図の主役であり、主数値と同じ扱い |
| 目盛りのラベル・軸名 | `--ink-3` | テキストの系列から選ぶ |

**データの点に `--home` / `--away` を使わない。** あの2色は「ホーム側／アウェイ側」という
対等な2つの側を指す対であり、較正の点にその意味はない。片方を借りると**無い区別を
読ませる**ことになる。ホーム・アウェイを描く図（将来の対比グラフ）でのみ使う。

**判定基準の線と枠を同じ濃さで描かない。** どちらが比べる相手か分からなくなる。

**走査は `stroke-` と `fill-` を必ず含める**（`web/scripts/check-contrast.mjs`）。
走査があること自体では守られない — **当たっていない接頭辞があれば素通りする。**

### 7.2 CI

**push / PR で必ず実行する。** 最重要の `test_leakage.py` を人間の規律に任せると、3ヶ月で形骸化する。

| 対象 | 内容 |
|---|---|
| Python | `ruff` / `mypy` / `pytest batch/tests`（リークテストを含む） |
| api | `tsc --noEmit` / eslint / vitest（Zod契約、認証、キャッシュヘッダ） |
| web | `tsc --noEmit` / **`eslint .`（`next lint` は Next.js 16 で削除された）** / トークンのコントラスト検証 / `next build` / **`out/` のファイル数検査（18,000以下）** / **初期JS の予算検査（gzip 180KB以下。要件 4.2）** / **タブの現在地の検査**（`aria-current` が自分のページを指すこと） / **出典表記と版と著作権表示の検査**（確定文言・版・© が全ページに出ていること、禁じた表記がどこにも無いこと。要件 4.5.5 / F-12 / A-07）／ **版と © は `web/lib/version.ts` の定数から照合する**（検査に文字列を書き写すと、上げたときに2か所を直すことになる） / **戦績・スタッツの検査**（試合ごとの記録の一覧を出さないこと、母数と分数が併記されること。要件 A-19） |
| リポジトリ | fixtures に実サイト由来文字列がないことの検査（`scripts/check_fixtures.py`）/ ワークフローの不変条件（`permissions: contents: read`・`concurrency`・`timeout-minutes`・`next lint` の不在）/ **スナップショットと D1 ローカルの一致検査** |

**`next lint` を使わない。** Next.js 16 で削除されており、`next build` もリントを実行しなくなった。ESLint は CLI を直接呼ぶ（`eslint .`）。設定は Flat Config（`eslint.config.mjs`）とする。`next lint` を CI に書くとコマンドが存在せず失敗するか、将来の互換シムに依存することになる。**CI に `next lint` が現れないことをテストで固定する**（コメントでの言及は許す）。

**api / web のジョブは、該当ディレクトリができる前から CI に書いておく。** `detect` ジョブが `package.json` の有無を出力し、下流のジョブがそれで分岐する。ディレクトリができた時点で自動的に有効になるため、後から CI に足し忘れることがない。`hashFiles()` を job 単位の `if` に書く方法は使えない（checkout より前に評価され、ワークスペースが空で常に偽になる）。

`monthly_train` の先頭にもリークテストを置き、失敗したらモデル登録に到達させない。

**`parser_canary`** は日次で実サイトの終了済み試合詳細1枚のみを取得してパースし、必須項目が取れなければ Actions を fail させる。fixture はスナップショットであるため、定義上サイト構造の変更を検知できない。これが唯一の早期検知手段になる。

**カナリアは「埋め込みJSONが取り出せること」まで見る。** ボックススコアは HTML の表ではなく `<script>` 内の JSON で配信されるため（2.1）、HTML の構造だけを見ても壊れたことに気づけない。次の3つを検査する。

1. 本文から JSON が取り出せる
2. 対応表（詳細設計 4.4）の必須フィールドがすべて存在する
3. `PeriodCategory` に 18（試合通算）が含まれる

サイトが JSON 配信をやめて HTML の表に戻った場合も、1 で落ちて検知できる。

### 7.4 シークレット管理

| 名称 | 保管先 | 用途 |
|---|---|---|
| `INGEST_TOKEN` / `INGEST_TOKEN_NEXT` | GitHub Secrets + Workers Secret | 内部API認証（2キー方式） |
| `FINALIZE_TOKEN` | 同上 | freeze 専用（破壊的操作を分離） |
| `CF_API_TOKEN` | GitHub Secrets | マイグレーション専用。スコープは対象D1のEditのみ |
| `CF_API_TOKEN_RO` | **手元のみ**（GitHub Secrets にも CI にも置かない） | 障害調査で `wrangler d1 execute --remote` の SELECT を流すため。スコープは対象D1の Read のみ |
| **`CF_PAGES_TOKEN`** | **GitHub Secrets** | **Pages への配り直し専用。スコープは `Account → Cloudflare Pages → Edit` のみ**（2026-10-06 に追加）。`CF_API_TOKEN`（D1 Edit）では配れず、逆にこのトークンで D1 は触れない。**用途ごとにトークンを分ける**という本節の方針どおりである |

`D1_DATABASE_ID` は機密ではない（操作には API トークンが別途必要）ため `wrangler.toml` に直書きしてよい。環境変数注入は `d1_databases` の必須フィールドでは効かないため、旧版の「直書きしない」という制約は実現不能だった。

**トークンの無停止回転手順**

1. 新トークンを Workers Secret に `INGEST_TOKEN_NEXT` として追加
2. 認証は現行・次期のいずれかに一致すれば通す
3. GitHub Secrets を更新
4. 次のバッチ成功を確認
5. 旧トークンを削除

**例外オブジェクトをそのままログ・DBに入れない。** D1 REST API の URL にはアカウントIDとDB IDが含まれるため、`str(e)` を `ingestion_logs.error_message` に保存し `/api/v1/health` で公開すると、それらが公開APIから漏れる。例外は型名と自前の短いメッセージに限定し、`/health` は `error_message` を返さない。

### 7.5 無料枠の監視

| リソース | 無料枠 | 想定使用量 |
|---|---|---|
| Workers リクエスト | 10万per日 | 数百〜数千per日（主要導線が静的配信のため） |
| **Workers CPU** | **10ms per リクエスト** | 実測 1.34ms（500行の JSON パース＋検証）。Zod で3〜4ms 見込み |
| **Workers サブリクエスト** | **50 per リクエスト** | 0（D1 Binding はサブリクエストに数えない） |
| D1 読取行 | 500万per日 | 約1万per日（**学習はスナップショット参照のため D1 を読まない**） |
| D1 書込行 | 10万per日（00:00 UTC にリセット） | **backfill 1シーズンで約65,800行・1試合あたり118.6行（実測）。**設計時の見積り26,500行は外れていた。**上限はシーズン数ではなく行数で管理する** — 1日の見積りを92,000行（枠の92%）に収め、端数のシーズンには `--limit` を渡して枠に当たる前に止める（詳細設計 4.8）。「1日1シーズン」にすると毎日34%を捨てることになる |
| **D1 クエリ数** | **50 per Worker 呼び出し（Free）** | **設計上の真の制約。** 1リクエストあたり行数をテーブルごとに算出する（詳細設計 3.4） |
| **D1 バインドパラメータ** | **100 per 文** | `max_rows_per_request = floor(100 / 列数) × 40` |
| **D1 1行のサイズ** | **2,000,000 バイト** | `artifact_text` に 1.5MB の上限チェックを課す |
| D1 ストレージ | 5GB | 100MB未満 |
| **Pages ファイル数** | **20,000 per デプロイ** | 約15,100（直近3シーズン、76%）。**1ルート5ファイルが実測値** |
| Pages ファイルサイズ | 25 MiB per ファイル | 静的JSONは1日分30KB程度 |
| Pages ビルド | 500回per月 | **最大120回**（`daily-ingest` が中身の変わった回だけ配る。1日最大4回 × 30日）。公式ドキュメントは**直接アップロードがビルド枠を消費するか明記していない**ため、**消費する前提で見積もる**（120 / 500 = 24%）。消費しないなら 0 である |
| **WAF レートリミット（Free）** | **1ルール / カウント期間10秒のみ / ブロック10秒のみ / IP のみ / 対象フィールドは Path と Verified Bot のみ** | `/api/v1/*` に1ルール |
| GitHub Actions | public のため無制限 | 月 約600分 |

**設計を実際に拘束するのは、ストレージでも CPU でもなく「D1 の1呼び出し50クエリ」である。** DDL から列数を数え直した結果、**書き込み対象14テーブルのうち12**が、旧設計のバッチサイズ（一律500行）でこの上限を超えていた。`player_predictions`（31列）は500件で167文を要し、上限の3倍を超える。列数は DDL の**全列数**（バインドしうる最大）で数える（詳細設計 3.4）。

**Workers CPU 10ms は当初 Critical と判断したが、実測で否定された。** 500行の JSON（141KB）のパース 0.56ms、検証 0.28ms、batch 組立 0.50ms で合計 1.34ms。Zod は手書き検証より数倍遅いため実際は3〜4ms と見込まれるが、それでも予算内に収まる。**バッチサイズは CPU ではなくクエリ数で決める。**

> `batch()` 内の各文が50クエリ制限にどう計上されるかは公式に記載がない。**Phase 0（P0-13）で実アカウントでの実測が必要**であり、それまでは「1文＝1クエリ」という最も厳しい前提で設計する。

`backfill` の1日の上限は**書き込み行数**で決める（詳細設計 4.8）。

`/api/v1/health` に当日のカウンタ（Workers リクエスト数、D1 rows_read 積算、キャッシュヒット率、前回バッチ所要時間）を出し、A-10 の検証手段とする。

## 8. 品質保証

### 8.1 テスト方針

| 層 | 配分 | 内容 |
|---|---|---|
| 単体 | 約70% | 特徴量・Elo・パーサ・整形 |
| 結合 | 約25% | D1ローカルでのAPIテスト、バッチの二度流し |
| E2E | 数本 | テーマ保持、横スクロールなし、免責への到達性 |

画面スナップショットは3画面×2テーマから、**1画面×2テーマ＋トークンのコントラスト単体テスト**に縮退させる。色トークンを1つ変えるたびに6枚落ちる維持コストは個人開発に見合わない。

**A-07（免責への到達性）は E2E ではなく静的検査で満たす**（v1.56）。`test:disclaimer` が**ビルドした全ページ**について確定文言の有無と禁じた表記の不在を見る（詳細設計 5.6）。**E2E より広い** — E2E は数ページしか踏めないのに対し、こちらは979ページすべてを見る。

**残る E2E は A-06（再訪時のテーマ保持）と 375px の横スクロールである。** どちらも `localStorage` とレイアウトの実挙動を要し、ブラウザなしでは検証できない。**依存を増やす判断**が要る。

**テストデータ**: 個人情報を持たないため本番コピーも匿名化も不要。`db/seeds/test/` に架空8チーム × 2シーズン（約300試合）の決定論的シードを置く。実在選手名を固定しない。pytest のスキーマは `db/migrations/*.sql` をそのまま in-memory SQLite に適用する（二重管理するとテストが本番を反映しなくなる）。

### 8.2 リーク検証（最重要）

**検証の向きは「`as_of` をずらす」ではなく「DBを撹乱する」。**

旧版のテストは `as_of` を7日後にずらして値が変わらないことを assert していたが、これは論理が逆だった。`as_of` を後ろにずらせば参照できる過去試合が増えるため、**正しい実装なら値は変わるのが正常**である。あのテストは正しい実装を落とし、`as_of` を一切見ない実装だけを通していた。

| テスト | 内容 |
|---|---|
| `test_target_game_mutation_does_not_change_features` | `as_of` 固定のまま対象試合のスコア・スタッツ・観客数を撹乱し、全キーが不変であること（**本命**） |
| `test_future_game_mutation_does_not_change_features` | `as_of` 以降の試合を撹乱し、不変であること |
| `test_as_of_is_actually_applied` | `as_of` を前にずらすと結果依存の特徴量が変化すること（引数が効いている陽性確認） |
| `test_backtest_uses_production_data_as_of` | 保存済み `feature_snapshot` と再構築結果が一致すること |
| `test_features_exclude_unfinished_games` | `SCHEDULED` の試合が集計に入らないこと |
| `test_features_exclude_in_progress_game` | 開始済み・未終了の試合が入らないこと |
| `test_accuracy_within_plausible_band` | `baseline < accuracy < 0.85` の両側境界 |
| `test_target_game_is_excluded_even_if_finished_before_as_of` | **入口ごとに**対象試合が現れないこと（下記） |
| `test_team_rate_*`（5件） | **TeamRate の特徴量にも同じ検証を当てる**（クラブ視点の31列。詳細設計 2.2.1） |
| **`test_player_avail_*`（6件）** | **第1段の特徴量にも同じ検証を当てる**（選手視点の5列）。**候補集合そのものにも当てる** — 候補が未来の情報から作られていれば、特徴量が守られていてもリークである |
| `test_player_minutes_*`（6件） | **第2段の特徴量にも同じ検証を当てる**（選手視点の4列。詳細設計 2.3.1）。**陽性確認は古い試合の分数を変えて作る** — 合成シードは選手ごとに分数が一定で、そのままでは `as_of` をずらしても値が動かない |
| ミューテーション試験 | 意図的にリークさせた実装でテストが**落ちること**を CI で確認（テストのテスト） |

**対象試合の除外は「入口ごと」に検査する。** 2026-10-03 の変異試験で、
`Context._club_history` から対象試合の除外を外しても**リークテストが1件も
落ちなかった**。原因は、検査が `Context.finished_team_games` だけを見ており、
**特徴量が実際に読む `club_history` / `player_history` / `finished_player_stats` を
見ていなかった**ことである。2.1.1 の索引を入れた時点でこれらが**それぞれ独立に
絞り込みを持つ**ようになっており、1つを検査しても他は守られない。

`as_of` の比較だけなら対象試合は自然に落ちる（自分の `tipoff_at` 時点では
まだ終わっていない）。**2本目の関門である「明示的な除外」が効いているかは、
`finished_at` を `as_of` より前に書き換えてから確かめる**必要がある。

**TeamRate の特徴量にも同じ検証を当てる。** 列が別ならリークの経路も別である。
ここを省くと「勝敗は守られているが目標値は漏れている」状態になり、整合化を
通して個人スタッツまで汚染される。

`sql_spy` はクエリ文字列だけでなく**バインドパラメータも記録する**こと。プレースホルダを使えば `game_id` はクエリ文字列に現れず、文字列一致では検出できない。

U-05 と U-06 は受け入れ基準 A-01 / A-02 の判定条件そのものであり、未決のままでは品質ゲートが機能しない。

**U-06 は画面文言にも波及する。** エントリー情報の確定タイミングが未確定であるため、暫定バッジの説明文からは具体時刻を外し「試合当日の午前中に更新されます」としている（要件 8.4）。P0-3 で確定タイミングが判明したら、`gameday_update` のスロット時刻と突き合わせて文言を具体化する。**判明する前に「〇時ごろ」と書かない。**

**U-09 は解決した。** 決めたのは次の4点で、詳細は詳細設計 3.7 にある。

1. **ファイルは4種**（`meta.json` / `today.json` / `schedule/<date>.json` / `games/<id>.json`）。
   一覧は当日＋7日、**詳細は当日の試合だけ**
2. **静的JSON 専用のスキーマを作らない。** 公開APIの応答と同一の形にし、クライアントは
   取得先だけを替える
3. `today.json` は**自分の日付**を持つ（00:00〜06:00 JST は中身が前日である）
4. **`meta.json` に `stale` を真偽値で入れない。** バッチは「今」を知らないため、
   遅延の判定はクライアントが `lastSuccessAt` と現在時刻で行う

**判断の軸は「public リポジトリの履歴に積む量」だった。** 静的JSON はバッチが書き出して
コミットするため、1日の書き換え量 × 365 がそのまま履歴に残る。7日ぶんの詳細まで静的に
すると年460MB積むため採らない（案C）。詳細を当日だけにすれば年90MBに収まり、
**無料枠が枯れた日でも根拠と個人スタッツまで表示できる**。
