# 画面デザインの候補（モック）

工程11a で実装した現行の画面（`web/`、基本設計 6章のトークン）とは**別の方向性**を探索した
モックを置く。**いずれも合成データで、`web/` のコードには影響しない。**

## 採用: 方向性A「データ密度型」

**2026-09-29 に採用が確定した。** 2026-09-28 に第1ラウンドの5案から選ばれ、追加で11案（第2ラウンド）を作って比較したうえで、運営者が A を確定させた。**比較した15案のうち、これ以外は採らない。**

| 画面 | 見るところ |
|---|---|
| 今日の予測（一覧） | https://bpredict-mockups.pages.dev/a-density |
| 試合詳細（試合前） | https://bpredict-mockups.pages.dev/a-density-detail |

### モックの HTML は追跡しない（判断は解消した）

`scripts/check_fixtures.py` は **`.html` を拡張子で一律に追跡禁止**にしている（要件 4.5.2 の
機械的な関門）。この判断は**関門を緩めない側で解消した**。

**採用が確定した以上、耐久性のある記録は設計文書と `web/` の実装であって、モックの HTML では
ない。** トークン・字組み・レイアウト規約・コンポーネントの仕様はすべて
`design-basic.md` 6章 と `design-detail.md` 5.3〜5.4 に写してあり、実装はそれを唯一の出典と
する。モックはそこへ至る過程の成果物であり、**役目を終えたら消えてよい**。

したがって `.html` の追跡禁止に穴を開ける必要はなくなった。**この関門は今後も緩めない。**

数値の生成スクリプトは [`gen_player_stats.py`](gen_player_stats.py) として追跡している
（`.py` なので関門に触れない）。`python3 docs/mockups/gen_player_stats.py` で再現できる。

### この方向性が持ち込むもの

| | 現行（工程11a） | 方向性A |
|---|---|---|
| 構成 | カードを縦に積む | 1試合 = 1レコードの表（`<tbody>` に `<tr>` 2本、時刻・バー・状態を `rowspan`） |
| 勝率の図示 | 左詰めのバー | **中央基準（ダイバージング）バー。** 50% からの隔たりだけを優勢な側へ伸ばす |
| アクセント | 緑 `#416A0E` / `#A3E635` | 藍 `#134A83`（ホーム）＋ 弁柄 `#8E3A12`（アウェイ）の2色 |
| 地色 | `#F6F7F9`（青みのグレー） | `#F7F5EF`（黄みのオフホワイト） |
| 書体 | システムサンセリフ1系統 | 見出しのみ明朝 / ラベルはサンセリフ / 数値は等幅 |
| 影 | ライトでは境界線＋淡い影 | 全廃 |

**中央基準バーが中核である。** 左詰めのバーは全行が左端から始まるため、68% と 52% の差
（このツールが最も伝えるべき差）がひと目で立ち上がらない。50% を軸にすると、拮抗した試合は
「軸の上にほとんど何も無い」という視覚的欠落として現れる。45〜55%（互角）の帯を同じ位置に
描いてあるので、**互角かどうかの判定を読者が自分の目で検算できる**。

**詳細ページは合計行を持つ。** 選手の合計（総出場時間 200.0分 / 得点）が予想スコアと一致して
いることを画面で確かめられる。整合化（詳細設計 2.4）が効いているという主張を、文章ではなく
数字で示す。

### モックの数値の作り方

**手で置いた数字ではない。** 詳細ページの個人スタッツは、詳細設計 2.4 の整合化を通して生成した。
出場時間を 200 分に正規化し、成功率3項目をロジット空間で一律シフトして、得点の合計が予想スコア
（ホーム84 / アウェイ78）に一致する共通シフト量を二分法で解いている。

結果: 得点 84.000000 / 78.000000、総出場時間 200.0000 分、「成功数 ≤ 試投数」の違反 0件。

**成功率のシフトだけで得点を合わせると、成功率が非現実的な水準まで押し下げられた**
（最初の試行でチーム FT% が 69.5% になった）。試投数の置き方が目標得点に対して多すぎたため
である。本番のパイプラインでも試投数はペース予測から来るので、**先に試投数の側を合わせ、
残差だけを成功率のシフトに渡す**手順へ直した。結果は 2FG% 53.7 / 3FG% 37.1 / FT% 74.4、
FGA 63.2 本（ホーム）で、いずれも実在リーグの水準に収まっている。

**丸めで合計がずれる。** 整合化そのものは厳密一致するが、各選手を小数第1位に丸めるとアウェイの
列の和が 77.9 になる。**合計行には「画面に出ている値を足した数」を出し**、ずれの理由を表の下に
書いた。丸める前の 78.0 を出すと、読者が列を足した結果と合計行が食い違う。

### 実測（375px の実ビューポート、Chrome headless）

|---|---|
| 横スクロール | なし（360px でも `scrollWidth == clientWidth`） |
| 44px 未満のタップ対象 | 0件 |
| 段階開示 | 開閉と `aria-expanded` の連動が動作 |

### 採用するなら先に直す文書

この方向性は**基本設計 6章（デザインシステム）と矛盾する**。採用を決めたら、実装の前に
次を更新する（CLAUDE.md「設計から外れる必要が出たとき」）。

| 文書 | 直すところ |
|---|---|
| `design-basic.md` 6.1 | デザイントークン一式（`--accent` の廃止、`--home` / `--away` / `--band` / `--axis` の追加） |
| `design-basic.md` 6.2〜6.3 | 書体（明朝の併用）、カードの角丸と影 |
| `design-detail.md` 5.3 | `ProbabilityBar` を中央基準バーに、`PlayerStatTable` を表構造に |
| `design-detail.md` 5.4 | トークンの CSS |
| `.claude/skills/ui-implementation/SKILL.md` | トークンの複写（`docs/README.md` の複写一覧にある） |

**トークンのコントラストは CI の単体テストで検証する**という規約（基本設計 6.1）は変わらない。
各案の狙いと実測値は、デプロイした HTML の冒頭コメントに書いてある。

### 残っている論点

- **詳細ページが縦に長い。** 18選手ぶんの表を両チーム並べているため。「アウェイを折りたたむ」
  「主力5人＋控えを折りたたむ」という案があるが、**どちらも情報を隠すことになるため入れていない**
- 1試合1行に根拠が入らず、すべて詳細ページ送りになる。根拠の一貫性を差別化に掲げる
  （要件 1.2）以上、一覧で何も言えないのは弱点である
- クラブ名が8文字までで、長い名称は略称運用が前提になる

## 採らなかった案

**2ラウンドで15案を比較した。** 第1ラウンドは 2026-09-28 に5案、第2ラウンドは 2026-09-29 に11案。A 以外はすべて採らない。
**残さないのは、比較のための一時的な成果物であり、残すと「どれが候補か」が曖昧になるため。**
判断の記録はこの節と `git log` に残る。

| 案 | 中核 | 落ちた理由（運営者は A を選んだ） |
|---|---|---|
| 読み物としての予測 | 朝刊の1面。注目の1試合を散文で読ませる。訂正欄を常設 | 明朝が環境依存（Android に和文明朝がなく、Web フォントは予算外）。一覧性が最も低い |
| 中継グラフィック | 暗い面に発光する巨大な数字。68% の真下に同じ大きさで通算的中率 | **要件 8.1（既定テーマはライト）と衝突する。** 縦に長くファーストビューに1試合しか入らない |
| 引き算のミニマル | 画面の横線が全部データ。2px の線の分割点が勝率そのもの | タップできるように見えない。覚える規約が3つある |
| 図が主役 | 横＝勝率／縦＝開始時刻の散布図。較正グラフに今日の位置を重ねる | 13試合の日に点が重なる（7試合前提）。状態バッジの置き場が図上にない |

### 第2ラウンド（2026-09-29・11案）

A とも第1ラウンドの4案とも重ならない方向性を、11人の担当がそれぞれ独立に作った。

| 案 | 中核 |
|---|---|
| 番付・星取表 | 勝率を「十番やったら何勝何敗か」に翻訳し、5つめと6つめの間に切れ目を刻む |
| 設計図 | 勝率を**寸法として記入**。連続寸法で引くので片側だけの表示は図として破綻する |
| 端末 | 50%の位置に**1本の柱**を通す。バーを SVG でなく文字で描く |
| 計器盤 | 角度の比較は人間が最も苦手なので、判断を「注意帯からはみ出しているか」にすり替える |
| 1画面1試合 | **画面そのものを勝率のバーにする**。継ぎ目の高さが勝率 |
| 確信度で仕分け | 仕分けの区切りを的中率の帯の区切りと同じにし、箱の見出しを較正表の1行にする |
| スイス様式 | 8試合を1枚のポスターとして組む |
| 地図 | 会場の位置に配置。近い会場は1点にまとめて番号を並べる |
| 半券 | 再推論を「版を改めて発行し直す」行為として、前の版の勝率を控えに残す |
| 面積モザイク | 縫い目の高さが勝率。8列の縫い目が「今日1日の稜線」になる |
| 時刻表 | 主語を試合から時刻へ。空白の高さが実時間に比例する |

**11案とも 375px で横スクロールなし・装飾タグ0件・両テーマ動作を実測で確認したうえで比較した。**
採らなかったのは品質ではなく方向性の判断である。

### この2ラウンドで分かったこと

**1人に複数案を作らせると必ず似通う。** 第1ラウンドの前に一度、同じ担当に5案を作らせたが、
運営者の評価は「バーのアニメーションが増えただけで、見た目が全て同じに見える」だった。
**担当ごとに独立したコンテキストで、避けるべき既存案を明示して作らせる**ようにしてから、
初めて構造の違う案が出た。

**並行作業は計測器を奪い合う。** 11人が同じマシンで headless Chrome を固定のデバッグポートで
立てたため、次々に停止した。**共有スクラッチパッドの汎用名（`gen.py` / `probe.js`）も衝突する。**
検証は最後に1人がまとめて行う方が速い。
