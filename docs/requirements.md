## 1. 背景と目的

### 1.1 背景

2026-27シーズンより B.LEAGUE は新体制へ移行し、B.LEAGUE PREMIER / B.ONE / B.NEXT の3リーグ構成となった（開幕: 2026年9月22日）。昇降格制度の変更に伴いクラブ構成も再編されている。

B.LEAGUE には一般公開されたデータAPIが存在せず、ファンが試合前に「どちらが勝ちそうか」を定量的に知る手段が乏しい。既存のスタッツサイトは実績値の集計が中心で、試合前の予測を継続的に提示し、かつその的中率を検証可能な形で公開しているサービスは見当たらない。

### 1.2 目的

過去の試合データから統計的に勝敗確率・予想スコア・個人スタッツを算出し、その根拠とともに提示する。同時に、自らの予測精度を隠さず公開することで、検証可能な予測ツールとして信頼を得る。

**このプロダクトの差別化は予測精度の絶対値ではなく、確率の較正の正確さ（「70%」と出した試合が実際に約70%勝つこと）と、判断根拠の一貫性にある。**

### 1.3 スコープ外（明示的に扱わないもの）

- 金銭・ポイントを賭ける機能、およびそれに類する一切の要素
- ブックメーカーのオッズの参照・表示、および外部リンク
- **賭博・ギャンブル事業者の広告掲載、およびこれらとのアフィリエイト契約**
- 公式サイトから取得した記事本文・画像・ロゴの転載
- **取得した生HTMLのリポジトリへのコミット**（4.5.2 参照）
- 取得した生データの一括配信・公開API化
- B.ONE / B.NEXT の試合（v1では対象外）

## 2. プロダクト定義

### 2.1 プロダクトの性格

**モデル予測型**。統計モデルが予測を算出し、ユーザーは閲覧する。ユーザーが予想を入力する機能、的中を競う機能は v1 に含まない。

### 2.2 想定利用者

| 利用者像 | 利用シーン | 求めるもの |
|---|---|---|
| B.PREMIER のファン | 試合当日の朝・移動中 | 今日の試合がどうなりそうか |
| 特定クラブのサポーター | 試合前日〜直前 | 推しチームの勝算と、その根拠 |
| データ好きのバスケファン | 随時 | モデルの精度、どの要素が効いているか |

利用者の大半は統計の専門家ではない。専門用語をそのまま画面に出さないこと。

### 2.3 提供価値

1. **試合前に勝敗確率がわかる** — 感覚ではなく数値で
2. **なぜその予測なのかがわかる** — 判断根拠を日本語で提示
3. **どれだけ当たっているかがわかる** — 的中率をモデルバージョン別に公開し、外れた試合も隠さない

### 3.2 v2 以降の候補

- ユーザー登録、お気に入りクラブ、予測通知
- ユーザー自身の予想入力と、モデルとの対戦
- B.ONE への対象拡大
- iOS ネイティブアプリ

**v2 でユーザー機能を追加する際は、認証方式・個人データの保存範囲・削除手順・キャッシュ方針を先に決めること。** 現在の設計は「公開データのみ・全レスポンスが共有キャッシュ可能」という前提で最適化されており、認証付きレスポンスに `Cache-Control: public` を流用すると他人のデータが配信される。また、ユーザー投稿を受け付ける場合はプロバイダ責任制限法への対応と、選手への誹謗中傷を含む投稿の削除方針が新たに必要になる。

### 3.3 予測の確定ルール

- 予測は試合開始時刻をもって **確定（freeze）** し、以後一切更新しない
- 試合開始前の再推論は、**既存行を `is_active = 0` にして新しい行を追加する**（上書きしない）
- 確定済み予測（`is_final = 1`）は改変不可能とし、的中率算出の唯一の根拠とする
- **試合開始時刻を過ぎた試合への予測書き込みは、API層で拒否する**（宣言ではなく関門で守る）

## 4. 非機能要件

### 4.1 コスト制約（最優先制約）

| 項目 | 要件 |
|---|---|
| 年間運用費 | 原則ゼロ。やむを得ない場合も合計 **年額5,000円以内** |
| 従量課金 | **上限のない従量課金構成は採用不可**。超過時に停止する無料枠のみ使用する |
| 除外項目 | Apple Developer Program 年会費（約12,000円）は上記上限の対象外 |

この制約は設計の前提であり、性能・機能より優先される。

**例外的に容認する支出**: 独自ドメイン（Cloudflare Registrar で年1,000〜1,500円）。これは Cloudflare の WAF レートリミットを使えるようにするためであり、**無料枠を守るための投資**として上限内で認める（4.2 の可用性要件を参照）。`*.pages.dev` はゾーンを持たないため WAF・レートリミット・キャッシュルールが一切使えない。

### 4.2 性能

測定条件を伴わない目標は検証できないため、以下のとおり定義する。

| 指標 | 目標 | 測定条件 |
|---|---|---|
| LCP | 2.5秒以内 | モバイル4G相当 / p75 |
| INP | 200ms以内 | p75 |
| CLS | 0.1以内 | p75 |
| API応答（キャッシュミス） | 300ms以内 | Workers内計測 / p95 |
| API応答（キャッシュヒット） | 50ms以内 | p95 |
| 日次バッチ | 15分以内 | p95 |
| 初期JS | 120KB以内 | gzip後 |
| 総転送量（初回） | 250KB以内 | gzip後 |

日次バッチ15分の内訳予算: 依存セットアップ2分 / スクレイピング3分 / D1 I/O 2分 / 推論3分 / 予備5分。

**可用性に関する制約**: 無料枠は超過時に課金されず停止するため、枠の枯渇はそのままサービス停止を意味する。Workers の枠は 00:00 UTC（09:00 JST）にリセットされるため、日中に枯渇すると**日本の夕方から夜という最も価値のある時間帯が使えなくなる**。したがって以下を要件とする。

- 主要導線（今日の予測・試合一覧）は **Workers を経由せず静的アセットとして配信**し、枠枯渇時も表示が継続すること
- 公開URLの空間に上限を設けること（日付の範囲外を D1 到達前に打ち切る）
- レート制限を設けること

### 4.3 可用性・運用

- 日次バッチが失敗しても、静的に配信済みの予測が残るため画面は表示され続ける
- バッチ失敗時は実行ログに記録し、画面に更新遅延を表示する
- 個人開発前提のため、24時間監視・即時復旧は要件としない。**壊れても表示が止まらないことを優先する**

### 4.4 セキュリティとプライバシー

- リポジトリは public。**認証情報・トークン類をコードに含めない**
- D1 への書き込みは Workers の内部エンドポイント経由に一本化し、Bearer トークンで保護する
- **例外オブジェクトをそのままログ・DBに保存しない**（トークンやIDがURLに含まれて漏洩するため）
- 公開APIのレスポンスに内部IDや取得元URLを含めない

**個人情報の取扱いについて（重要な訂正）**

v1 は**サイト利用者**の個人情報を取得しない（ユーザー登録・問い合わせフォーム・ログイン機能を持たない）。

ただし、**選手の氏名等を検索可能な形でDB化して保持するため、個人情報保護法上の「個人情報データベース等」を構成し、運営者は個人情報取扱事業者に該当する**（5,000件要件は2017年改正で撤廃済み。個人・非営利でも該当する）。公表情報からの取得であること、写真を使わないことは事業者該当性を否定しない。

したがって以下を v1 の必須要件とする。

- 利用目的の公表（F-13 プライバシーポリシー）
- 安全管理措置
- 開示・訂正・利用停止等の請求に対応する連絡先の設置
- **予測に不要な属性（生年月日、出身地、契約情報等）は取得対象から除外する**

### 4.5 法務・コンプライアンス

#### 4.5.1 基本方針

| 項目 | 方針 |
|---|---|
| 位置づけ | B.LEAGUE および各クラブとは無関係の非公式ツールである旨を明記 |
| 賭博 | 賭博・ギャンブルを助長しない旨を明記。金銭・ポイント要素を持たない |
| 広告 | 導入する場合、**賭博カテゴリのブロック設定を導入と同時に行う**。カテゴリブロックができない広告事業者を採用しない |

#### 4.5.2 生HTMLの取扱い（最重要）

**取得した生HTMLをリポジトリにコミットしてはならない。**

個々のスコアや日程に著作物性は認められにくい一方、**HTMLページそのものは事実データではない**。ページ内のテキスト表現、見出し、ナビゲーション文言、レイアウト構造を含む一体としてのページは著作物として保護されうる。これを public リポジトリに置くことは複製（著作権法21条）および公衆送信（23条1項）に当たり、「事実データだから」という本プロジェクトの立論が**一切通用しない唯一の行為**である。情報解析目的の利用（30条の4）も、リポジトリでの再配布には適用が困難である。

したがって、

- 取得したHTMLはローカルの gitignore 対象ディレクトリにのみ置く
- パーサのテスト用フィクスチャは、**構造のみを模し、値をダミーに置換した合成データ**とする。実サイトの文言・記事・画像参照を残さない
- **ボックススコアは `<script>` 内の埋め込みJSONで配信される**（Phase 0 で確認）。取得した本文を生のままコミットしない点は HTML と同じであり、fixture も合成データとする
- `.gitignore` に `**/fixtures/**/*.html` と `**/fixtures/**/*.raw.json` を含める
- CI で fixtures に実サイト由来の文字列が混入していないことを検査する

#### 4.5.3 著作権とデータ取得の評価

事前調査の結果は 5.1 に記載する。その上で、**本方針は確定的な法的判断ではなく、以下を残存リスクとして認識する**。

- 約8,000試合・20万行という体系的・網羅的な複製が、**データベースの著作物**（著作権法12条の2）の侵害と評価される可能性
- 著作物性が否定されても、大量複製が**不法行為**（民法709条）を構成しうること（自動車データベース事件・東京地判平成13年5月25日）
- 著作権法30条の4（情報解析）の適用余地はあるが、同条ただし書「著作権者の利益を不当に害することとなる場合」により、**B.LEAGUE または提携事業者が統計データを有償提供している場合は適用が否定されうる**こと（Phase 0 で有無を調査する）
- 利用規約の「複製、公衆送信**その他の利用**をすることはできません」は包括条項であり、「スクレイピングを名指ししていない」ことは何も保証しないこと

なお、不正競争防止法の「限定提供データ」（2条7項）は電磁的管理性を要件とするため、誰でも閲覧できる公式サイトのデータには及ばない。この点のリスクは低い。

#### 4.5.4 免責事項に盛り込む項目

- **選手個人のスタッツ予測は、選手個人の能力や将来の評価を示すものではなく、過去の統計から算出された機械的な推定値であること**

#### 4.5.7 サービス名

## 6. 予測モデル要件

### 6.1 出力

| 出力 | 形式 | モデル |
|---|---|---|
| 勝敗確率 | ホーム/アウェイの百分率 | **二値分類と点差回帰の両方を実装し、Phase 0 で比較して採用経路を決める** |
| 予想スコア | 両チームの得点（整数） | **得点差と合計得点の回帰から導出** |
| 個人スタッツ | フルボックススコア（6.8） | ハードルモデル＋レート回帰＋チーム整合化 |
| 判断根拠 | 要因グループ別の寄与 | SHAP を4〜5グループに集約 |

**勝率と予想スコアは構造的に整合させること。** 独立した2本の回帰で各チーム得点を予測すると、「ホーム68%」なのに「82–85でアウェイ勝ち」という出力が原理的に起こる。接戦ではほぼ確実に発生し、試合詳細画面で両者が並ぶため直接ユーザーに見える。得点差（margin）と合計得点（total）を予測し、`home = (total + margin) / 2`、`away = (total - margin) / 2` とすれば整合が保証される。

**勝率の導出経路は2つあり、v1 では両方を実装して Phase 0（P0-11）で比較する。**

| 経路 | 内容 | 長所 | 短所 |
|---|---|---|---|
| A: Winner 直接 | 二値分類の出力をそのまま勝率とする | logloss を直接最適化するため較正が良い | Margin 予測と符号が食い違いうる |
| B: Margin から導出 | `P(home) = Φ(margin / σ)`、σ は残差標準偏差 | 勝率と予想スコアが定義上一致する | 残差が正規でない場合に較正が崩れる |

**σ の値は決め打ちしない。** 12〜13点というのは他リーグからの見当であって本データの実測値ではない。**P0-11 で walk-forward の残差から実測し**、`model_versions.margin_sigma` に記録する。実測前に定数として書かない。

比較は同一の walk-forward ウィンドウで Brier と ECE を測って行う。**判定基準**: B の Brier が A より 0.003 以上悪ければ A を採用する。差が 0.003 未満なら整合性が保証される B を採用する。いずれを採用しても、**画面に出す勝率と予想スコアの符号が矛盾しないこと**（A 採用時は `test_win_prob_and_score_agree` で検出し、矛盾した試合は勝率側を正としてスコアを丸める）を保証する。

どちらを採用したかは `model_versions` に記録し、`/about` の「予測の仕組み」に反映する。

予想スコアの MAE は現実的に8〜10点であるため、**小数第1位まで表示しない**（精度の誤認を招く）。

### 6.3 データリーク防止（絶対原則）

**特徴量は「試合開始時点で確定している情報」のみで構成すること。**

- 特徴量関数は必ず `as_of` を引数に取り、参照クエリに絞り込みを含める
- 当該試合の `team_game_stats` / `player_game_stats` / `games.attendance` を参照しない
- 試合後にしか判明しない値は、必ず「過去試合の集計」に変換してから使用する
- 検証は時系列分割で行う。ランダムシャッフル分割は使用しない
- 特徴量生成時のスナップショットを予測レコードに保存する

**注意**: 試合終了時刻がスキーマにないため、`tipoff_at` で絞ると「17:05開始・19:05終了の試合」が「19:05開始の試合」の特徴量に確定情報として混入する。**絞り込みは試合終了時刻で行うこと**（`finished_at` を追加する）。

`finished_at` は**列として保持する**（読み出し時に計算しない）。すべてのリーク判定クエリがこの値を通るため、計算式が呼び出し側に散ると、一箇所直し忘れただけでリークが復活する。取り込み時に実測値を入れ、取得できない場合は `tipoff_at + 2時間` を書いたうえで `finished_at_is_estimated = 1` を立て、推定値であることを区別できるようにする。

また、**本番とバックテストでデータ鮮度が一致することを保証する必要がある**。本番の日次推論は最大7日前の情報で予測するが、バックテストでは全試合がDBに揃っているため開始直前の情報が使える。同じ関数を呼んでいても入力が違い、検証スコアが体系的に過大評価される。これは「リーク」と呼ばれずに見逃される種類のバイアスであり、`predictions` に推論実行時点のデータ鮮度（`data_as_of`）を記録して検証する。

### 6.4 評価指標とベースライン

| 指標 | 用途 |
|---|---|
| Brier Score | **主要な改善指標**。確率予測の質。採用ゲートはこれで判定する |
| Accuracy | **表示専用**。一般向けに公開する「的中率」。**採用ゲート・モデル比較・アラートのいずれにも使わない** |
| Log Loss | 学習時の目的関数 |
| ECE（等頻度10ビン、ビンあたり最低50サンプル） | 較正誤差。**n ≥ 500 のときのみゲートに使う** |
| MAE | 予想スコアの誤差 |

#### ECE の閾値は固定値にしない（検証済み）

**ECE は完全に較正されたモデルでもサンプリングノイズだけで有限の値を取り、その大きさは n に依存する。** 固定閾値 0.05 は小標本では良いモデルを落とし、大標本では素通りする。

真の確率を知る完全較正モデルで4,000回シミュレーションした実測値:

| n | 1ビンの件数 | ECE 平均 | ECE 95%点 | 固定閾値 0.05 の挙動 |
|---|---|---|---|---|
| 200 | 20 | 0.0824 | 0.1163 | 完全なモデルでも落ちる |
| 500 | 50 | 0.0518 | 0.0734 | 半々 |
| 1,200 | 120 | 0.0337 | 0.0479 | ほぼ常に通過 |
| 3,000 | 300 | 0.0212 | 0.0299 | 常に通過 |

したがって閾値は次のように定める。

- **n < 500 のとき、ECE をゲートに使わない**（1ビン50件を満たさず、値がノイズに支配される）
- **n ≥ 500 のとき、`ECE < ノイズフロア95%点 × 1.5` をゲートとする。** ノイズフロアは「そのモデルの予測確率分布」からブートストラップで毎回推定する（上表は一様分布での参考値であり、そのまま定数化しない）
- 推定には `verification/01_ece_noise_floor.py` を用いる

> この表は `verification/01_ece_noise_floor.py` で再現できる。

**ベースラインは3段で持つ。**

1. ホームチームが必ず勝つ（Accuracy の比較用）
2. **Elo差単体のロジスティック回帰**（GBDT の真の対抗馬）
3. 全特徴のロジスティック回帰

2 を Brier で有意に上回れなければ、LightGBM を使う理由がない。

**Accuracy を採用ゲートにしない理由**: ホーム勝率が約60%の場合、良い確率モデルでも `home_prob > 0.5` を出す試合が大多数になるため Accuracy はベースラインとほぼ並ぶ。Brier で明確に優れているモデルが Accuracy 条件で誤って棄却される。

### 6.5 モデルの採用基準

新モデルは以下をすべて満たす場合のみ有効化する。

1. **評価サンプル数が n ≥ 500**（この下限を満たさない場合、いかなる比較も行わず現行モデルを継続使用する）
2. **同一の評価ウィンドウ**（直近2シーズンを対象とした walk-forward）で再評価した Brier が現行モデルより良い
3. その差が**有意かつ実質的**であること — 試合ごとの Brier 差のブートストラップ信頼区間（95%）が0を跨がず、**かつ**点推定の差が **0.003 以上**（最小実質差）
4. ECE が 6.4 の n 依存閾値を満たす（n < 500 ではこの条件を課さない = 条件1により到達しない）
5. **欠損率30%を超える特徴量が存在しない**

**Accuracy は採用判定に一切使わない。** 「Accuracy が +0.03」といった基準は統計的に識別できない。理想モデル（真の勝率を知る上限）で20,000回試行した実測では、ベースラインとの差の標準偏差は n=200 で 0.041、n=500 で 0.026 であり、`+0.03` は n=200 では 1SD 以内に収まる。理想モデルですら 8.5% の確率で基準を落ちる。

| n | 理想モデル | ベースライン | 差の平均 | 差の SD | `+0.03` を落ちる確率 |
|---|---|---|---|---|---|
| 200 | 0.656 | 0.572 | 0.085 | 0.041 | 8.5% |
| 500 | 0.656 | 0.572 | 0.084 | 0.026 | 1.7% |
| 1,200 | 0.656 | 0.571 | 0.085 | 0.017 | 0.0% |

> この表は `verification/02_acceptance_criteria_power.py` で再現できる。副産物として、理想モデルの精度が 65.6% となり付録B の見立て「64〜68%」と整合することも確認した。

学習条件は必ず再現可能にすること。`seed` / `bagging_seed` / `feature_fraction_seed` / `deterministic` を固定し、`model_versions.params` に記録する。これらを固定しないと、`bagging_fraction` により Brier が ±0.003 ぶれ、**モデルの差し替え可否が実質的に乱数で決まる**。

#### 再学習頻度と検出力の関係（重要な前提）

再学習の頻度は**月次または新シーズン開始時**とする。週に増える試合は約30件（全体の0.4%）で、毎週作り直す統計的理由がない。

ただし、**月次の差し替え判定は検出力が低い**ことを前提として受け入れる。真の差 0.03 を検出できる確率は n=200 で 12.7%、n=1,200 でも 54.8% にとどまる。これは以下を意味する。

- 月次で回しても「ノイズで誤って差し替わる」ことは起きない（上記の厳格ゲートが防ぐ）
- 代わりに「**実際の改善を見逃す**」方向に倒れる。見逃した改善は次の月次、最終的にはシーズン単位の評価で拾う
- したがって月次維持は安全側の選択であり、**ゲートを緩めて検出力を上げてはならない**（それは誤差し替えを招く方向の変更になる）
- 学習コストは毎月発生し続けるため、`monthly_train` の120分タイムアウト管理は必須とする（7章・design-basic 4.1）

### 6.6 コールドスタートと分布シフト

**シーズン序盤**

- Elo の初期値は前シーズン終了時点の値を平均方向へ回帰させた値とする（回帰率は実データで探索。NBAの標準値0.75より強い回帰が適切な可能性が高い）
- 消化試合数が10未満のチームは、当季集計を明示的な縮約式で扱う: `winrate = (w + k × prior) / (n + k)`、k=10、prior は前季勝率の回帰値
- 消化試合数が5未満の場合、画面に序盤である旨を表示する

**昇格クラブ・復帰クラブ**

昇格クラブに Elo 1500（＝旧B1平均）を与えると**大幅に過大評価**する。前季 PREMIER 下位層の水準を初期値にする。

**「前季にトップリーグの試合がないクラブ」はすべてこの扱いにする。** 空白が1シーズンでも8シーズンでも同じであり、過去にトップリーグにいた Elo が残っていても**持ち越さず捨てる**。`SEASON_REGRESSION` を空白シーズン数だけ適用すると偏差が `R^N` に縮んで実質 1500（トップリーグ平均）になり、二部に長くいたクラブを平均と評価することになる。空白シーズン数の閾値は設けない（11シーズンで該当が7件しかなく、推定する検出力がない）。

**B.ONE / B2 時代の Elo は存在しない。** 取得対象はトップリーグ（PREMIER と前身の B1）のみであり（5.4）、下位リーグの試合を取り込まないため Elo も計算されない。v1.7 まで記載していた「B.ONE 時代の Elo があればリーグ間オフセットを推定して平行移動する」という分岐は**永久に発火しないため削除した**。

**B.PREMIER の構成は昇降格の結果ではない。** 2026-27 では `718` 神戸（B1 在籍は 2017-18 のみ、以後8シーズン不在）と `716` 信州（2シーズン不在）が該当する（`verification/RESULTS.md`）。

**観客制限期間（2020-21 / 2021-22）**

約1,500〜2,000試合が無観客または収容制限下で行われている。この期間は**ホームアドバンテージ自体が消失**することが各国リーグで確認されており、固定値での Elo 更新は系統的に歪む。

- `games` に観客制限フラグ（`spectator_restricted`）を持たせる。**取り込み時に判定して列に書く**（特徴量生成時に毎回計算し直さない）
  - `attendance / capacity < 0.2` なら 1
  - `attendance` または `capacity` が NULL なら **NULL（判定不能）** とし、Elo 更新では通常のホームアドバンテージを使う
  - ただし **2020-21 / 2021-22 シーズンは期間指定で強制的に 1 とする**（入場者数が非公開の試合が混じっても取りこぼさないため）
- 該当期間は Elo 更新時のホームアドバンテージを0にする
- 動員系特徴（#29）の集計から除外する

**時間方向の重み**

10年前の試合と先週の試合を同じ重みで学習しない。`weight = exp(-λ × 経過シーズン数)` で λ を walk-forward 上で探索する（半減期3〜5シーズンが出発点）。これはルール変更とリーグ再編の両方に効く。

### 6.7 確率の較正

**較正は out-of-fold で fit すること。** 学習データそのもので fit すると、学習データ上の過剰な分離を「正しい」と学習し、本番では過信が増幅される。しかも較正誤差は学習時には小さく見えるため、採用ゲートも機能しなくなる。

**そもそも較正が必要かを先に測ること。** logloss を目的関数にした LightGBM の出力は元々ほぼ較正されている。較正なしの信頼性曲線を測り、ECE が十分小さければ較正器を入れない。

入れる場合、Isotonic は非パラメトリックで自由度が高く、n=800 程度の較正セットでは裾のブロックが数サンプルになり悪化しうる。**パラメータ2個の Platt scaling を第一候補**とする。較正器も `model_versions` の管理対象に含める。

### 6.8 個人スタッツ予測

#### 6.8.1 予測する項目

公式のボックススコア項目（[B.LEAGUE スタッツ用語集](https://www.bleague.jp/glossary/)に準拠）を予測する。**シュート項目は「試投数（カウント）＋成功率（0〜1）」の組で予測し、成功数は導出する。**

| 分類 | 予測する項目 | 形式 |
|---|---|---|
| 出場 | MIN（出場時間） | カウント |
| シュート（試投） | 2FGA / 3FGA / FTA | カウント |
| シュート（成功率） | **2FG% / 3FG% / FT%** | 率（0〜1） |
| リバウンド | OR / DR | カウント |
| プレー | AS / TO / ST / BS | カウント |
| ファウル | F（ファウル数） / **FD（被ファウル数）** | カウント |

上表は15行ある。このうち **MIN は第2段（PlayerMinutes）の出力**であり、**第3段（PlayerRates）の出力は MIN を除いた14項目**（カウント11 + 成功率3）である。以降「14項目」と書いた場合は常に第3段の14項目を指す。

「テイクチャージ」は NBA のハッスルスタッツであり、FIBA 系のボックススコアには存在しない。**FD（被ファウル数）が実質これに相当する。**

**なぜ「成功数」ではなく「成功率」を予測するのか。** 旧版は 2FGM / 3FGM / FTM を成功数（カウント）として予測していたが、これではチーム予測への整合化（6.8.5）が原理的に成立しない。成功数と試投数を独立にスケールすると `成功数 > 試投数` が生じ、それを防ぐためのクリップが収束を壊す。実測では整合化の失敗ケースの **73% が FT 成功率**で発生した。試投数と成功率の組で持てば、成功率をロジット空間でシフトするだけで制約を自動的に満たす（6.8.5）。

これは 6.8.2 の「率を直接予測しない」と矛盾しない。**モデルが出す率は「この選手のこの試合における期待成功率」という連続量**であり、画面に出す `FG% = FGM / FGA` とは別物である。表示する率は必ず導出値であり、分数と併記する（8.3）。モデル出力としての率を単独で画面に出してはならない。

#### 6.8.2 導出する項目（予測しない）

以下はカウントの予測値から計算で求める。独立に予測すると恒等式が崩れる。

| 項目 | 導出式 |
|---|---|
| 2FGM / 3FGM / FTM | `2FG% × 2FGA` / `3FG% × 3FGA` / `FT% × FTA` |
| PTS | `2FGM × 2 + 3FGM × 3 + FTM` |
| FGM / FGA | `2FGM + 3FGM` / `2FGA + 3FGA` |
| TR | `OR + DR` |
| FG%（表示用） | `FGM / FGA` |
| EFG% | `(FGM + 0.5 × 3FGM) / FGA` |
| TS% | `PTS / (2 × (FGA + 0.44 × FTA))` |

**画面に率を単独で出してはならない。** 1試合の試投数は6本程度であり、実績としての FG% は `0 / 16.7 / 33.3 / 50 / 66.7 / 83.3 / 100` しか取りえない離散値になる。ここに「FG% 47.3%」とだけ出すのは、存在しない精度を主張することにあたる。**必ず分数と併記し**（`6.4 / 13.1 (48.9%)`）、試投数の予測値が閾値未満の選手には率を出さず分数のみ表示する（8.3）。

**FG は 2P と 3P の合計として導出する。** FG を予測してから 2P/3P に分解すると `FGM = 2FGM + 3FGM` が成立しない。

**PTS は恒等式で導出する。** 独立に予測すると内訳と合計が食い違う。

#### 6.8.3 予測しない項目

| 項目 | 理由 |
|---|---|
| **＋/－** | チームの結果を個人に帰属させた指標で、1試合の分散が極端に大きい。MAE は 9〜12点規模になり、ほぼ毎回外れて見える。しかも「チーム得点差予測 × 出場時間シェア」以上の情報を持たず、出しても新しいことを伝えない。**実績のみ表示し、予測はしない** |
| EFF | 導出は可能だが、複数項目の誤差が合算されるため予測値としての意味が薄い。実績のみ表示 |

#### 6.8.4 モデル構成

```
第1段  PlayerAvail    P(出場)                          二値分類
第2段  PlayerMinutes  E[出場時間 | 出場]               回帰
第3段  PlayerRates    カウント11項目: 単位時間レート   回帰 × 11
                      成功率3項目: 2FG% / 3FG% / FT%   回帰 × 3（レートではない）
第4段  Reconciliation チーム予測への整合化             計算
```

**カウント11項目（2FGA / 3FGA / FTA / OR / DR / AS / TO / ST / BS / F / FD）は per-minute レートで学習する。** カウントのまま学習すると出場時間の分散に支配される。

**成功率3項目（2FG% / 3FG% / FT%）は per-minute にしない。** 率は時間当たりの量ではないため、per-minute 化は無意味である。目的変数は過去試合の成功率、学習重みは試投数とし、シュリンク（`(made + k × prior) / (attempted + k)`、prior はリーグ平均、k は試投数ベースで探索）を経た値を使う。出力は `clip(0.01, 0.99)` に収める（ロジット変換の定義域を確保するため。6.8.5）。

`P(出場) < 0.5` の選手は**表示対象から除外する**。登録選手の3〜4割が0分であり、単一回帰では欠場濃厚な選手に「8分・4.2点」のような値が出る。

期待値の積（`E[minutes] × E[pts/min]`）は `E[minutes × pts/min]` と等しくない。出場時間と単位時間生産性は正相関するため、素朴な積は系統的に過小評価になる。第4段の整合化でこれを補正する。

#### 6.8.5 チーム予測との整合化（必須）

**選手ごとに独立して予測した値をそのまま表示してはならない。** 5人の得点合計がチームの予想スコアと一致せず、FGA の合計もチーム予測とずれる。同じ画面に矛盾した数字が並ぶことになる。

##### 予測の持ち方（重要）

シュート項目は**成功数と試投数を独立に予測しない**。「試投数」と「成功率」に分解して予測する。

| 予測する | 導出する |
|---|---|
| `2FGA` `3FGA` `FTA`（試投数、カウント） | `2FGM = 2FG% × 2FGA` など |
| `2FG%` `3FG%` `FT%`（成功率、0〜1） | `PTS = 2FGM×2 + 3FGM×3 + FTM` |

この持ち方により **`成功数 ≤ 試投数` が構造的に保証**される。成功数を直接予測すると、後段のスケーリングで試投数を超えてしまい、クリップが必要になる。

**チーム側の目標値も同じ構造で作る。** 各項目を独立に生成すると、約2%の確率で「FT成功数 > FT試投数」のような実行不能な目標が生まれ、整合化が原理的に成立しなくなる（検証済み）。

##### 前段: チーム目標の整合化（必須）

**TeamRates の出力をそのままチーム目標にしてはならない。** TeamRates（試投数・成功率の回帰）と Margin / Total は別のモデルであり、TeamRates から導出した得点が予想スコアと一致する保証がない。一致しないまま選手側の整合化に渡すと、「選手の合計＝チーム目標」は満たされるが「チーム目標＝画面に出る予想スコア」が崩れ、矛盾の位置が一段ずれるだけになる。

**予想スコアを正とし、チームの成功率を寄せる。** 選手側と同じロジット空間シフトを、チーム目標の生成時にもう1段入れる。

```
S     = (total + margin) / 2        （アウェイは (total - margin) / 2）
l_s   = logit(TeamRates の成功率 s)  （s ∈ {2FG%, 3FG%, FT%}）

pts(d) = 2·σ(l₂ + d)·A₂ + 3·σ(l₃ + d)·A₃ + 1·σ(l_f + d)·A_f

pts(d) = S を満たす共通シフト量 d を brentq で解き、成功率を σ(l_s + d) に置き換える
```

- **σ は単調増加、係数（2 / 3 / 1）と試投数 `A` は非負**であるため `pts(d)` は `d` について単調増加であり、解は一意に存在する。反復は不要（1回で厳密一致する）
- **試投数（`A₂` `A₃` `A_f`）は動かさない。** ペースと配分の予測をそのまま残し、得点の帳尻は成功率だけで合わせる
- 成功率はロジット空間で動かすため `[0,1]` を出ない。**ここでもクリップを使わない**
- `pts(d)` の値域は `(0, 2A₂ + 3A₃ + A_f)` であるため、`S` がこの区間の外なら解が存在しない。その場合は選手側と同じく **`InfeasibleTargetError` を投げる**（無言でクリップしない）。当該試合の個人スタッツ予測を破棄し、チーム予測のみを保存して、画面には算出不能と表示する

この前段を通した値だけを `prediction_team_targets` に保存する。保存された目標値が予想スコアと ±0.5点以内で一致することは受け入れ基準 A-16 で検証する。

##### 整合化の手順

```
1. 期待出場時間       m_i = P(出場_i) × E[MIN_i | 出場]
2. 総出場時間を正規化   m_i ← m_i × 200 / Σ m_i        （5人 × 40分 = 200分）
3. 試投数・その他       x_i,s = rate_i,s × m_i
4. 試投数をチーム目標へ  x_i,s ← x_i,s × T_s / Σ_i x_i,s
5. 成功率をチーム目標へ  ロジット空間で一律シフトし Σ(pct_i × att_i) = T_made を満たす d を解く
                       pct_i ← sigmoid( logit(pct_i) + d )
6. 得点・成功数は導出    PTS_i = 2FGM_i×2 + 3FGM_i×3 + FTM_i
```

**手順5でクリップを使ってはならない。** 成功率を [0,1] の範囲で一律に掛け算すると、1.0 に張り付いた選手が出た時点で合計を目標に合わせられなくなり、反復が振動する。実測では失敗ケースの**73%がFT成功率**で発生した。

ロジット変換は (0,1) を (-∞,∞) に写すため**クリップが原理的に不要**になり、単調性から解が一意に存在する。

```python
def shift_to_target(pct, att, target):
    """sum(pct * att) = target を満たすロジットシフト量を解く。"""
    lo = logit(np.clip(pct, 1e-4, 1 - 1e-4))
    f  = lambda d: (sigmoid(lo + d) * att).sum() - target
    return sigmoid(lo + brentq(f, -50, 50))
```

##### 反復回数と許容誤差

**手順4〜5を3回反復する。** 1,500ケースの検証結果（設計の妥当性はこの数値で判断する）。

| 反復 | 項目誤差 中央値 | 99%点 | 最大 | 得点誤差 最大 |
|---|---|---|---|---|
| 1 | 0.0000% | 3.39% | 10.73% | 0.00000 |
| 2 | 0.0000% | 0.94% | 3.51% | 0.00000 |
| **3（採用）** | **0.0000%** | **0.27%** | **1.87%** | **0.00000** |

許容誤差は**得点 ±0.5点、その他 ±2%**、制約違反0件とする。**2回では最大誤差が 3.51% で許容範囲（±2%）を超えるため、3回とする。**

得点誤差が反復1回でも厳密にゼロなのは、手順6が恒等式による導出であり、手順5で成功数が目標に厳密一致するため。残る誤差は手順4と手順5の相互作用による試投数側のずれである。

旧版の「試投数と成功数を別々に比例スケールして2回反復」は収束しない。同一条件での実測は項目誤差の最大 24.7%、得点誤差 4.42点だった。

延長戦がある場合、総出場時間は 200分ではなく `200 + 25 × 延長回数` になる。予測時点では延長を仮定しない。

> この手順は `verification/03_reconciliation_logit.py` で再検証できる。整合化のロジックを変更した際は必ず再実行すること。

#### 6.8.6 誤差の提示

誤差の目安は「**当該選手の直近N試合の絶対誤差の中央値**」と定義する。モデル全体の平均 MAE を全選手に表示しても意味がない（20点の選手と4点の選手に同じ値を出すことになる）。

**低レートの項目（ST・BS）は、MAE が平均値と同程度になる。** 1試合あたり平均0.7回程度の項目では、予測は実質「その選手の平均を出しているだけ」であり、付加価値がほとんどない。表示はするが、これを隠さず誤差目安を併記する。

誤差目安を全項目に表示すると画面が埋まるため、主要4項目（MIN・PTS・TR・AS）に限定する。

#### 6.8.7 学習コストへの影響

予測対象が14項目（カウント11 + 成功率3）に増えるため、学習時間が延びる。出場確率と出場時間を加えると選手モデルは計16本になる。LightGBM はマルチ出力をネイティブにサポートしないため、項目ごとにモデルを持つことになる（特徴量行列は共通なのでパイプラインは1本）。

- 選手スタッツの学習行数は約20万行
- 16項目 × fold 数の学習が必要
- `monthly_train` のタイムアウトを **120分** に設定する
- **選手モデルの fold 数は3に制限する**（チームモデルは5）

学習時間が枠に収まらない場合、per-minute レートでの学習に切り替え、木をさらに小さくする。

### 6.9 根拠の提示

SHAP 値は**ログオッズ空間の値であり、確率への加算ではない**。「寄与 +12%」のような百分率表示は「勝率を12ポイント押し上げた」と誤読されるため行わない。`%` は勝率専用に予約する。

**個別特徴ではなく要因グループ単位で集約して表示する。** 特徴量は展開すると60〜70列になり、Elo・勝率・得失点差・ORtg・SOS・Four Factors・動員はすべて「チームの強さ」という単一の潜在因子の観測値で相互相関が0.6〜0.9に達する。LightGBM は予測が壊れないが、分割の選択が相関特徴間で分散するため**SHAP 値も分散し、ほぼ同じ条件の2試合で表示される根拠が入れ替わる**。

グループは「チーム力」「日程・疲労」「選手」「会場」の4〜5とし、グループ内の SHAP を合算する。

**表現の規約**: 根拠ラベルに**選手個人の能力・資質・人格に対する評価を含む表現を用いない**。使用するのは公式記録から機械的に導かれる事実の記述に限る。

- 可: 「直近5試合の平均得点」「出場時間の減少」「欠場による影響」
- 不可: 「不調」「衰え」「戦力外」「期待できない」「使えない」

## 7. システム構成要件

| レイヤ | 採用技術 | バージョン | 無料枠 |
|---|---|---|---|
| フロントエンド | Next.js（**静的出力**） on Cloudflare Pages | **Next.js 16 / Node.js 20.9+ / TypeScript 5.1+** | **1デプロイあたり20,000ファイル / 1ファイル25MiB / ビルド500回per月** |
| 予測データ配信 | **バッチが書き出した静的JSON**（Pages の静的アセット） | — | 無料・無制限 |
| API | Cloudflare Workers（Hono） | — | 10万リクエストper日 / **CPU 10ms per リクエスト** / サブリクエスト50 |
| データベース | Cloudflare D1 | — | 5GB / 読取500万行per日 / **書込10万行per日** / **1呼び出しあたり50クエリ（Free）** / バインドパラメータ100per文 / 1行2,000,000バイト |
| バッチ | Python 3.12 on GitHub Actions | LightGBM / pandas | public リポジトリのため実行時間無制限 |
| ドメイン | Cloudflare Registrar（年1,000〜1,500円） | — | WAF レートリミットのため |

#### 無料枠のうち、設計を直接拘束するもの

| 制限 | 値 | 設計への影響 |
|---|---|---|
| **D1: 1 Worker 呼び出しあたり50クエリ（Free）** | Paid は1,000 | 一括書き込みの1リクエストあたり行数を**テーブルごとに**算出する（詳細設計 3.4）。`player_predictions` を500件で送ると167文必要になり、3倍以上超過する |
| **D1: バインドパラメータ100per文** | — | `max_rows_per_request = floor(100 / 列数) × 40` |
| **Workers: CPU 10ms** | 壁時計ではなく CPU 時間 | 実測で500行のJSONパース＋検証は 1.34ms（Zod で3〜4ms 見込み）。**制約は CPU ではなくクエリ数である**。バッチサイズはクエリ数で決める |
| **Pages: 1デプロイ20,000ファイル** | — | 静的生成の範囲を**直近5シーズン**に限定する（約10,184ファイル、上限の51%）。全10シーズンでは 20,184 ファイルとなり超過する |
| **D1: 1行2,000,000バイト** | — | `model_versions.artifact_text` の**上限を1.5MB とし、登録時にチェックする**。LightGBM のテキストモデルは通常 0.27〜0.70MB だが、early stopping が効かず木が2,000本まで伸びると 1.75MB に達する |

> これらの数値は Cloudflare / Next.js の公式ドキュメントで確認した（2026-09 時点）。`batch()` 内の各文が50クエリ制限にどう計上されるかは公式に記載がなく、**Phase 0（P0-13）で実測する**。

**ISR を使わない。** Cloudflare Pages 上の Next.js は、`next-on-pages` では ISR が動作せず（`revalidate` 指定のルートはビルド時に固定され更新されない）、`@opennextjs/cloudflare` では R2/KV のインクリメンタルキャッシュが必須となり従量課金リソースに依存する。いずれも 4.1 に抵触する。

**主要導線は Workers を経由しない。** バッチが予測JSONを静的アセットとして書き出し、Pages が配信する。1日分30KB程度で、更新は1日3回しかない。これにより Workers 枠と D1 読取を一切消費せず、枠枯渇時も当日の予測が表示され続ける。Workers API は日付指定・チーム別・的中率といった動的クエリに限定する。

**Workers Paid（年額約9,000円）へ移行しない。** 上限を超える。

### 8.1 デザイン方向

データ系のレイアウト。数値を主役とし、情報密度を高く保つ。

| 項目 | 仕様 |

| 対応幅 | モバイルファースト。375px で横スクロールを発生させない |
| フォント | システムフォントスタックを既定とする。Web フォントは数字用の1ウェイトのみ（60KB以内） |

### 8.2 画面一覧

| 画面 | パス | 内容 |
|---|---|---|
| 今日の予測 | `/` | 当日の試合と勝率の一覧 |
| 日付別 | **`/schedule/[date]`** | 指定日の試合一覧。**シーズン範囲外は404** |
| 試合詳細 | `/games/[id]` | 試合前: 勝率・予想スコア・根拠・個人スタッツ / 試合後: 実績との対比 |
| 結果 | `/results` | 終了した試合の実績と予測の対比 |
| チーム別 | `/teams/[slug]` | 予測履歴と成績 |
| 的中率 | `/accuracy` | 精度推移、モデルバージョン別比較、較正 |
| このサイトについて | `/about` | 免責、出典、仕組み、**個人情報の取扱い、連絡先** |

全ページ共通フッターに免責・出典・`/about` へのリンクを常設する。

**日付別を `/games/[date]` にしない。** 同一階層に `[date]` と `[id]` の2つの動的セグメントを置くことはできない（Next.js の App Router では同じ階層に複数の動的セグメント名を定義できず、ビルドエラーになる）。仮に回避しても `/games/2026-09-22` と `/games/12345` の区別がパス形状に依存し、試合IDが日付形式を取った瞬間に破綻する。**日付別は `/schedule/[date]` に分離する。**

**静的生成の範囲は直近5シーズンとする。** Pages の20,000ファイル上限に対し、1ルートあたり HTML と RSC ペイロードの2ファイルが生成される前提で試算した。

| 静的生成の範囲 | 推定ファイル数 | 上限に対して |
|---|---|---|
| 全10シーズン | 20,184 | **101%（超過）** |
| **直近5シーズン（採用）** | **10,184** | **51%** |
| 直近3シーズン | 6,184 | 31% |
| 今季のみ | 2,184 | 11% |

5シーズンより古い日付・試合は静的生成せず、Workers API からクライアント fetch で表示する（存在しない日付は `notFound()`）。1ルートあたりのファイル数は Next.js のバージョンで変わるため、**CI でビルド後のファイル数を検査し、18,000を超えたら fail させる**（受け入れ基準 A-14）。

### 8.3 情報提示の原則

- 勝率は**必ず両チーム分**を表示する。圧縮カードでも省略しない
- 45〜55% の試合は「ほぼ互角」と表現し、一方的な試合と見た目で区別する
- 「暫定」「確定」「序盤」「更新遅延」の状態を明示する
- 的中率は良い時も悪い時も同じ場所に表示する。**外れた試合を隠さない**
- 個人スタッツ予測には誤差の目安を添える（主要4項目に限定）
- **率（FG%等）は試投数の予測値が閾値未満なら表示しない。** 分数のみを出す
- 個人スタッツは**段階開示**とする。初期表示は主要項目のみ、展開でフルボックススコア
- 専門指標（Brier、較正曲線）は一般向けの言い換えを先に置く
- 一覧カードに的中率を出す場合は**母数を併記する**

### 8.4 状態表示の配置

| 階層 | 対象 | 形式 |
|---|---|---|
| アプリ全体 | 更新遅延 | ヘッダー直下の全幅バナー |
| 試合カード | 暫定 / 確定 / 序盤 | メタ行の右端にバッジ |
| 試合詳細 | 同上 | 勝率ブロック直下に理由の説明文 |

文言例:

- 暫定（詳細）: 「暫定 — 出場選手が未発表のため、直近5試合の出場傾向から推定しています。試合当日の午前中に更新されます。」
- 序盤: 「両チームとも今季4試合しか消化していないため、この予測はまだ精度が安定しません」
- 更新遅延: 「表示中の予測は9月21日 6:02時点のものです。その後の欠場情報は反映されていません。」

### 8.5 空状態

| 状態 | 文言 | 次のアクション |
|---|---|---|
| 試合がない日 | 「9月23日（水）に予定されている試合はありません。」 | 次の試合日へのリンク |
| オフシーズン | 「今シーズンの全日程が終了しました。」 | 的中率ページへの導線 |
| 予測未生成 | 「この試合の予測はまだありません。試合前日の朝に公開されます。」 | — |
| エラー | 「予測を読み込めませんでした。時間をおいて再度お試しください。」 | `/about` へのリンク |

Bリーグは年間の1/3以上がオフシーズンであり、空状態の設計は例外処理ではなく主要画面の一つである。

### 8.6 アクセシビリティ

- 見出し要素で文書構造を作る（試合1件を `article`、対戦名を見出し）
- タブ・ボタンは `button` / `a` で実装し、最低44×44px を確保する
- 確率ブロックに `role="img"` と一文の `aria-label` を与え、内部の数値とバーは `aria-hidden` にする
- 装飾目的で `<s>` `<i>` `<em>` を使わない
- 色だけで情報を伝えない

## 付録A. 用語

| 用語 | 意味 |
|---|---|
| Elo レーティング | 対戦結果から算出する相対的なチーム強度指標 |
| Brier Score | 確率予測の精度指標。0に近いほど良い |
| ECE | 予測確率と実際の発生率の乖離。等頻度10ビンで算出 |
| Four Factors | eFG%、TOV%、ORB%、FTレートの4指標 |
| ポゼッション | 攻撃回数の推定値 |
| SHAP | 各特徴量の予測への寄与度を算出する手法。ログオッズ空間の値 |
| データリーク | 予測時点で未知の情報が特徴量に混入すること |
| 暫定 | 出場者未確定の状態で算出された予測 |
| freeze | 試合開始をもって予測を確定し変更不可とすること |
| ハードルモデル | ゼロ過剰な分布を「発生するか」と「発生した場合の量」に分けて扱うモデル |

ST と BS は1試合あたり平均0.7回程度であり、MAE が平均値と同水準になる。これは「その選手の平均を出しているだけ」の状態であり、表示はするが誤差目安を併記して誤認を避ける。

**的中率 71% / Brier 0.186 は、運の良い1シーズン（n=300程度）なら出うるが、複数シーズンの walk-forward で安定する水準ではない。** これを目標として掲げないこと。
