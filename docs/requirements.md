## 1. 背景と目的

### 1.1 背景

2026-27シーズンより B.LEAGUE は新体制へ移行し、B.LEAGUE PREMIER / B.ONE / B.NEXT の3リーグ構成となった（開幕: 2026年9月22日）。昇降格制度の変更に伴いクラブ構成も再編されている。

B.LEAGUE には一般公開されたデータAPIが存在せず、ファンが試合前に「どちらが勝ちそうか」を定量的に知る手段が乏しい。既存のスタッツサイトは実績値の集計が中心で、試合前の予測を継続的に提示し、かつその的中率を検証可能な形で公開しているサービスは見当たらない。

### 1.2 目的

過去の試合データから統計的に勝敗確率・予想スコア・個人スタッツを算出し、その根拠とともに提示する。同時に、自らの予測精度を隠さず公開することで、検証可能な予測ツールとして信頼を得る。

**このプロダクトの差別化は予測精度の絶対値ではなく、確率の較正の正確さ（「70%」と出した試合が実際に約70%勝つこと）と、判断根拠の一貫性にある。**

### 1.3 スコープ外（明示的に扱わないもの）

- 金銭・ポイントを賭ける機能、およびそれに類する一切の要素
- ブックメーカーのオッズの参照・表示、および外部リンク
- **賭博・ギャンブル事業者の広告掲載、およびこれらとのアフィリエイト契約**
- 公式サイトから取得した記事本文・画像・ロゴの転載
- **取得した生HTMLのリポジトリへのコミット**（4.5.2 参照）
- 取得した生データの一括配信・公開API化
- B.ONE / B.NEXT の試合（v1では対象外）

## 2. プロダクト定義

### 2.1 プロダクトの性格

**モデル予測型**。統計モデルが予測を算出し、ユーザーは閲覧する。ユーザーが予想を入力する機能、的中を競う機能は v1 に含まない。

### 2.2 想定利用者

| 利用者像 | 利用シーン | 求めるもの |
|---|---|---|
| B.PREMIER のファン | 試合当日の朝・移動中 | 今日の試合がどうなりそうか |
| 特定クラブのサポーター | 試合前日〜直前 | 推しチームの勝算と、その根拠 |
| データ好きのバスケファン | 随時 | モデルの精度、どの要素が効いているか |

利用者の大半は統計の専門家ではない。専門用語をそのまま画面に出さないこと。

### 2.3 提供価値

### 4.2 性能

測定条件を伴わない目標は検証できないため、以下のとおり定義する。

| 指標 | 目標 | 測定条件 |
|---|---|---|
| LCP | 2.5秒以内 | モバイル4G相当 / p75 |
| INP | 200ms以内 | p75 |
| CLS | 0.1以内 | p75 |
| API応答（キャッシュミス） | 300ms以内 | Workers内計測 / p95 |
| API応答（キャッシュヒット） | 50ms以内 | p95 |
| 日次バッチ | 15分以内 | p95 |
| 初期JS | **180KB以内** | gzip後。下記の測定に基づく |
| 総転送量（初回） | 250KB以内 | gzip後 |

日次バッチ15分の内訳予算: 依存セットアップ2分 / スクレイピング3分 / D1 I/O 2分 / 推論3分 / 予備5分。

**初期JS の上限は実測に合わせて 180KB とした（v1.12）。** 旧版は 120KB だったが、7章が指定する Next.js 16 / React 19 の App Router では、**クライアントコンポーネントと `next/link` を外しても初期JS が 169KB（gzip）ある**（工程11a の実測。`verification/RESULTS.md`）。アプリ側の書き方では下がらず、120KB を維持するにはフレームワークの変更が必要で、それは静的出力・ルーティング・画面設計の前提をすべて書き換えることになる。

**代わりに次を維持する。** 総転送量（初回）250KB以内、LCP 2.5秒以内、INP 200ms以内。ロゴ・写真・Webフォント（数字用1ウェイトを除く）を使わないため LCP 要素はテキストであり、JS は描画をブロックしない。チャートライブラリ・日付ライブラリ・状態管理ライブラリを入れない方針（CLAUDE.md）も維持する。**上限は CI で検査する**（基本設計 7.2）。

**可用性に関する制約**: 無料枠は超過時に課金されず停止するため、枠の枯渇はそのままサービス停止を意味する。Workers の枠は 00:00 UTC（09:00 JST）にリセットされるため、日中に枯渇すると**日本の夕方から夜という最も価値のある時間帯が使えなくなる**。したがって以下を要件とする。

- 主要導線（今日の予測・試合一覧）は **Workers を経由せず静的アセットとして配信**し、枠枯渇時も表示が継続すること
- 公開URLの空間に上限を設けること（日付の範囲外を D1 到達前に打ち切る）
- レート制限を設けること

#### 4.5.2 生HTMLの取扱い（最重要）

**取得した生HTMLをリポジトリにコミットしてはならない。**

個々のスコアや日程に著作物性は認められにくい一方、**HTMLページそのものは事実データではない**。ページ内のテキスト表現、見出し、ナビゲーション文言、レイアウト構造を含む一体としてのページは著作物として保護されうる。これを public リポジトリに置くことは複製（著作権法21条）および公衆送信（23条1項）に当たり、「事実データだから」という本プロジェクトの立論が**一切通用しない唯一の行為**である。情報解析目的の利用（30条の4）も、リポジトリでの再配布には適用が困難である。

したがって、

- 取得したHTMLはローカルの gitignore 対象ディレクトリにのみ置く
- パーサのテスト用フィクスチャは、**構造のみを模し、値をダミーに置換した合成データ**とする。実サイトの文言・記事・画像参照を残さない
- **ボックススコアは `<script>` 内の埋め込みJSONで配信される**（Phase 0 で確認）。取得した本文を生のままコミットしない点は HTML と同じであり、fixture も合成データとする
- `.gitignore` に `**/fixtures/**/*.html` と `**/fixtures/**/*.raw.json` を含める
- CI で fixtures に実サイト由来の文字列が混入していないことを検査する

名称は **Phase 0 完了時までに確定**させ、J-PlatPat（無料）で第9類・第41類・第42類の類似商標を検索する。`B.` プレフィックスとリーグ名の直接的な組み合わせは避ける。

**フッターの著作権表示がこの名称を権利者名として公開している**（2026-10-06 から。
`© 2026 B.PREDICT`。8.2）。**運営者はこの節のリスクを承知のうえでこの名義を選んだ。**

##### 名称を `B.PREDICT` で確定した（2026-10-08。運営者の指示）

**画面から「（仮称）」を外した。** ヘッダーの札と、全ページの `<title>` にあった
`B.PREDICT（仮称）` を `B.PREDICT` に変えた。**U-01 はこれで解決とする。**

**ただし J-PlatPat の検索（P0-8）は済んでいない。** 11章の記録のとおり、
**この調査は運営者にしか実行できない**（本プロジェクトから外部の商標データベースを
引けない）。**したがって本節のリスクは一つも消えていない** — 不正競争防止法
2条1項1号・2号、商標法4条1項15号、App Store Review Guideline 5.2 のいずれも、
名称を確定させたことによって評価が変わるものではない。

| 変わったこと | 変わっていないこと |
|---|---|
| 画面に「仮称」と出さない | **商標の調査が未了である**（P0-8 / R-12） |
| U-01（未決事項）を閉じる | 4.5.8 の論点5（弁理士への相談）は残る |

**「仮称」を外すことがリスクを増やすわけではない。** 混同惹起も著名表示冒用も
**名称を使用していること**で成立し、仮称という注記は抗弁にならない。**外した結果
変わるのは、利用者がこの名称を暫定だと読まなくなることだけである。**

**問題を指摘されたときは 4.5.6 の手順に従う**（反論を先にせず、まず止める）。
名称を変える場合は、出典が `web/lib/version.ts` の定数1か所であるため、
**そこを直せば画面・著作権表示・CI の検査がすべて追随する**。

**U-01 で名称が変わったら、著作権表示も連動して変える。** 出典は
`web/lib/version.ts` の1か所で、CI の検査がそこから読んで全ページを照合するため、
**定数を直せば画面と検査の両方が追随する**（直し忘れた側だけが残ることはない）。

### 5.1 取得元と事前調査結果

**B.LEAGUE 公式サイト**からのスクレイピングを一次ソースとする。2026年9月時点の調査結果は以下。

- `robots.txt` に `User-agent: *` の記述はなく、一般クローラーへの制限は設定されていない。`Disallow` は今回の再確認では SEO 解析ボット6種を対象とし、別の2種には `Crawl-delay` がある

### 5.2 取得ルール（遵守事項）

1. アクセス間隔は **最低3秒＋ジッタ**。並列取得は行わない
2. User-Agent に識別可能な名称と連絡先URLを含める
3. 取得は必要最小限のページに限る。全ページクロールは行わない
4. 初期の一括取得（過去シーズン分）は複数日に分割して実行する
5. **1日あたりの総リクエスト数に上限（3,000）を設け、クライアント側で強制する**
6. 取得したHTMLは保存せず、抽出した数値データのみを保持する
7. **レスポンスサイズに上限（5MB）を設け、超過時は中止する**
8. 429 / 503 応答を受けた場合は取得区間を即座に中止し、同じUTC日には再試行しない。照合・推論等の内部処理は継続する
9. **`robots.txt` と利用規約をバッチ実行のたびに取得してハッシュ照合し、変更があればジョブを中止して人間の確認を求める**

| 大会区分 | 扱い | 理由 |
|---|---|---|
| リーグ戦（B1リーグ / B.PREMIER） | **取り込む**（`REGULAR`） | — |

| オールスターゲーム | 取り込まない | 選抜チーム同士の対戦であり、`clubs` に存在しないチームが現れる。Elo に混入すると全チームのレーティングが歪む |

**不戦敗は学習データに入れない。** 2022-23 の `500609`（2023-04-12 滋賀 対 名古屋D）は、
名古屋の選手4名がインフルエンザ、2名が負傷でエントリー要件を満たさず、**B リーグ規約
第57条第1項により 0–20 の不戦敗**として処理された。公式は試合数に計上し、得失点差を
20減算する。

**公式の成績としては正しいが、予測の入力としては歪む。** 実際にプレーしていないため、
得点差20をそのまま Elo の `multiplier` に通すと、**実力差の証拠がないのにレーティングが
大きく動く**。得失点差の移動平均（#04）も同じである。

| 用途 | 扱い |
|---|---|
| 学習・特徴量・Elo | **入れない**（取り込み自体を行わない） |
| 記録 | **`batch/exclusions/excluded_games.json` に残す。** 試合ID・日付・両クラブ・得点 |
| 画面 | **後で注釈として出す** — 「これらの試合は学習データに含めていない」 |

**取り込まない帰結を承知しておく。** その日の試合一覧にこの試合が出ず、当該クラブの
勝敗数と得失点差が公式の順位表と食い違う。注釈で補う。

**検出は「状態欄が空 ＋ 得点欄に値がある」で行い、点数は条件にしない。** `20–0` を
条件にすると、規約が別の点数を定める場合や、別の理由による不成立を取りこぼす。
**件数は実行結果に出し、一覧には必ず残す** — 静かに消えるのは、この設計が最も避けたい
壊れ方である。

**`event` の値だけでは絞り込めない（2026-09-22 の実測で判明）。** `event=2` は
「そのシーズンの日程」であり、リーグ戦だけでなく**チャンピオンシップ・オールスター・
国際試合を含む**。2016-17 の実データでは、`event=2` の555試合の内訳が
リーグ戦540（18クラブ × 60試合 ÷ 2）＋ チャンピオンシップ15 で、さらに
`EAST ASIA CLUB CHAMPIONSHIP`（`川崎` 対 `安養KGC`）と `ALLSTARGAME2017`
（`B.BLACK` 対 `B.WHITE`）の2試合が混ざっていた。

したがって取り込みは次の3段で絞る。

1. **`event=3`（チャンピオンシップ）を先に辿る。** ここに出た試合IDを `PLAYOFF` として確定させる
2. **次に `event=2` を辿り、既に出た試合IDを飛ばす。** 残りが `REGULAR` である。
   先に CS を確定させないと、`competition` が `REGULAR` で上書きされる
3. **ボックススコアの `TeamID` が `club_source_ids` で解決できない試合を飛ばす。**
   選抜チーム・海外クラブ・下位リーグが該当する。飛ばした件数と、解決できなかった
   IDは必ず出力に出す（黙って捨てると、規則が壊れたときに気づけない）

**クラブ名で絞り込まない（v1.15 で変更）。** 旧版は「その年度のクラブ一覧（日程ページの
`select[name=club]`）にない名前を飛ばす」としており、「改称は選択肢側も当該年度の名称に
なるため、この規則で実在の試合を取りこぼすことはない」と書いていた。**この前提は偽
だった。** 2020-21 の実データでは、**行が略称（`千葉J` / `横浜BC`）、選択肢が正式名称
（千葉ジェッツ / 横浜ビー・コルセアーズ）**で一致せず、**実在する128試合を落としていた**
（クラブ一覧の件数は20で正しく、名前だけが食い違っていた）。

`TeamID` はシーズン・改称・リーグ再編をまたいで不変であり（Phase 0 で確認）、略称にも
表記ゆれにも影響されない。**取り込みのクラブ解決は元から `TeamID` で行っている**ため、
絞り込みだけが名前に依存していた。

この変更で、除外する試合（オールスター等）のボックススコアを1回取得することになる。
**シーズンあたり1〜2件**であり、5.2 の「取得は必要最小限のページに限る」に対する増分は
無視できる。

区分は `games.competition` として保持する（詳細設計 1.3）。**取り込み段階で絞り、かつ列でも区別する。** 絞り込みは成績に直結しない試合を DB に入れないため、列はリーグ戦とチャンピオンシップを区別するためであり、役割が違う。区別を捨てると特徴量 #17（順位・プレーオフ争いの状況）が算出できない。

**同じレスポンスに含まれていても取得しないもの。** ボックススコアの埋め込みJSONには、予測に使わないデータが同梱されている（Phase 0 で確認）。**必要なフィールドだけを抜き出して保存する。**

| 同梱されているが取得しない | 理由 |
|---|---|
| 審判名（主審・副審） | 特徴量 #30 は見送り。人物の個人情報でもある |
| プレイバイプレイ（1試合700件規模） | 予測に使わない。取得は必要最小限に限るという 5.2 の方針に反する |
| シュートチャートの座標 | 同上 |
| `EFF` / `EFG` / `TS` / `USG` 等の導出値 | カウントから導出できる。冗長に持つと不整合の余地が生まれる |

**取得値の検証**: パーサは必須項目の有無だけでなく、値域と恒等式も検証する。`pts` 0–250、`minutes` 0–60、`fga >= fgm`、`fga = 2fga + 3fga`、`pts = 2fgm × 2 + 3fgm × 3 + ftm`、`reb = oreb + dreb`、`f` 0–5（ないし6）、`attendance <= capacity × 1.2`。範囲外・恒等式違反は当該試合をスキップする。**スクレイピングは入力が信用できないパイプラインであり、異常値が Elo 計算に流れ込むとレーティング全体が破壊される。**

**Phase 0 の検証項目に追加**: `FD`（被ファウル数）と `2FGM/2FGA` が試合ごとのボックススコアとして取得可能か（用語集には定義があるが、個別試合ページでの公開は別途確認が必要）。取得できない場合は該当項目を予測対象から外す。

### 5.4 学習データ範囲

- 対象リーグ: B.LEAGUE PREMIER（前身の B1 を含む）
- 期間: 取得可能な全シーズン
- 想定規模: 試合 約8,000件、選手別スタッツ 約20万行

**分布シフトへの対応**（6.6 参照）: 全シーズンを一様に扱わない。観客制限期間の扱い、時間減衰重み、昇格クラブの初期値を個別に設計する。

### 5.5 出場者情報の扱い

| タイミング | 処理 |
|---|---|
| 試合前日まで | 直近の出場傾向から推定し、`暫定` フラグを立てる |
| 試合当日（複数回） | エントリー情報を取得。確定すれば `暫定` を解除 |

| 出力 | 形式 | モデル |
|---|---|---|
| 勝敗確率 | ホーム/アウェイの百分率 | **全特徴ロジスティック回帰**（v1.25。二値分類と点差回帰の両方を実装して比較し、A-09 を満たす唯一の構成を採った。6.1.1） |
| 予想スコア | 両チームの得点（整数） | **勝率（→得点差）と合計得点の回帰から導出**（v1.25。6.1.1） |
| 個人スタッツ | フルボックススコア（6.8） | ハードルモデル＋レート回帰＋チーム整合化 |
| 判断根拠 | 要因グループ別の寄与 | SHAP を4〜5グループに集約 |

**勝率と予想スコアは構造的に整合させること。** 独立した2本の回帰で各チーム得点を予測すると、「ホーム68%」なのに「82–85でアウェイ勝ち」という出力が原理的に起こる。接戦ではほぼ確実に発生し、試合詳細画面で両者が並ぶため直接ユーザーに見える。得点差（margin）と合計得点（total）を予測し、`home = (total + margin) / 2`、`away = (total - margin) / 2` とすれば整合が保証される。

**勝率の導出経路は2つあり、v1 では両方を実装して Phase 0（P0-11）で比較する。**

| 経路 | 内容 | 長所 | 短所 |
|---|---|---|---|
| A: Winner 直接 | 二値分類の出力をそのまま勝率とする | logloss を直接最適化するため較正が良い | Margin 予測と符号が食い違いうる |
| B: Margin から導出 | `P(home) = Φ(margin / σ)`、σ は残差標準偏差 | 勝率と予想スコアが定義上一致する | 残差が正規でない場合に較正が崩れる |

**σ の値は決め打ちしない。** 12〜13点というのは他リーグからの見当であって本データの実測値ではない。**P0-11 で walk-forward の残差から実測し**、`model_versions.margin_sigma` に記録する。実測前に定数として書かない。

**実測した（2026-10-02）。σ = 12.93点**（out-of-fold の残差。全11シーズン / n=3,031）。見当は当たっていたが、**当たっていたことも測るまで分からなかった。** 実装は σ に既定値を持たず、正の有限値でなければ例外を投げる（`batch/model/train_score.py`）。

**比較の結果、経路B を採用する。**

| 経路 | Brier | Accuracy | ECE | Elo単体との差（95%CI） |
|---|---:|---:|---:|---|
| A: Winner 直接 | 0.2020 | **0.6895** | **0.0201** | +0.0008（−0.0012〜+0.0028） |
| **B: `Φ(margin / σ)`（採用）** | **0.2013** | 0.6866 | 0.0265 | +0.0014（−0.0006〜+0.0034） |

B − A = **−0.0006** で、上の判定基準のどちらの枝でも B になる。**A は Accuracy と ECE で上回っているが、Accuracy は採用ゲートに使わず（6.4）、ECE はどちらもノイズフロアの閾値の内側である。** B を採ると勝率と予想スコアが定義上一致するため、`test_win_prob_and_score_agree` で矛盾を検出して丸める運用が不要になる。

**予想スコアの実測**（同じウィンドウ）。

| 指標 | 実測 | 見立て |
|---|---:|---|
| **チーム得点 MAE** | **8.84点** | 付録B「8〜10点」 |
| 得点差 MAE | 10.27点 | — |
| 合計得点 MAE | 14.17点 | — |

**得点差の MAE と混同しない。** 6.4 と付録B が言う「予想スコアの MAE」はチーム得点である。

比較は同一の walk-forward ウィンドウで Brier と ECE を測って行う。

**判定の順序**（v1.25 で1段目を追加した）。

1. **受け入れ基準 A-09 を満たす経路だけを候補にする。** 品質ゲート（12章）は
   A-09 を絶対条件にしており、**これを満たさない経路は選べない**
2. 候補が2つ残ったとき — B の Brier が A より 0.003 以上悪ければ A、差が 0.003 未満なら
   整合性を優先して B
3. 候補が1つなら、それを採る

**1段目を後から足したのは、規則と品質ゲートが実際に衝突したからである**（下記 v1.25）。
旧版は2段目だけを書いており、**A-09 を満たさない経路を規則が強制しうる**状態だった。

どちらを採用したかは `model_versions.win_prob_source` に記録し、`/about` の
「予測の仕組み」に反映する。

予想スコアの MAE は現実的に8〜10点であるため、**小数第1位まで表示しない**（精度の誤認を招く）。

### 6.1.1 勝率モデルを全特徴ロジスティック回帰にし、予想スコアを勝率から導く（v1.25）

**上の P0-11 の結論（経路B）を覆す。** 理由は A-09 であり、根拠は実測である
（n=3,031 / 22列 / 同一 walk-forward / `verification/RESULTS.md`）。

| モデル | Brier | Elo単体との差 | 95%信頼区間 | **A-09** |
|---|---:|---:|---|---|
| **全特徴ロジスティック回帰（採用）** | **0.198699** | **+0.004045** | **[0.00182, 0.00617]** | **満たす** |
| LightGBM（旧 経路A） | 0.201241 | +0.001503 | [−0.00076, 0.00370] | 未達 |
| 旧 経路B（`Φ(margin/σ)`） | 0.200807 | +0.001937 | [−0.00005, 0.00394] | 未達 |

**A-09 を満たすのは1つだけである。** したがって上の判定の順序により、
**勝率は Winner モデル直接（経路A）**とし、**Winner モデルの実装を LightGBM 二値分類から
全特徴ロジスティック回帰に変える**。

**旧 経路B は信頼区間の下限が −0.000045 で、わずかに 0 を跨いだ。** 惜しいが未達は
未達であり、ゲートを緩めない（6.5「検出力を上げるためにゲートを緩めてはならない」）。

#### 予想スコアは勝率から導く

経路A を採ると勝率と予想スコアが別のモデルから出るため、**符号が食い違う**。
実測で **142 / 3,031試合（4.7%）**、加えて丸めて同点になる試合が 167件（5.5%）あった。
際どい試合が多いが、**勝率 12.3%（アウェイ優勢）なのにスコアはホーム勝ちという例もある。**

旧版はこれを「勝率側を正としてスコアを丸める」としていたが、**丸め方を定めていなかった**。
代わりに**向きを逆にする** — 予想スコアを勝率から導けば、食い違いは原理的に起きない。

```
margin = σ · Φ⁻¹(p)          p は勝率（[0.05, 0.95] にクランプ済み）
total  = Total 回帰の出力
home   = (total + margin) / 2        away = (total − margin) / 2
```

**精度は落ちない。むしろわずかに良い**（同じウィンドウの実測）。

| 予想スコアの作り方 | チーム得点 MAE | 得点差 MAE | 符号の食い違い |
|---|---:|---:|---|
| Margin 回帰から（旧） | 8.839 | 10.257 | **4.7%** |
| **勝率から導く（採用）** | **8.832** | **10.214** | **0件（構造的）** |

2つの得点差の相関は 0.97 で、**ほぼ同じものを別の経路で出していた**。

**Margin 回帰は引き続き学習する。** σ（out-of-fold 残差の標準偏差）を出すために必要で、
σ は「勝率 → 得点差」の変換係数そのものになる。`model_versions.margin_sigma` に記録する。

**Total 回帰も引き続き必要である**（合計得点は勝率から導けない）。

#### A-11 は構造的に満たされる

勝率と予想スコアが同じ値から出るため、`test_win_prob_and_score_agree` は
**実装の検査から構造の検査に変わる**（丸めの運用は不要になる）。

#### 較正器は引き続き入れない

全特徴ロジスティック回帰の ECE は **0.0221**（22列。同じウィンドウ）で、
ノイズフロア95%点 × 1.5（約 0.042）の内側である。6.7 の「logloss を目的関数に
するモデルは元々ほぼ較正されている」は、**ロジスティック回帰にはそのまま当てはまる**
（LightGBM への当てはめより素直である）。**モデルを差し替えたら測り直す**規定は維持する。

#### 6.2.1 観客動員の扱い

当該試合の観客数は試合前に未知であるため、そのままでは特徴量に使用できない。以下の変換を経て使用する。

**SHAP で上位に出ても、因果として画面に表示しないこと。** 動員数は強さの代理変数であり、「動員が多いから勝つ」という表示は誤った因果をユーザーに伝える。

### 6.3 データリーク防止（絶対原則）

**特徴量は「試合開始時点で確定している情報」のみで構成すること。**

- 特徴量関数は必ず `as_of` を引数に取り、参照クエリに絞り込みを含める
- 当該試合の `team_game_stats` / `player_game_stats` / `games.attendance` を参照しない
- 試合後にしか判明しない値は、必ず「過去試合の集計」に変換してから使用する
- 検証は時系列分割で行う。ランダムシャッフル分割は使用しない
- 特徴量生成時のスナップショットを予測レコードに保存する

**注意**: 試合終了時刻がスキーマにないため、`tipoff_at` で絞ると「17:05開始・19:05終了の試合」が「19:05開始の試合」の特徴量に確定情報として混入する。**絞り込みは試合終了時刻で行うこと**（`finished_at` を追加する）。

`finished_at` は**列として保持する**（読み出し時に計算しない）。すべてのリーク判定クエリがこの値を通るため、計算式が呼び出し側に散ると、一箇所直し忘れただけでリークが復活する。取り込み時に実測値を入れ、取得できない場合は `tipoff_at + 2時間` を書いたうえで `finished_at_is_estimated = 1` を立て、推定値であることを区別できるようにする。

また、**本番とバックテストでデータ鮮度が一致することを保証する必要がある**。本番の日次推論は最大7日前の情報で予測するが、バックテストでは全試合がDBに揃っているため開始直前の情報が使える。同じ関数を呼んでいても入力が違い、検証スコアが体系的に過大評価される。これは「リーク」と呼ばれずに見逃される種類のバイアスであり、`predictions` に推論実行時点のデータ鮮度（`data_as_of`）を記録して検証する。

### 6.4 評価指標とベースライン

| 指標 | 用途 |
|---|---|
| Brier Score | **主要な改善指標**。確率予測の質。採用ゲートはこれで判定する |
| Accuracy | **表示専用**。一般向けに公開する「的中率」。**採用ゲート・モデル比較・アラートのいずれにも使わない** |
| Log Loss | 学習時の目的関数 |
| ECE（等頻度10ビン、ビンあたり最低50サンプル） | 較正誤差。**n ≥ 500 のときのみゲートに使う** |
| MAE | 予想スコアの誤差 |

#### ECE の閾値は固定値にしない（検証済み）

**ECE は完全に較正されたモデルでもサンプリングノイズだけで有限の値を取り、その大きさは n に依存する。** 固定閾値 0.05 は小標本では良いモデルを落とし、大標本では素通りする。

真の確率を知る完全較正モデルで4,000回シミュレーションした実測値:

| n | 1ビンの件数 | ECE 平均 | ECE 95%点 | 固定閾値 0.05 の挙動 |
|---|---|---|---|---|
| 200 | 20 | 0.0824 | 0.1163 | 完全なモデルでも落ちる |
| 500 | 50 | 0.0518 | 0.0734 | 半々 |
| 1,200 | 120 | 0.0337 | 0.0479 | ほぼ常に通過 |
| 3,000 | 300 | 0.0212 | 0.0299 | 常に通過 |

したがって閾値は次のように定める。

- **n < 500 のとき、ECE をゲートに使わない**（1ビン50件を満たさず、値がノイズに支配される）
- **n ≥ 500 のとき、`ECE < max(ノイズフロア95%点 × 1.5, 0.01)` をゲートとする。** ノイズフロアは「そのモデルの予測確率分布」からブートストラップで毎回推定する（上表は一様分布での参考値であり、そのまま定数化しない）
- 推定には `verification/01_ece_noise_floor.py` を用いる

#### 下限 0.01 を置く理由（v1.32。運営者の判断）

**ノイズフロアは標本が大きいほど小さくなるため、大標本では到達不能になる。**
上の表は n=3,000 までしか想定しておらず、**第1段（PlayerAvail）が初めて
n を10万規模にしたときに破綻した**（2026-10-05 の実測。`verification/RESULTS.md`）。

| テストの n | ECE | 閾値（下限なし） | 判定 |
|---:|---:|---:|---|
| 500 | 0.0147 | 0.0467 | 通る |
| 3,000 | 0.0127 | 0.0187 | 通る |
| 10,000 | 0.0091 | 0.0102 | 通る |
| 30,000 | 0.0066 | 0.0059 | **落ちる** |
| **124,927** | **0.0089** | **0.0029** | **落ちる** |

**同じモデル・同じ予測である。** 判定を反転させたのは標本の大きさだけで、
**ECE は n が増えるほど良くなっている**（0.0147 → 0.0089）のに閾値がそれより
速く縮む。これは「良いモデルを落とす」方向の誤りであり、6.4 が固定閾値 0.05 を
捨てた理由（小標本で良いモデルを落とす）と**同じ種類の誤りが反対側で起きている**。

**下限の意味は「確率の目盛りのずれが1ポイント以内なら良しとする」である。**
完全に較正されたモデルでも n=1,200 で ECE 95%点は 0.0479 であり（上表）、
**0.01 は設計が想定した標本規模に対しては十分に厳しい水準**である。

**勝敗モデルの判定は変わらない。** n=3,031 では `max(0.042, 0.01) = 0.042` で、
**下限はノイズフロアが1ポイントを下回った大標本のときだけ効く。**

**固定閾値に戻したのではない。** 6.4 が退けたのは「n に依らない単一の閾値」で
あって、**n 依存の閾値に下限を添えること**ではない。小標本では引き続き
ノイズフロアが閾値を決める（n=500 で 0.0467）。

> この表は `verification/01_ece_noise_floor.py` で再現できる。

**ベースラインは3段で持つ。**

1. ホームチームが必ず勝つ（Accuracy の比較用）
2. **Elo差単体のロジスティック回帰**（**A-09 の相手。これは変えない**）
3. **LightGBM**（v1.25 で入れ替えた。下記）

**2 を Brier で有意に上回れなければ、本番モデルを使う理由がない。**

**3段目を「全特徴のロジスティック回帰」から「LightGBM」に入れ替えた（v1.25）。**
全特徴ロジスティック回帰が**本番モデルになった**ため（6.1.1）、ベースラインには
残れない。入れ替えた相手が LightGBM であるのは、**実測で 2 を有意に超えられず
（+0.0015 / CI が 0 を跨ぐ）本番にできなかった**からである — 旧版が
「2 を超えられなければ LightGBM を使う理由がない」と書いた条件に、LightGBM 自身が
当たった。

**段の役割は変わっていない。** 1 は Accuracy の比較用、2 は A-09 の相手、
3 は本番モデルの対抗馬である。

**Accuracy を採用ゲートにしない理由**: Accuracy の差は統計的に識別できない。理想モデル（真の勝率を知る上限）とベースラインの差の標準偏差は n=200 で 0.041 あり、`+0.03` という基準は 1SD の内側に収まる（下表）。**ホーム勝率が何%であれ、この検出力の問題は変わらない。**

**旧版はここに「ホーム勝率が約60%なら Accuracy はベースラインとほぼ並ぶ」という根拠も併記していたが、実測で前提が外れた。** B1 のリーグ戦4シーズン（n=1,829）の実測は **52.7%** で、平均得点差は **+1.41点**にとどまる（`verification/RESULTS.md`）。ベースラインが弱いぶん Accuracy には余地があり、「並ぶ」は成立しない。**結論（Accuracy をゲートにしない）は上記の検出力の根拠だけで維持できる。**

### 6.5 モデルの採用基準

新モデルは以下をすべて満たす場合のみ有効化する。

1. **評価サンプル数が n ≥ 500**（この下限を満たさない場合、いかなる比較も行わず現行モデルを継続使用する）
2. **同一の評価ウィンドウ**（直近2シーズンを対象とした walk-forward）で再評価した Brier が現行モデルより良い
3. その差が**有意かつ実質的**であること — 試合ごとの Brier 差のブートストラップ信頼区間（95%）が0を跨がず、**かつ**点推定の差が **0.003 以上**（最小実質差）
4. ECE が 6.4 の n 依存閾値を満たす（n < 500 ではこの条件を課さない = 条件1により到達しない）。**ただし「確率を画面に出さず、用途が相対比だけ」のモデルには課さない**（下記）
5. **欠損率30%を超える特徴量が存在しない**

#### 条件の射程 — **回帰モデルには条件2〜4 を課せない**（v1.34）

**この5条件は Brier と ECE で書かれている。** どちらも確率予測の指標であり、
**得点差・合計得点・試投数・出場時間・レートを出す回帰モデルには定義されない。**

| モデル | 条件2〜4 |
|---|---|
| 勝敗（WINNER） | 課す |
| 出場するか（PlayerAvail） | 課す（**条件4 は上記の例外**） |
| **MARGIN / TOTAL / TeamRate 14本 / PlayerMinutes / PlayerRate 14本（計30本）** | **課せない** |

**MAE に対する「最小実質差」を本書は定めていない。** 条件3 の 0.003 は Brier の
値であり、点（MAE 8.8点）や分（MAE 4.3分）や試投数に流用できる数ではない。
**ここで発明しない。**

**課すのは条件1（n ≥ 500）と条件5（欠損率）、および詳細設計 4.6 の条件6
（想定外の定数列がない）である。** いずれも指標の種類に依らない。

**帰結を承知しておく。** 学習しないベースライン（「直近の水準をそのまま出す」）に
負ける回帰モデルも有効化される。実際に2本がそうであり、**運営者はこれを承知の
うえで「モデルのまま出す」と決めた**（6.8.1）。**比較の結果は
`model_versions.notes` に必ず残す** — 門にはしないが、どのモデルが学習に値したのかは
後から辿れるようにする。

**30本は勝敗モデルの判定に連動する。** 勝敗が採用されたときだけ33本をまとめて
有効化し、1つでも落ちたら1本も登録しない（詳細設計 4.5.1）。個人スタッツは
チーム予測に整合化してから保存するため（6.8.5）、**一部だけ世代を入れ替えると
整合化の両側が別のモデルから出る。**

#### 条件4の例外 — 確率を画面に出さないモデル（v1.33。運営者の判断）

**第1段（PlayerAvail。選手が出場するか）には条件4を課さない。** 2026-10-05 の
実測で ECE 1.42ポイント（閾値 1.0）であり、較正器（Platt scaling）を入れても
改善しなかった。**較正器が有害なのではなく、ゲートを通すには足りない**
（Brier は 0.043001 → 0.042810 と改善する）。

**課さない根拠は「この確率が画面に出ず、用途が相対比だけである」ことである。**

| 用途 | 目盛りのずれが効くか |
|---|---|
| `P(出場) < 0.5` の選手を表示しない（6.8.4） | **効かない。** 50%のどちら側かだけを見る |
| 整合化の期待出場時間（`m_i = P(出場_i) × E[MIN_i]`） | **ほぼ効かない。** 5人の合計を200分に正規化するため、**全員が同じ方向にずれていれば打ち消える** |

2つ目は実測の裏付けがある — 当てはめた較正器の**傾きが 0.98〜0.99 でほぼ 1**
であり、ずれは「全員まとめて少しずらす」型（ロジット空間のほぼ平行移動）である。

**この確率を画面に出すことになったら、課し直す。** 表示するなら「70% と出した
選手が実際に約70%出場する」ことを保証しなければならず、それは 1.2 が掲げる
較正の正確さそのものである。

**例外の射程を広げない。** 対象は**確率を画面に出さないモデル**に限る。
勝敗確率（WINNER）は画面の主役であり、**例外に含めない**。ECE が通らないのに
採用した事実は `model_versions.notes` に残す。

**他の門は課す。** 標本数（条件1）・現行モデルとの比較（条件2〜3）・
ベースライン超え・欠損率・定数列はそのまま適用する。**Brier の門が残るため、
確率の総合的な質は引き続き見張られている。**

**Accuracy は採用判定に一切使わない。** 「Accuracy が +0.03」といった基準は統計的に識別できない。理想モデル（真の勝率を知る上限）で20,000回試行した実測では、ベースラインとの差の標準偏差は n=200 で 0.041、n=500 で 0.026 であり、`+0.03` は n=200 では 1SD 以内に収まる。理想モデルですら 8.5% の確率で基準を落ちる。

| n | 理想モデル | ベースライン | 差の平均 | 差の SD | `+0.03` を落ちる確率 |
|---|---|---|---|---|---|
| 200 | 0.656 | 0.572 | 0.085 | 0.041 | 8.5% |
| 500 | 0.656 | 0.572 | 0.084 | 0.026 | 1.7% |
| 1,200 | 0.656 | 0.571 | 0.085 | 0.017 | 0.0% |

> この表は `verification/02_acceptance_criteria_power.py` で再現できる。副産物として、理想モデルの精度が 65.6% となり付録B の見立て「64〜68%」と整合することも確認した。

学習条件は必ず再現可能にすること。`seed` / `bagging_seed` / `feature_fraction_seed` / `deterministic` を固定し、`model_versions.params` に記録する。これらを固定しないと、`bagging_fraction` により Brier が ±0.003 ぶれ、**モデルの差し替え可否が実質的に乱数で決まる**。

#### 再学習頻度と検出力の関係（重要な前提）

再学習の頻度は**月次または新シーズン開始時**とする。週に増える試合は約30件（全体の0.4%）で、毎週作り直す統計的理由がない。

ただし、**月次の差し替え判定は検出力が低い**ことを前提として受け入れる。真の差 0.03 を検出できる確率は n=200 で 12.7%、n=1,200 でも 54.8% にとどまる。これは以下を意味する。

- 月次で回しても「ノイズで誤って差し替わる」ことは起きない（上記の厳格ゲートが防ぐ）
- 代わりに「**実際の改善を見逃す**」方向に倒れる。見逃した改善は次の月次、最終的にはシーズン単位の評価で拾う
- したがって月次維持は安全側の選択であり、**ゲートを緩めて検出力を上げてはならない**（それは誤差し替えを招く方向の変更になる）
- 学習コストは毎月発生し続けるため、`monthly_train` の120分タイムアウト管理は必須とする（7章・design-basic 4.1）

### 6.6 コールドスタートと分布シフト

**シーズン序盤**

- Elo の初期値は前シーズン終了時点の値を平均方向へ回帰させた値とする（回帰率は実データで探索。NBAの標準値0.75より強い回帰が適切な可能性が高い）
- 消化試合数が10未満のチームは、当季集計を明示的な縮約式で扱う: `winrate = (w + k × prior) / (n + k)`、k=10、prior は前季勝率の回帰値
- 消化試合数が5未満の場合、画面に序盤である旨を表示する

**昇格クラブ・復帰クラブ**

昇格クラブに Elo 1500（＝旧B1平均）を与えると**大幅に過大評価**する。前季 PREMIER 下位層の水準を初期値にする。

**「前季にトップリーグの試合がないクラブ」はすべてこの扱いにする。** 空白が1シーズンでも8シーズンでも同じであり、過去にトップリーグにいた Elo が残っていても**持ち越さず捨てる**。`SEASON_REGRESSION` を空白シーズン数だけ適用すると偏差が `R^N` に縮んで実質 1500（トップリーグ平均）になり、二部に長くいたクラブを平均と評価することになる。空白シーズン数の閾値は設けない（11シーズンで該当が7件しかなく、推定する検出力がない）。

**B.ONE / B2 時代の Elo は存在しない。** 取得対象はトップリーグ（PREMIER と前身の B1）のみであり（5.4）、下位リーグの試合を取り込まないため Elo も計算されない。v1.7 まで記載していた「B.ONE 時代の Elo があればリーグ間オフセットを推定して平行移動する」という分岐は**永久に発火しないため削除した**。

**B.PREMIER の構成は昇降格の結果ではない。** 2026-27 では `718` 神戸（B1 在籍は 2017-18 のみ、以後8シーズン不在）と `716` 信州（2シーズン不在）が該当する（`verification/RESULTS.md`）。

**観客制限期間（2020-21 / 2021-22）**

約1,500〜2,000試合が無観客または収容制限下で行われている。この期間は**ホームアドバンテージ自体が消失**することが各国リーグで確認されており、固定値での Elo 更新は系統的に歪む。

**ホームアドバンテージの水準は実測で決める。** 旧版は「ホーム勝率60%」を前提に Elo のホームアドバンテージを70点前後と見込んでいたが、**実測 52.7% に対応するのは 18.8点**である（`verification/RESULTS.md`）。探索の範囲は実測値を含むように取る（詳細設計 2.5）。

- `games` に観客制限フラグ（`spectator_restricted`）を持たせる。**取り込み時に判定して列に書く**（特徴量生成時に毎回計算し直さない）
  - `attendance / capacity < 0.2` なら 1
  - `attendance` または `capacity` が NULL なら **NULL（判定不能）** とし、Elo 更新では通常のホームアドバンテージを使う
  - ただし **2020-21 / 2021-22 シーズンは期間指定で強制的に 1 とする**（入場者数が非公開の試合が混じっても取りこぼさないため）
- 該当期間は Elo 更新時のホームアドバンテージを0にする
- 動員系特徴（#29）の集計から除外する

**時間方向の重み**

10年前の試合と先週の試合を同じ重みで学習しない。`weight = exp(-λ × 経過シーズン数)` で λ を walk-forward 上で探索する（半減期3〜5シーズンが出発点）。これはルール変更とリーグ再編の両方に効く。

### 6.7 確率の較正

**較正は out-of-fold で fit すること。** 学習データそのもので fit すると、学習データ上の過剰な分離を「正しい」と学習し、本番では過信が増幅される。しかも較正誤差は学習時には小さく見えるため、採用ゲートも機能しなくなる。

**そもそも較正が必要かを先に測ること。** logloss を目的関数にした LightGBM の出力は元々ほぼ較正されている。較正なしの信頼性曲線を測り、ECE が十分小さければ較正器を入れない。

入れる場合、Isotonic は非パラメトリックで自由度が高く、n=800 程度の較正セットでは裾のブロックが数サンプルになり悪化しうる。**パラメータ2個の Platt scaling を第一候補**とする。較正器も `model_versions` の管理対象に含める。

**測った結果、v1 では較正器を入れない（2026-10-03。運営者の判断）。**

| 経路 | ECE | ノイズフロア95%点 × 1.5 |
|---|---:|---:|
| A: Winner 直接 | 0.0201 | 0.0415 |
| **B: `Φ(margin / σ)`（採用）** | **0.0265** | 0.0415 |

**根拠は「測ったら閾値の内側だった」であって、「構造上そうなる」ではない。** 本節の「logloss を目的関数にした LightGBM の出力は元々ほぼ較正されている」という論は、**採用した経路B には当てはまらない**（B は `Φ(margin / σ)` であり logloss を最適化していない）。実際 B の ECE は A より悪い。

したがって**モデルを差し替えたら測り直す**。`n < 500` では ECE をゲートに使わないという 6.4 の規定も引き続き適用する。

### 6.8 個人スタッツ予測

#### 6.8.1 予測する項目

公式のボックススコア項目（[B.LEAGUE スタッツ用語集](https://www.bleague.jp/glossary/)に準拠）を予測する。**シュート項目は「試投数（カウント）＋成功率（0〜1）」の組で予測し、成功数は導出する。**

| 分類 | 予測する項目 | 形式 |
|---|---|---|
| 出場 | MIN（出場時間） | カウント |
| シュート（試投） | 2FGA / 3FGA / FTA | カウント |
| シュート（成功率） | **2FG% / 3FG% / FT%** | 率（0〜1） |
| リバウンド | OR / DR | カウント |
| プレー | AS / TO / ST / BS | カウント |
| ファウル | F（ファウル数） / **FD（被ファウル数）** | カウント |

上表は15行ある。このうち **MIN は第2段（PlayerMinutes）の出力**であり、**第3段（PlayerRates）の出力は MIN を除いた14項目**（カウント11 + 成功率3）である。以降「14項目」と書いた場合は常に第3段の14項目を指す。

「テイクチャージ」は NBA のハッスルスタッツであり、FIBA 系のボックススコアには存在しない。**FD（被ファウル数）が実質これに相当する。**

**なぜ「成功数」ではなく「成功率」を予測するのか。** 旧版は 2FGM / 3FGM / FTM を成功数（カウント）として予測していたが、これではチーム予測への整合化（6.8.5）が原理的に成立しない。成功数と試投数を独立にスケールすると `成功数 > 試投数` が生じ、それを防ぐためのクリップが収束を壊す。実測では整合化の失敗ケースの **73% が FT 成功率**で発生した。試投数と成功率の組で持てば、成功率をロジット空間でシフトするだけで制約を自動的に満たす（6.8.5）。

これは 6.8.2 の「率を直接予測しない」と矛盾しない。**モデルが出す率は「この選手のこの試合における期待成功率」という連続量**であり、画面に出す `FG% = FGM / FGA` とは別物である。表示する率は必ず導出値であり、分数と併記する（8.3）。モデル出力としての率を単独で画面に出してはならない。

#### 6.8.2 導出する項目（予測しない）

以下はカウントの予測値から計算で求める。独立に予測すると恒等式が崩れる。

| 項目 | 導出式 |
|---|---|
| 2FGM / 3FGM / FTM | `2FG% × 2FGA` / `3FG% × 3FGA` / `FT% × FTA` |
| PTS | `2FGM × 2 + 3FGM × 3 + FTM` |
| FGM / FGA | `2FGM + 3FGM` / `2FGA + 3FGA` |
| TR | `OR + DR` |
| FG%（表示用） | `FGM / FGA` |
| EFG% | `(FGM + 0.5 × 3FGM) / FGA` |
| TS% | `PTS / (2 × (FGA + 0.44 × FTA))` |

**画面に率を単独で出してはならない。** 1試合の試投数は6本程度であり、実績としての FG% は `0 / 16.7 / 33.3 / 50 / 66.7 / 83.3 / 100` しか取りえない離散値になる。ここに「FG% 47.3%」とだけ出すのは、存在しない精度を主張することにあたる。**必ず分数と併記し**（`6.4 / 13.1 (48.9%)`）、試投数の予測値が閾値未満の選手には率を出さず分数のみ表示する（8.3）。

**FG は 2P と 3P の合計として導出する。** FG を予測してから 2P/3P に分解すると `FGM = 2FGM + 3FGM` が成立しない。

**PTS は恒等式で導出する。** 独立に予測すると内訳と合計が食い違う。

#### 6.8.3 予測しない項目

| 項目 | 理由 |
|---|---|
| **＋/－** | チームの結果を個人に帰属させた指標で、1試合の分散が極端に大きい。MAE は 9〜12点規模になり、ほぼ毎回外れて見える。しかも「チーム得点差予測 × 出場時間シェア」以上の情報を持たず、出しても新しいことを伝えない。**実績のみ表示し、予測はしない** |
| EFF | 導出は可能だが、複数項目の誤差が合算されるため予測値としての意味が薄い。実績のみ表示 |

#### 6.8.4 モデル構成

```
第1段  PlayerAvail    P(出場)                          二値分類
第2段  PlayerMinutes  E[出場時間 | 出場]               回帰
第3段  PlayerRates    カウント11項目: 単位時間レート   回帰 × 11
                      成功率3項目: 2FG% / 3FG% / FT%   回帰 × 3（レートではない）
第4段  Reconciliation チーム予測への整合化             計算
```

**カウント11項目（2FGA / 3FGA / FTA / OR / DR / AS / TO / ST / BS / F / FD）は per-minute レートで学習する。** カウントのまま学習すると出場時間の分散に支配される。

**成功率3項目（2FG% / 3FG% / FT%）は per-minute にしない。** 率は時間当たりの量ではないため、per-minute 化は無意味である。目的変数は過去試合の成功率、学習重みは試投数とし、シュリンク（`(made + k × prior) / (attempted + k)`、prior はリーグ平均、k は試投数ベースで探索）を経た値を使う。出力は `clip(0.01, 0.99)` に収める（ロジット変換の定義域を確保するため。6.8.5）。

`P(出場) < 0.5` の選手は**表示対象から除外する**。登録選手の3〜4割が0分であり、単一回帰では欠場濃厚な選手に「8分・4.2点」のような値が出る。

**表示人数（U-05）は「1クラブあたり5人以上」とする**（v1.35。運営者の委任により決めた。
2026-10-05）。これは受け入れ基準 A-01 が求める「規定人数」である。

| 項目 | 値 |
|---|---:|
| 実測（本番相当の33試合 / 66組） | **最小 9人 / 平均 11.4人 / 最大 13人** |
| **A-01 の下限** | **5人** |

**5 は新しい定数ではない。** 6.8.5 が整合化の基礎に「**5人 × 40分 = 200分**」を
置いており、そこにある値をそのまま使う（閾値を推測で増やさない）。

**実測の最小（9人）を下限にしない。** 66組は1日ぶんの窓であり、分布が安定している
と主張できる標本ではない。とくに**季の1試合目は候補集合の recall が 0.5449** しか
なく（詳細設計 2.3.1）、人数が落ちる。A-01 は「当日の `SCHEDULED` 全試合」に課す
基準であり、**開幕日に落ちる下限を置くと品質ゲートが毎季の初日に止まる**。

**5 が意味を持つのは、それがバスケットの最小構成だからである。** 4人以下しか
出せない予測は、画面に出す前に壊れていると分かる（モデルが揃っていない / チーム目標が
到達不能で破棄された / 候補集合が空に近い）。**この3つが A-01 で捕まえたい状態である。**

期待値の積（`E[minutes] × E[pts/min]`）は `E[minutes × pts/min]` と等しくない。出場時間と単位時間生産性は正相関するため、素朴な積は系統的に過小評価になる。第4段の整合化でこれを補正する。

#### 6.8.5 チーム予測との整合化（必須）

**選手ごとに独立して予測した値をそのまま表示してはならない。** 5人の得点合計がチームの予想スコアと一致せず、FGA の合計もチーム予測とずれる。同じ画面に矛盾した数字が並ぶことになる。

##### 予測の持ち方（重要）

シュート項目は**成功数と試投数を独立に予測しない**。「試投数」と「成功率」に分解して予測する。

| 予測する | 導出する |
|---|---|
| `2FGA` `3FGA` `FTA`（試投数、カウント） | `2FGM = 2FG% × 2FGA` など |
| `2FG%` `3FG%` `FT%`（成功率、0〜1） | `PTS = 2FGM×2 + 3FGM×3 + FTM` |

この持ち方により **`成功数 ≤ 試投数` が構造的に保証**される。成功数を直接予測すると、後段のスケーリングで試投数を超えてしまい、クリップが必要になる。

**チーム側の目標値も同じ構造で作る。** 各項目を独立に生成すると、約2%の確率で「FT成功数 > FT試投数」のような実行不能な目標が生まれ、整合化が原理的に成立しなくなる（検証済み）。

##### 前段: チーム目標の整合化（必須）

**TeamRates の出力をそのままチーム目標にしてはならない。** TeamRates（試投数・成功率の回帰）と Margin / Total は別のモデルであり、TeamRates から導出した得点が予想スコアと一致する保証がない。一致しないまま選手側の整合化に渡すと、「選手の合計＝チーム目標」は満たされるが「チーム目標＝画面に出る予想スコア」が崩れ、矛盾の位置が一段ずれるだけになる。

**予想スコアを正とし、チームの成功率を寄せる。** 選手側と同じロジット空間シフトを、チーム目標の生成時にもう1段入れる。

```
S     = (total + margin) / 2        （アウェイは (total - margin) / 2）
l_s   = logit(TeamRates の成功率 s)  （s ∈ {2FG%, 3FG%, FT%}）

pts(d) = 2·σ(l₂ + d)·A₂ + 3·σ(l₃ + d)·A₃ + 1·σ(l_f + d)·A_f

pts(d) = S を満たす共通シフト量 d を brentq で解き、成功率を σ(l_s + d) に置き換える
```

- **σ は単調増加、係数（2 / 3 / 1）と試投数 `A` は非負**であるため `pts(d)` は `d` について単調増加であり、解は一意に存在する。反復は不要（1回で厳密一致する）
- **試投数（`A₂` `A₃` `A_f`）は動かさない。** ペースと配分の予測をそのまま残し、得点の帳尻は成功率だけで合わせる
- 成功率はロジット空間で動かすため `[0,1]` を出ない。**ここでもクリップを使わない**
- `pts(d)` の値域は `(0, 2A₂ + 3A₃ + A_f)` であるため、`S` がこの区間の外なら解が存在しない。その場合は選手側と同じく **`InfeasibleTargetError` を投げる**（無言でクリップしない）。当該試合の個人スタッツ予測を破棄し、チーム予測のみを保存して、画面には算出不能と表示する

この前段を通した値だけを `prediction_team_targets` に保存する。保存された目標値が予想スコアと ±0.5点以内で一致することは受け入れ基準 A-16 で検証する。

##### 整合化の手順

```
1. 期待出場時間       m_i = P(出場_i) × E[MIN_i | 出場]
2. 総出場時間を正規化   m_i ← m_i × 200 / Σ m_i        （5人 × 40分 = 200分）
3. 試投数・その他       x_i,s = rate_i,s × m_i
4. 試投数をチーム目標へ  x_i,s ← x_i,s × T_s / Σ_i x_i,s
5. 成功率をチーム目標へ  ロジット空間で一律シフトし Σ(pct_i × att_i) = T_made を満たす d を解く
                       pct_i ← sigmoid( logit(pct_i) + d )
6. 得点・成功数は導出    PTS_i = 2FGM_i×2 + 3FGM_i×3 + FTM_i
```

**手順5でクリップを使ってはならない。** 成功率を [0,1] の範囲で一律に掛け算すると、1.0 に張り付いた選手が出た時点で合計を目標に合わせられなくなり、反復が振動する。実測では失敗ケースの**73%がFT成功率**で発生した。

ロジット変換は (0,1) を (-∞,∞) に写すため**クリップが原理的に不要**になり、単調性から解が一意に存在する。

```python
def shift_to_target(pct, att, target):
    """sum(pct * att) = target を満たすロジットシフト量を解く。"""
    lo = logit(np.clip(pct, 1e-4, 1 - 1e-4))
    f  = lambda d: (sigmoid(lo + d) * att).sum() - target
    return sigmoid(lo + brentq(f, -50, 50))
```

##### 反復回数と許容誤差

**手順4〜5は1回でよい（v1.20 で 3回から訂正）。** 1,500ケースの検証結果。

| 反復 | 項目誤差 中央値 | 99%点 | 最大 | 得点誤差 最大 |
|---|---|---|---|---|
| **1（採用）** | **0.0000%** | **0.0000%** | **0.0000%** | **0.00000** |
| 2 | 0.0000% | 0.0000% | 0.0000% | 0.00000 |
| 3 | 0.0000% | 0.0000% | 0.0000% | 0.00000 |

許容誤差は**得点 ±0.5点、その他 ±2%**、制約違反0件とする。**実測は全項目で厳密に一致するため、許容に頼らない。**

**なぜ1回で合うのか。** 手順4で各項目の合計を目標に一致させ、手順5は**試投数を触らずに**成功率だけを動かす。したがって2回目の手順4は倍率1、手順5はシフト0になり、結果は完全に同一である。

> **v1.19 まではここに反復3回を定め、「1回 99%点 3.39% / 最大 10.73%、3回 0.27% / 1.87%」という表を根拠にしていた。**
>
> **あの表は `verification/03_reconciliation_logit.py` が `pf` を 5.0 でクリップした状態で測ったものだった** — 詳細設計 2.4 が「`pf` の 5.0 クリップも行わない」と禁じている処理である。同スクリプトの当該行を外して再実行すると全反復で 0 になる（`verification/RESULTS.md`、2026-10-03）。
>
> 併せて、旧版の「残る誤差は手順4と手順5の相互作用による試投数側のずれである」という説明も**誤りだった**（手順5は試投数を触らない）。

旧版の「試投数と成功数を別々に比例スケールして2回反復」は収束しない。同一条件での実測は項目誤差の最大 24.7%、得点誤差 4.42点だった。

延長戦がある場合、総出場時間は 200分ではなく `200 + 25 × 延長回数` になる。予測時点では延長を仮定しない。

> この手順は `verification/03_reconciliation_logit.py` で再検証できる。整合化のロジックを変更した際は必ず再実行すること。

#### 6.8.6 誤差の提示

誤差の目安は「**当該選手の直近N試合の絶対誤差の中央値**」と定義する。モデル全体の平均 MAE を全選手に表示しても意味がない（20点の選手と4点の選手に同じ値を出すことになる）。

**低レートの項目（ST・BS）は、MAE が平均値と同程度になる。** 1試合あたり平均0.7回程度の項目では、予測は実質「その選手の平均を出しているだけ」であり、付加価値がほとんどない。表示はするが、これを隠さず誤差目安を併記する。

誤差目安を全項目に表示すると画面が埋まるため、主要4項目（MIN・PTS・TR・AS）に限定する。

#### 6.8.7 学習コストへの影響

予測対象が14項目（カウント11 + 成功率3）に増えるため、学習時間が延びる。出場確率と出場時間を加えると選手モデルは計16本になる。LightGBM はマルチ出力をネイティブにサポートしないため、項目ごとにモデルを持つことになる（特徴量行列は共通なのでパイプラインは1本）。

- 選手スタッツの学習行数は約20万行
- 16項目 × fold 数の学習が必要
- `monthly_train` のタイムアウトを **120分** に設定する
- **選手モデルの fold 数は3に制限する**（チームモデルは5）

学習時間が枠に収まらない場合、per-minute レートでの学習に切り替え、木をさらに小さくする。

### 6.9 根拠の提示

**勝率モデルがロジスティック回帰になったため、寄与は SHAP ではなく係数から厳密に出る**
（v1.25。6.1.1）。

```
寄与_i = 係数_i × (特徴量_i − 学習データの平均_i)      （ログオッズ空間の加算）
```

**これは近似ではなく恒等式である。** 全寄与の和と切片を足すと、そのままログオッズに
なる。下記の「相関特徴間で SHAP 値が分散し、ほぼ同じ条件の2試合で根拠が入れ替わる」
という問題は、**構造的に消える** — 係数は学習時に1つ決まり、試合ごとに動かない。

**それでも要因グループ単位で表示する**（下記）。理由が変わる — SHAP の不安定さでは
なく、**60〜70列の個別名を画面に出さない**ためである。

**値はログオッズ空間であり、確率への加算ではない。**「寄与 +12%」のような百分率表示は
「勝率を12ポイント押し上げた」と誤読されるため行わない。`%` は勝率専用に予約する。

**個別特徴ではなく要因グループ単位で集約して表示する。** 特徴量は展開すると60〜70列になり、Elo・勝率・得失点差・ORtg・SOS・Four Factors・動員はすべて「チームの強さ」という単一の潜在因子の観測値で相互相関が0.6〜0.9に達する。LightGBM は予測が壊れないが、分割の選択が相関特徴間で分散するため**SHAP 値も分散し、ほぼ同じ条件の2試合で表示される根拠が入れ替わる**。

グループは「チーム力」「日程・疲労」「選手」「会場」の4〜5とし、グループ内の SHAP を合算する。

**表現の規約**: 根拠ラベルに**選手個人の能力・資質・人格に対する評価を含む表現を用いない**。使用するのは公式記録から機械的に導かれる事実の記述に限る。

- 可: 「直近5試合の平均得点」「出場時間の減少」「欠場による影響」
- 不可: 「不調」「衰え」「戦力外」「期待できない」「使えない」

#### 文言は「代表1項目の事実」を出す（v1.28。運営者の判断）

グループ名と有利な側だけを出すと「チーム力の差 → ホーム有利」しか言えず、
**なぜそう言えるのかが画面に残らない**。一方で全項目を並べると、上の
「生の特徴量名を画面に出さない」に戻る。

**そのグループで最も寄与が大きかった1項目の事実を、ラベルと値にする。**

```
チーム力の差          82ポイント            → ホーム有利
休養日数の差          2日                   → アウェイ有利
```

- **値に向きを書かない。** 画面は「ラベル / 値 / 有利な側」の3要素を並べるため
  二重になる。符号つきの数値（`＋82`）も出さない — どちらのチームから見た符号なのかが
  画面に出ていない
- **代表はグループ合計と同じ向きの項目から選ぶ。** そうでないと、グループが
  「ホーム有利」なのに代表の事実が逆を向く行が出る
- 21列ぶんの `label_ja` と書式は詳細設計 2.7.1 の表が持つ

#### 現在の21列では根拠が2件しか出ない（A-01 は未達）

| グループ | 該当する列 | 寄与 |
|---|---|---|
| チーム力 | 13列 | 出る |
| 日程・疲労 | 5列 | 出る |
| 選手 | 3列 | **厳密に 0**（`game_entries` が0行で定数列） |
| 会場 | **0列** | — |

`VENUE` は #15（メイン会場）を落とし、#16（移動距離）と #29（動員）を実装ごと
削除したため該当列がない（6.2）。`PLAYER` の3列は定数であり
`特徴量 − 平均` が 0 になる。**合計が 0 のグループは行を作らない**（向きが定まらず
`favors` を書けないため。詳細設計 2.7.1）。

**したがって A-01 の「根拠が3件以上」は満たさない。** 満たすには `game_entries` が
入って `PLAYER` が動くこと（P0-3 / U-06）が必要である。**品質ゲート（12章）は A-01 を
絶対条件にしているため、この状態で Phase 1 を公開しない。**

| 既定テーマ | ライトのみ設計し、ダークは値の読み替え | **ライトとダークを別々に設計する**（下記） |

**なぜ密度を捨てるのか。** 運営者が「文字が小さい・情報が詰まりすぎ・表が読みにくい」の
3点を挙げ（2026-10-07）、10案を作って比べた結果、**「字を大きくする」と「一目で見渡す」は
両立しなかった**。10案すべてで1試合あたりの高さが現行の2倍以上になった（120〜180px）。
**トレードオフであり、設計で選ぶしかない。** 読めることを取る。

**帰結を承知しておく。** 13試合ある日の一覧は約2,300px、3画面ぶんのスクロールになる。
「今日どれが接戦か」を俯瞰する用途は現行より弱い。

#### 両テーマを別々に設計する（v1.18 の前提が実測で崩れた）

旧版は「ライトを設計し、ダークは同じトークン名を再定義する」方式だった。
**この配色では成立しない。**

| 境目 | ライト | ダーク | 向き |
|---|---|---|---|
| パネル / 地 | +0.243 | +0.006 | **そろう** |
| 溝 / パネル | −0.304 | −0.003 | **そろう** |
| 従属の面 / パネル | −0.114 | **+0.006** | **逆** |
| 構造の帯 / 地 | −0.118 | **+0.031** | **逆** |
| 互角帯 / 溝 | −0.222 | **+0.028** | **逆** |

（相対輝度の差。2026-10-08 に算出）

**ダークは地が黒に近く、下に余地がない。** したがって面は上へ行くしかない。
ライトは上下に余地があり、**白を「前に出す面」として使える**。この非対称が
「1段離れる」の向きを逆にする。

**したがって「明るいほど前に出る」という単一の規則を置かない。** 代わりに
**役割で名前を付け、値と向きはテーマごとに決める**（基本設計 6.1）。
トークン名を両テーマで共有する方式そのものは維持する — 破れたのは**値の決め方の
説明**であって、仕組みではない。

**地を純白にしない。** 白を地にすると面は下へ行くしかなく、パネルと地の差が
1.12:1 までしか取れない。地を `#DDE2EA` に落とすと白が使えて 1.30:1 になる。
**ダークが純黒を避けたのと同じ型の判断である**（滲みとハレーションを避けるため）。

| 項目 | 仕様 |
|---|---|
| 既定テーマ | ライト |
| 切替 | ヘッダーのボタンでダークへ切替可能。選択は端末に保持。**ボタンはアイコン**（太陽／月のインライン SVG。文字ではない。詳細設計 5.3） |
| コントラスト | **両テーマで 4.5:1 以上。トークン単体テストで CI 検証する** |
| 数値表記 | 等幅数字（`tabular-nums`）を使用し桁を揃える |
| 対応幅 | モバイルファースト。375px で横スクロールを発生させない |
| フォント | **システムフォントのみ。Web フォントを読み込まない。** 見出しは明朝、ラベルと本文はサンセリフ、数値は等幅の3系統に分ける（基本設計 6.2）。旧版は「数字用の1ウェイトのみ（60KB以内）」を許していたが、**数値を等幅システムフォントで組むことにしたため不要になった**（v1.18） |
| チャート | ライブラリを使わずインライン SVG で実装する |
| **数値の主役の立て方** | **ライトは「彩度の孤立」、ダークは「輝度」。**明るい地では最暗色が沈んで重く見えるだけで主役が決まらないため、**勝率の数値だけを有彩色にし、カードの他すべてを無彩の灰にする**。暗い地では最明色が自ら光るため輝度で足りる。**同じ装置を両テーマで使えない**（2026-10-08 の実測。白と `#F5F7FB` の差は 1.07:1 で、明度の上端に余地がない）|
| **ホームとアウェイ** | **相対輝度をそろえ、色相だけで分ける。** 「明るい側＝有利」と読まれないため。**赤と緑の対を使わない**（色覚の多様性）。青系と橙系を使う |

**あわせて版を表示する**（運営者の指示。2026-10-06）。文言は **`ver. 1.0.0 beta`** で、
これを**唯一の出典（`web/lib/version.ts` の定数）から出す**。

**何のための表示か。** 利用者が見ている画面がいつの実装かを言えるようにするため
である。予測は日次で変わり、画面も工程ごとに変わるため、**不具合の報告を受けたときに
「どの版か」を訊けないと再現できない**。`beta` は**まだ Phase 1 の品質ゲート
（12章）を通していない**ことを明示する。

**上げ方は決めていない。** 定数を書き換えるのは運営者の判断とし、**自動で上げない**
（コミット数やタグから機械的に導くと、画面の文字が意図せず動く）。

**モデルの版と混ぜない。** `model_versions.version`（`winner-v1.1.0` など）は
予測を出したモデルの識別子であり、試合詳細に出る（8.2 の画面一覧）。
フッターの版はサイトの実装の版である。

**著作権表示も出す**（運営者の指示。2026-10-06）。文言は **`© 2026 B.PREDICT`** で、
版と同じ定数ファイルから出す。

| 決めたこと | 内容 |
|---|---|
| 名義 | **`B.PREDICT`**。**4.5.7 のリスクを承知のうえでの運営者の判断**。U-01 で名称が変わったら連動して変える |
| 年 | **`2026`（公開年）の単年。** 範囲（`2026–`）にしない |
| 年を自動で現在年にしない | 静的出力であり、**ビルドしなければ古いまま、ビルドすれば勝手に動く**。版と同じく手で上げる |
| `All rights reserved` | **付けない。** ベルヌ条約下で効果がなく、行が長くなるだけである |
| 置く順序 | **出典 → 非公式表明 → `/about` → © → 版。** © を出典より先に置かない — **この表示が公式記録そのものへの権利主張と読まれてはならない**（4.5.5 の出典文がデータの出所を述べた後に来る） |

**保護の対象は本サイトの集計・加工・画面であって、試合の記録そのものではない。**
4.5.5 の出典文言が先に出ることで、この順序が読み手に伝わる。

**日付別を `/games/[date]` にしない。** 同一階層に `[date]` と `[id]` の2つの動的セグメントを置くことはできない（Next.js の App Router では同じ階層に複数の動的セグメント名を定義できず、ビルドエラーになる）。仮に回避しても `/games/2026-09-22` と `/games/12345` の区別がパス形状に依存し、試合IDが日付形式を取った瞬間に破綻する。**日付別は `/schedule/[date]` に分離する。**

**静的生成の範囲は直近3シーズンとする（v1.12 で5シーズンから縮小）。** Pages の20,000ファイル上限に対し、
**1ルートあたり5ファイル**が生成されることを実測した（`index.html` + RSC ペイロード4本。
Next.js 16.3.5 / React 19.3 / `output: 'export'`。工程11a、`verification/RESULTS.md`）。
旧版は「HTML と RSC ペイロードの2ファイル」を前提にしていたが、**実測はその2.5倍だった**。

| 静的生成の範囲 | ルート数（推定） | 推定ファイル数 | 上限に対して |
|---|---:|---:|---|
| 全10シーズン | 約10,092 | 約50,000 | **250%（超過）** |
| 直近5シーズン（旧版の採用値） | 約5,046 | 約25,200 | **126%（超過）** |
| **直近3シーズン（採用）** | **約3,028** | **約15,100** | **76%** |
| 今季のみ | 約1,092 | 約5,500 | 28% |

ルート数は旧版の試算（全10シーズンで 20,184 ファイル ÷ 2）から逆算した推定値である。
**実際のルート数は試合数と日付数で決まるため、工程11b で実データを入れてから確定する。**
3シーズンでも 18,000 を超えた場合は、要件 11章 の P0-14 に従ってさらに縮小する。

3シーズンより古い日付・試合は静的生成せず、Workers API からクライアント fetch で表示する（存在しない日付は `notFound()`）。1ルートあたりのファイル数は Next.js のバージョンで変わるため、**CI でビルド後のファイル数を検査し、18,000を超えたら fail させる**（受け入れ基準 A-14）。

**選手ページも同じ「直近3シーズン」の原則で絞る**（F-15）。実測（2026-10-06 の
スナップショット）で全期間の出場選手は 1,028人、直近3シーズンに出場したのは **557人**
である。

| 静的生成する選手 | ルート数 | ファイル数 | 現在の 4,919 に足すと |
|---|---:|---:|---|
| **直近3シーズンに出場（採用）** | **557** | **2,785** | **7,704（43%）** |
| 全期間の出場選手 | 1,028 | 5,140 | 10,059（56%） |

**全期間でも上限には収まるが、採らない。** 8.2 が範囲を絞るのは**ファイル数だけが
理由ではない** — 「公開URLの空間に上限を設ける」（4.2）ためでもあり、日付・試合・
選手で別の原則を持つ理由がない。範囲外の選手は `notFound()` とし、**リンクも出さない**
（開けないリンクを置かない）。

### 8.3 情報提示の原則

- 勝率は**必ず両チーム分**を表示する。圧縮カードでも省略しない
- 45〜55% の試合は「ほぼ互角」と表現し、一方的な試合と見た目で区別する
- 「暫定」「確定」「序盤」「更新遅延」の状態を明示する
- 的中率は良い時も悪い時も同じ場所に表示する。**外れた試合を隠さない**
- 個人スタッツ予測には誤差の目安を添える（主要4項目に限定）
- **率（FG%等）は試投数の予測値が閾値未満なら表示しない。** 分数のみを出す
- 個人スタッツは**段階開示**とする。初期表示は主要項目のみ、展開でフルボックススコア
- 専門指標（Brier、較正曲線）は一般向けの言い換えを先に置く
- 一覧カードに的中率を出す場合は**母数を併記する**
- **実績の集計値にも母数（試合数）を併記する**（F-10 / F-15）。1試合平均は試合数が
  分からないと読めない
- **実績の率には閾値を設けない。** 分数を必ず併記し、**試投数が0のときだけ率を出さない**
  （分母0の率は定義されない）。上の「試投数の予測値が閾値未満なら表示しない」は
  **予測値**についての規約であり、実績には及ばない — 実績の分数は丸めのない事実であり、
  読者が `1 / 2` を見れば自分で判断できる。**ここで新しい閾値を発明しない**

### 8.4 状態表示の配置

| 階層 | 対象 | 形式 |
|---|---|---|
| アプリ全体 | 更新遅延 | ヘッダー直下の全幅バナー |
| 試合カード | 暫定 / 確定 / 序盤 | メタ行の右端にバッジ |
| 試合詳細 | 同上 | 勝率ブロック直下に理由の説明文 |

文言例:

- 暫定（詳細）: 「暫定 — 出場選手が未発表のため、直近5試合の出場傾向から推定しています。試合当日の午前中に更新されます。」
- 序盤: 「両チームとも今季4試合しか消化していないため、この予測はまだ精度が安定しません」
- 更新遅延: 「表示中の予測は9月21日 6:02時点のものです。その後の欠場情報は反映されていません。」

### 8.5 空状態

| 状態 | 文言 | 次のアクション |
|---|---|---|
| 試合がない日 | 「9月23日（水）に予定されている試合はありません。」 | 次の試合日へのリンク |
| オフシーズン | 「今シーズンの全日程が終了しました。」 | 的中率ページへの導線 |
| 予測未生成 | 「この試合の予測はまだありません。試合前日の朝に公開されます。」 | — |
| エラー | 「予測を読み込めませんでした。時間をおいて再度お試しください。」 | `/about` へのリンク |
| **ページがない（404）** | **「お探しのページはありません。」** | 「今日の予測」と `/about` へのリンク |
| **読み込み中** | **「予測を読み込んでいます。」** | — |
| **照合した試合がまだない（的中率ページ）** | **「的中率の記録はまだありません。試合が終わったあとに集計されます。」** | 「今日の予測」へのリンク |
| **集計がまだない（戦績・スタッツ）** | **「成績の記録はまだありません。」** | — |

Bリーグは年間の1/3以上がオフシーズンであり、空状態の設計は例外処理ではなく主要画面の一つである。

**読み込み中を表に加える（v1.29 で追加）。** 基本設計 5.6 は「ビルド時に埋め込まず、
**クライアントで静的JSONを読む**」と定めている（バッチが更新しても再ビルドを要らなく
するため）。したがって**取得が終わるまでの一瞬が必ず存在し**、そこに出す文言が要る。

**「読み込み中」は予測の確からしさについて何も主張しない。** 「予測を読み込めません
でした」（エラー）とは別の状態であり、**同じ文言を使い回すと取得中と失敗が区別
できない**。次のアクションは置かない（待てば変わる）。

**「照合した試合がまだない」を表に加えた（v1.31 で追加）。** 的中率ページは
**`accuracy_summary` が空の状態で必ず一度は踏まれる** — 結果照合が初めて走るのは
本番の最初の試合の後であり、それまで `overall` は null である（詳細設計 3.3）。

**「読み込み中」でも「エラー」でもない。** 取得は成功しており、集計する対象が
まだ無いだけである。3つを同じ文言にすると、**取得中・失敗・データなしが
区別できない**（v1.29 と同じ理由）。

**オフシーズンの文言を使い回さない。** あちらは「今シーズンの全日程が終了しました」で
**時期を主張する**が、ここで言いたいのは「まだ1試合も照合していない」である。

**文言を確定した**（v1.35。運営者の委任により決めた。2026-10-05）。上の表の2行
（「予測を読み込んでいます。」「的中率の記録はまだありません。試合が終わったあとに
集計されます。」）を**そのまま採る**。

**案をそのまま採れる理由は、この表の他の4行と形が揃っていることである。** いずれも
「〜ません。」または「〜ています。」で終わり、**次に何が起きるかを添えている**
（「次の試合日へのリンク」「試合が終わったあとに集計されます」）。表の中で1行だけ
違う語り方をしていないかが、ここで確かめるべきことだった。

**3つが区別できていることも確かめた** — 取得中（「読み込んでいます」）/ 失敗
（「読み込めませんでした」）/ データなし（「記録はまだありません」）。v1.29 と
v1.31 がそれぞれ警戒したとおりに分かれている。

**「集計がまだない」を表に加えた（v1.36）。** 戦績・スタッツの画面は
`player_stat_summary` / `team_stat_summary` が空の状態で必ず一度は踏まれる
（集計が初めて走るのは次の `daily_ingest` である）。

**「照合した試合がまだない」を使い回さない。** あちらは**的中率**について述べており、
ここで言いたいのは「成績の集計がまだ走っていない」である。**次のアクションは置かない** —
待てば変わる（「読み込み中」と同じ）。

**404 を空状態の表に含める（v1.13 で追加）。** シーズン範囲外の日付・存在しない試合ID・静的生成の範囲外は 404 で打ち切る設計であり（8.2、要件 4.2）、**実際に踏まれる画面**である。Next.js の既定の 404 は英語であるうえ、`prefers-color-scheme` を見る独自CSSを差し込んで**利用者が選んだテーマを無視する**ため使わない。

### 8.6 アクセシビリティ

- 見出し要素で文書構造を作る（試合1件を `article`、対戦名を見出し）
- タブ・ボタンは `button` / `a` で実装し、最低44×44px を確保する
- 確率ブロックに `role="img"` と一文の `aria-label` を与え、内部の数値とバーは `aria-hidden` にする
- 装飾目的で `<s>` `<i>` `<em>` を使わない
- 色だけで情報を伝えない

## 付録A. 用語

| 用語 | 意味 |
|---|---|
| Elo レーティング | 対戦結果から算出する相対的なチーム強度指標 |
| Brier Score | 確率予測の精度指標。0に近いほど良い |
| ECE | 予測確率と実際の発生率の乖離。等頻度10ビンで算出 |
| Four Factors | eFG%、TOV%、ORB%、FTレートの4指標 |
| ポゼッション | 攻撃回数の推定値 |
| SHAP | 各特徴量の予測への寄与度を算出する手法。ログオッズ空間の値 |
| データリーク | 予測時点で未知の情報が特徴量に混入すること |
| 暫定 | 出場者未確定の状態で算出された予測 |
| freeze | 試合開始をもって予測を確定し変更不可とすること |
| ハードルモデル | ゼロ過剰な分布を「発生するか」と「発生した場合の量」に分けて扱うモデル |

## 付録B. 精度の見立て

設計時点での現実的な見積もり。**これは目標ではなく前提である。**

| 指標 | 見立て |
|---|---|
| Brier（勝敗） | 0.200 〜 0.212 |
| Accuracy（勝敗） | 64 〜 68% |
| ベースライン（ホーム必勝） | **52.7%**（実測。リーグ戦4シーズン n=1,829。旧版は「約60%」としていた） |
| Elo単体ロジスティック回帰 | Brier 0.213 〜 0.220 / Accuracy 63 〜 66% |
| MAE（チーム得点） | 8 〜 10点 |

| 項目 | MAE | 備考 |
|---|---|---|
| MIN | 5 〜 7分 | |
| PTS | 4.5 〜 6点 | |
| TR | 2.0 〜 2.5 | |
| AS | 1.2 〜 1.8 | |
| FGA | 2.5 〜 3.5 | |
| FGM | 1.5 〜 2.0 | |
| 3FGA | 1.5 〜 2.0 | |
| FTA | 1.5 〜 2.0 | |
| F | 0.9 〜 1.2 | |

| ST | 0.6 〜 0.8 | **平均値と同程度。予測の付加価値がほぼない** |
| BS | 0.4 〜 0.6 | **同上** |

ST と BS は1試合あたり平均0.7回程度であり、MAE が平均値と同水準になる。これは「その選手の平均を出しているだけ」の状態であり、表示はするが誤差目安を併記して誤認を避ける。

**的中率 71% / Brier 0.186 は、運の良い1シーズン（n=300程度）なら出うるが、複数シーズンの walk-forward で安定する水準ではない。** これを目標として掲げないこと。

勝敗予測において Elo 差を超える増分は非常に小さく、30項目の特徴量のうち Brier を有意に改善するのはおそらく5〜8項目である。このプロダクトの価値は精度の絶対値ではなく、較正の正確さと根拠提示の一貫性にある（1.2 参照）。
