# B.LEAGUE データ取得元の調査・開発引き継ぎ

## 1. この資料の位置づけ

工程5（スクレイパ・パーサ）の前に、取得すべきページ、取得する項目、確認できた構造、未確認事項をまとめた調査資料。
Claude Code / Codex のどちらで再開しても、会話履歴ではなく、この資料と既存設計を参照できるようにする。
**本資料は設計変更の承認でも、スクレイピング機能の実装完了報告でもない。**

参照順序は [CLAUDE.md](../CLAUDE.md) の「文書の優先順位」に従う。

1. [CLAUDE.md](../CLAUDE.md) の絶対ルール

3. [基本設計](design-basic.md) 2.1、4章、7.2、9章
4. [詳細設計](design-detail.md) 1章、4.3〜4.4、4.8
5. [scraping スキル](../.claude/skills/scraping/SKILL.md)
6. [既存の測定記録](../verification/RESULTS.md) と本資料

本調査ではアプリケーション、CI、DB、既存の仕様を変更していない。過去全試合の収集もしていない。
既存設計との食い違いは第7節に記録した。関係する実装に入る前に解決する。

### 証拠の区分

| 区分 | 意味 |
|---|---|
| `HTTP確認` | 今回、識別用UA付きのGETで初回レスポンスの構造を確認した。本文はメモリ上で解析し、ファイル保存していない |
| `閲覧確認` | 今回、Web閲覧ツールで公式ページの表示内容・リンクを確認した。キャッシュを含む可能性があり、初回HTMLや最新HTTP応答の保証には使わない |
| `既存記録` | `verification/RESULTS.md` などにある過去の確認。本調査で再測定したとは扱わない |
| `未確認` | URL候補や仕様上の必要性はあるが、取得方法・値の意味・網羅性が確定していない |

少数のサンプルでの確認であり、全年度・全試合・延期や延長等の全状態を保証しない。

## 2. 取得対象ページ一覧

ホストは、特記しない限り `https://www.bleague.jp`。URLの大文字・小文字を維持する。
`{year}` はシーズン開始年、`{game_id}` は `ScheduleKey`、`{player_id}` は `PlayerID`、`{venue_id}` は `StadiumCD`。

| ID | 役割 | URL / テンプレート | 取得する情報・利用先 | 利用タイミング | 確認状況 |
|---|---|---|---|---|---|

| S04 | 日程の追加取得 | `/schedule/?data_format=json&year={year}&mon=all&tab=1&event={event}&index={offset}` | ページングされた試合一覧。`games` のID・日程・対戦カード・結果への入口 | S03と同じ。既取得の一覧を重複取得しない | `event=2` の先頭2ページ、`event=3` の先頭をHTTP確認 |

## 3. 日程・試合詳細で確認できた構造

### S03/S04：日程は「JSONの中のHTML断片」も解析する

[2025年度の日程ページ](https://www.bleague.jp/schedule/?year=2025&mon=all&tab=1) の初回HTMLで次を確認した。

- `select[name=year]` に2016〜2026の選択肢がある。
- `select[name=club]` に公式TeamIDと、その年度の短縮名がある。
- `select[name=event]` は `2`（リーグ戦）、`3`（チャンピオンシップ）、`5`（オールスター）を含む。
- ページのJavaScript自身が `data_format=json` と `index` を指定して同じパスへGETする。

S04のレスポンスは、少なくとも今回のサンプルでは次の形だった。以下は**構造だけを示す合成例**であり、取得本文ではない。

```json
{
  "topics": ["<li class=\"list-item\" id=\"demo-game\">...</li>"],
  "broadcasts": [],
  "index": 20
}
```

`topics` は試合オブジェクトの配列ではなく、HTML文字列の配列。複数試合を同じ断片が含む可能性もあるので、配列長をそのまま試合数にしない。
今回のリーグ戦サンプルでは `li.list-item` の `id` と、`a.data-game` の `ScheduleKey` を含むリンクが見つかった。
日付・時刻・対戦カード・延期等の表示を抽出するセレクタは、今回すべてを確定したわけではない。

| 取得条件（year=2025 / mon=all / tab=1） | `topics` の長さ | 応答 `index` | 観測 |
|---|---:|---:|---|
| `event=2&index=0` | 20 | 20 | 20個の異なる試合IDを確認 |
| `event=2&index=20` | 20 | 40 | 20個の異なる試合ID。先頭ページとの重複なし |
| `event=3&index=0` | 16 | 今回未記録 | HTTP 200、JSONのトップレベルキーと配列長を確認。全試合の列挙・終端確認は未実施 |

次ページへ進む挙動は確認できたが、**空ページ、最終ページの `index`、途中の重複・順序変更、当季の大会区分は追加確認が必要**。
レスポンスがJSONだから構造化済みの試合レコードだと決めつけない。

取得対象は既存仕様どおり `event=2 → REGULAR`、`event=3 → PLAYOFF`。
`event` を省略した結果が全大会を網羅するかは未検証。既存のシーズン開始・終了日のCSVについても、PLAYOFFを含む上位集合になっているか別途照合が必要。

### S05：試合詳細の初回HTMLに埋め込みデータがある

終了済み2試合では `<script>` 内の **`_contexts_s3id.data = ...`** にJSONオブジェクトがあった。
HTTP取得だけで取り出せるため、この2件のボックススコア取得にブラウザ実行や追加AJAXは不要だった。
サイトのJavaScriptを `eval` する実装にはしない。

| 必要な部分 | 観測したパス・キー | 主な取り込み先 |
|---|---|---|
| 試合 | `data.Game`：`ScheduleKey`、`Year`、`HomeTeamID`、`AwayTeamID`、得点、`GameDateTime`、`Attendance` | `games` |
| 会場 | `data.Game.StadiumCD` / `StadiumNameJ` | `venues` / `venue_revisions` |
| 選手・クラブ名 | `HomeBoxscores` / `AwayBoxscores` の `PlayerID`、`PlayerNameJ`、`PlayerNo`、`TeamID`、`TeamNameJ` | `players`、所属断面の材料、試合実績 |
| 個人記録 | `data.HomeBoxscores` / `data.AwayBoxscores` の `PeriodCategory=18` | `player_game_stats` |
| チーム記録候補 | 上記配列の非選手行、`data.Summaries` の `PeriodCategory=18` | `team_game_stats`。行の区別は下記参照 |

スタッツの対応表の正本は [詳細設計4.4](design-detail.md)。例として `PT2M/PT2A`、`PT3M/PT3A`、`FTM/FTA`、`FOULON`、`PlayTime` を確認した。
同梱されている審判、プレイバイプレイ、シュートチャート等は保存対象にしない。
ページ内の `_players` には今回の試合以外も含む大きな辞書があり、その全体を選手マスタとして保存しない。

### 非選手行は1種類ではない

[2025年度の終了試合（505497）](https://www.bleague.jp/game_detail/?ScheduleKey=505497&tab=2) で、通算行はHOMEが13行、AWAYが14行。
そのうち選手IDありはそれぞれ11行・12行で、各チームに次の2種類の非選手行があった。

| 観測した行 | `PlayerID` | `TeamID` | 得点 | リバウンド等 | 解釈の扱い |
|---|---|---|---|---|---|
| `Category=2` | 空文字 | チームIDあり | この試合では0 | 0以外の値あり | チームに付いた記録と考えられる。全年度の意味は未確定 |
| `Category=3` | 空文字 | `null` | 試合のチーム得点と一致 | チーム合計の値 | チーム合計行と考えられる。親のHOME/AWAY情報でチームを解決する必要あり |

HOMEの非選手行では、`Category=2` のOR/DRが5/3、`Category=3` が11/27だった。
**`PlayerID` が空ならすべて同じチーム集計、と扱うと重複・誤集計になる。**
また、すべての項目で「チーム値＝選手の単純合計」とする既存の検証条件は、チーム記録を考慮して再検討する必要がある。
採用する行と項目別の恒等式は第7節のC01で扱い、今回の1試合だけで全年度の規則を確定しない。

### 年度・状態で異なる項目

| 項目 | 2016年度の試合 `22` | 2025年度の試合 `505497` | 実装前に必要なこと |
|---|---|---|---|
| `StadiumCD` | 整数 | 文字列 | 既存仕様どおり文字列へ正規化 |
| TeamID / PlayerID | サンプルで整数 | サンプルで文字列 | DBの文字列IDへ正規化し、TeamIDは対応表で解決 |
| `Game.GameDateTime` | 数値文字列 | 数値文字列 | 単位・タイムゾーンを確認しUTCへ統一 |
| トップレベル `GameDateTime` | 数値文字列 | `/Date(...+0900)/` 形式 | 同名でも階層で形式が違う。無差別に拾わない |
| `Game.GameEndTime` | キーあり | 確認したGameオブジェクトにはキーなし | 実測値と既存設計の推定終了時刻を区別する |
| 個人行の `PLUSMINUS` | 確認したHOME/AWAYサンプル行にはキーなし | サンプル行にあり | 全年度の欠損率を調べる。欠損を0に置換しない |
| `Event` | トップレベル・Game内で `2` | トップレベルは空文字、Game内ではキーなし | 大会区分は日程取得時に保持する。詳細だけで常に復元できると思わない |

未開始の [2026年度の試合（506381）](https://www.bleague.jp/game_detail/?ScheduleKey=506381&tab=2) では、終了済みと同じJSON代入を抽出できなかった。
`_positions` や `_players` の存在だけでは出場登録の確定を証明できない。
**1試合・1時点の観測から「試合前エントリーが存在しない」「何時間前に出る」とは結論しない。**

## 4. 選手・会場の補完

### S07/S08：選手一覧と選手詳細

[選手一覧](https://www.bleague.jp/roster/) のHTTP確認で見つかったパラメータは次のとおり。

| パラメータ | 確認した値・役割 |
|---|---|
| `year` | 2016〜2026の年度選択 |
| `club` | 公式TeamID |
| `p` | PG / SG / SF / PF / C の絞り込み |
| `c` | 日本 / 海外 の絞り込み。DBの登録区分とは別 |
| `o` | `random`（ランダム） / `sort`（50音順） |
| `e` | 在籍中 / 退団済 / 全選手 |
| `pageID` | ページ番号。ページ上の次ページリンクで確認 |
| `tab` | 取得した次ページリンクに `tab=1` が含まれる |

観測した次ページURLは
`/roster/?tab=1&year=2026&club=&p=&c=&o=random&pageID=2`。
**既定はランダム順**なので、このまま全ページを巡回すると欠落・重複の危険がある。
`o=sort` の選択肢は確認したが、固定順での複数ページ取得、退団済選手の網羅、古い年度の応答はまだ検証していない。
`e` が次ページへ引き継がれるかも要確認。

詳細へのリンクは **`/roster_detail/?PlayerID=...`**。`/player_detail/` ではない。
[詳細ページの確認例](https://www.bleague.jp/roster_detail/?PlayerID=51000321) では、氏名・身長・ポジション・リーグ登録国籍・年度別所属の表示を確認した。
本文中の生年月日、出身地、体重、経歴、写真等は現行の取得対象へ追加しない。

現在のDBは `player_seasons.position` が単一の5値に限定されるが、ページには `C/PF`、`PG/SG`、`SG/SF` 等がある。
先頭のポジションを勝手に採用しない。登録国籍から `JP/NATURALIZED/ASIA/FOREIGN` を推測で埋めることもしない。
年度途中の加入・退団日、過去時点の身長・ポジション・登録区分について、現在のプロフィールだけで復元できるとは扱わない。

### S09：会場詳細

[会場詳細の確認例](https://www.bleague.jp/arena_detail/?ArenaCD=169) で住所の表示を確認した。
会場IDは試合の `StadiumCD` を使い、同じ会場名から新しいIDを採番しない。

既存設計では座標を国土地理院で一度だけ解決しCSVへ固定し、収容人数は出典付き手入力とする。
今回、会場詳細から座標や収容人数を自動取得できることは検証していない。
住所・現名称を過去の全試合へ無条件に適用せず、履歴の扱いは既存の **U-10** の解決を待つ。

## 5. 取得順序とリクエスト量の考え方

既存設計に沿う取得経路は以下。まだ実装手順の確定ではなく、取得対象間の依存関係を示す。

1. S01/S02で取得前確認をする。
2. S03から年度・大会・クラブ対応を確認し、S04から対象試合IDを列挙する。
3. `event=2/3` の区分を保持し、既取得IDを除いてS05を取得する。
4. 試合に現れる未知の選手・会場だけS07/S08/S09で必要属性を補完する。
5. パーサで正規化・値域検証し、既存の `/internal/*` を通して保存する。今回この保存処理は行っていない。
6. 学習用入力は同じ正規化済みデータからスナップショットへ書き出す。D1を学習入力として読み出さない。

今回の終了試合2件では、試合・個人記録・チーム記録候補が1回の詳細GETに同梱されていた。
これは「全用途が1試合1リクエストで済む」ことの証明ではない。選手・会場の補完、日程のページング、エントリー確認は別途必要。

```text
総取得数 = 取得前確認 + 日程の取得ページ数 + 未取得試合詳細数
           + 未解決選手の補完数 + 未解決会場の補完数 + 試合前の再確認数
```

P0-4 / U-07 の全体見積もりは未完了。今回のサンプルから全シーズンの所要時間を確定しない。
既存の「1日1シーズン」「再開可能」「日次3,000リクエスト上限」は維持する。

## 6. 今回の確認方法と証跡

直接GETは識別用UA `BPredict-research/0.1 (+https://github.com/yozamaru/bpredict/issues)` を使い、逐次実施した。
各取得間は最低3秒を超える間隔を確保し、タイムアウト20秒・本文上限5 MiBで実施。リポジトリに生HTML・生JSONは保存していない。
Web閲覧ツールは表示・リンクの補助確認に限り、以下では直接GETと分けて記録する。

### HTTP確認の記録

直接GETの成功は10回、9種類のURL。`505497` は抽出位置を特定するため2回取得した。全件HTTP 200。
別途、サンドボックス内での最初のcurlは名前解決に失敗し、ネットワーク許可後に取得した。
