## 1. 満たさなければならない制約

| # | 制約 | 出典 |
|---|---|---|
| 1 | **主要導線（今日の予測・試合一覧）は Workers も D1 も経由しない。** 無料枠が枯れても表示が続くこと | 要件 4.2 |
| 2 | **Pages の1デプロイ 20,000ファイル**。静的ルートで約15,100使っており、CI は 18,000 で落とす。`web/public/` の中身は `out/` にそのまま入るため、**JSONもこの数に入る** | 要件 7章 / A-14 |
| 3 | **バッチが書き出してリポジトリにコミットする。** public リポジトリであり、**毎日書き換わるファイルの総量がそのまま履歴に積む** | 基本設計 4.1 / 7.3 |
| 4 | 更新は日次1回 ＋ 当日3スロット（最大4回/日） | 基本設計 4.1 |
| 5 | ISR を使わない。ビルド時に値を埋め込まず、クライアントが JSON を読む | 要件 7章 / 基本設計 5.6 |

制約3が効く。**1日あたりの書き換え量 × 365 がリポジトリに積む。**

| 1ファイルの目安 | 実測の根拠 |
|---|---|
| 一覧1試合ぶん | 約400バイト（両チームの勝率・予想スコア・状態・時刻・クラブ名） |
| 詳細1試合ぶん | **約14KB**（根拠4件 ＋ 出場確率50%以上の選手20人 × フルボックススコア。API の応答例から算出） |

## 2. 画面が読むもの

| 画面 | 必要なデータ | 枠が枯れても見えるべきか |
|---|---|---|
| `/`（今日の予測） | 当日の試合一覧、両チームの勝率、予想スコア、状態、更新遅延 | **必須**（要件 4.2） |
| `/games/[id]`（試合前） | 上記 ＋ 根拠4件 ＋ 個人スタッツ ＋ 直近成績 ＋ モデル精度 | **このプロダクトの中身**。判断根拠が価値の半分 |
| `/schedule/[date]` | 指定日の試合一覧 | 未来日は必須。過去日は API でよい |
| `/games/[id]`（試合後） | 実績との対比、確率帯の通算的中率 | API でよい（過去は静的生成済みのHTMLがある） |
| `/results` `/accuracy` `/teams/[slug]` | 集計 | API でよい |

## 3. 案

### 案A（最小）— `today.json` と `meta.json` だけ

| 項目 | 値 |
|---|---|
| ファイル数 | 2 |
| 1日の書き換え | 約20KB |
| 枠が枯れたとき | 今日の一覧は見える。**試合詳細（根拠・個人スタッツ）が見えない** |

制約1は満たすが、**枠が枯れた日に「なぜその予測なのか」が消える**。

### 案B（推奨）— 一覧は7日窓、詳細は当日だけ

```
web/public/data/
├── meta.json                生成時刻・モデル版・ジョブの最終成功・更新遅延の判定材料
├── today.json               当日の一覧（= GET /games?date= と同じ形）
├── schedule/2026-09-26.json 翌日以降7日ぶんの一覧（同じ形）
└── games/<gameId>.json      **当日の試合だけ**の詳細（= GET /games/:gameId と同じ形）
```

| 項目 | 値 |
|---|---|
| ファイル数 | 約23（`meta` 1 ＋ `today` 1 ＋ 7日 ＋ 当日13試合） |
| 1日の書き換え | 約250KB（詳細13試合 × 14KB ＋ 一覧） |
| 1年で積む量 | 約90MB（生。git のパック後はこれより小さい） |
| 枠が枯れたとき | **今日の予測と根拠・個人スタッツまで見える。** 過去と集計は見えない |

**前日以前の `games/<id>.json` は削除する。** 試合後の表示は API に切り替わる
（過去の試合詳細は静的生成済みのHTMLがあり、実績は D1 にしかない）。
削除しないとファイル数と書き換え量が単調増加する。

### 案C（全部）— 7日窓の詳細まで静的

| 項目 | 値 |
|---|---|
| ファイル数 | 約110 |
| 1日の書き換え | **約1.3MB**（詳細90試合 × 14KB） |
| 1年で積む量 | **約460MB**（生） |

制約3に照らして採らない。**public リポジトリの履歴に年460MB積むのは、
無料枠を守るという方針と釣り合わない**（GitHub の推奨は1GB以下）。
7日先の詳細を静的にして得られるのは「枠が枯れた日に明日以降の個人スタッツも見える」
ことだけで、価値が費用に見合わない。

## 4. 案Bで決めることの中身

### 4.1 スキーマは公開APIと同じ形にする

**静的JSON専用のスキーマを作らない。** `{ "data": ..., "meta": ... }` の形（詳細設計 3.1）を
そのまま使い、中身も対応する API の応答と**同一**にする。

| 静的ファイル | 同じ形の API |
|---|---|
| `today.json` / `schedule/<date>.json` | `GET /games?date=` |
| `games/<id>.json` | `GET /games/:gameId`（**実装済み**。詳細設計 3.3） |

こうすると、クライアントは1つの型と1つの描画経路だけを持つ。
`/games/[id]` は「当日なら静的ファイル、それ以外は API」と**取得先だけを替える**。

**この決定が公開API の残り4本の形も決める。** `GET /games?date=` の形が
`today.json` の形になるため、U-09 を決めれば `/games?date=` も書ける。

### 4.2 `today.json` は自分の日付を持つ

`today.json` は 06:00 JST に書き出される。**00:00〜06:00 JST の間、中身は前日である。**
ファイル名では「今日」を保証できないため、`data.gameDate` を必ず入れ、
画面はその日付を明示して描く（「9月26日（土）の試合」）。
ブラウザの日付と食い違ったら、画面は**ファイルの日付を正**として表示する
（推測で「試合がありません」と出さない。要件 8.5）。

### 4.3 `meta.json` に入れるもの（更新遅延バナーの判定材料）

| キー | 用途 |
|---|---|
| `generatedAt` | 「表示中の予測は9月26日 6:02時点のものです」の時刻（要件 8.4） |
| `dataAsOf` | 推論時点で DB にあった最新試合の終了時刻（詳細設計 1.5 の `data_as_of`） |
| `lastSuccessAt` | **`status = 'SUCCESS'` の最新**の終了時刻。これから24時間で遅延と判定する（基本設計 4.5） |
| `lastRunStatus` | `SUCCESS` / `PARTIAL` / `ABORTED` / `FAILED`。`SUCCESS` 以外は別バッジ |
| `modelVersions` | 代表バージョン（画面の「使用モデル」表示用） |

**`stale` を真偽値で入れない。** バッチは自分が書いた時点しか知らず、
「今」から24時間経ったかを判定できない。**判定はクライアントが `lastSuccessAt` と
現在時刻で行う**（バッチが `stale: false` と書いた瞬間に古くなる）。

### 4.4 書き出しと削除の規則

| 規則 | 理由 |
|---|---|
| 毎回、**7日窓の全ファイルを書き直す** | 冪等性。差分更新にすると、間が抜けたときに古い値が残る |
| **窓から出たファイルを削除する**（前日以前の `games/` と `schedule/`） | ファイル数と書き換え量を一定に保つ |
| 削除もコミットに含める | リポジトリと配信内容を一致させる |
| **推論に失敗したら1ファイルも書かない**（前回のものを残す） | 基本設計 4.3。画面は `meta.generatedAt` で遅延を出す |

### 4.5 CI で検査すること

| 検査 | 理由 |
|---|---|
| `out/` のファイル数 18,000以下 | 既にある（A-14）。静的JSONもここに含まれる |
| `data/` のファイル数に上限を置く（案Bなら 50） | 窓から出たファイルの削除漏れを機械で捕まえる |
| 静的JSON が API と同じスキーマに適合すること | 形を1つに保つ。ずれたら片方だけ壊れる |
