# Phase 0 検証スクリプト

設計上の前提を数値で確かめるためのスクリプト。実装前に実行し、結果を設計書へ反映する。

| ファイル | 検証内容 | 依存 |
|---|---|---|
| `01_ece_noise_floor.py` | 完全較正下での ECE 分布。採用ゲートの閾値をnに応じて決める | numpy |
| `02_acceptance_criteria_power.py` | 受け入れ基準とモデル比較の統計的検出力 | numpy |
| `03_reconciliation_logit.py` | 個人スタッツのチーム整合化アルゴリズムの収束 | numpy, scipy |
| `04_artifact_size_and_batch_limits.py` | artifact サイズ推定と D1 バッチ上限の算術 | numpy |
| `05_workers_cpu_budget.mjs` | JSON パース＋検証の CPU コスト | Node のみ |

## Phase 0 の実機検証へ送った6項目（P0-11〜P0-16）

設計段階で計画した15項目のうち9件を上のスクリプトで実行し、**残る6件は実機でしか測れない**ため
Phase 0 へ送った。理由は2つで、外部レジストリ（PyPI / npm）が組織ポリシーで 403 だったことと、
実データがなければ測れないこと。**実測するまで設計の前提を緩めないこと。**

| # | 項目 | 測り方 | 現在の前提 |
|---|---|---|---|
| P0-11 | **勝率の導出経路 A / B の比較と、経路B の σ の実測** | 同一 walk-forward ウィンドウで Brier と ECE を測り、同ウィンドウの Margin 残差から σ を出す | 両方実装。σ は未測定（12〜13点は他リーグからの見当であり定数化しない） |
| P0-12 | **LightGBM の実 artifact サイズ** | 設計のパラメータで学習し `booster.save_model()` の出力バイト数を測る | `04` は書式からの推定値（0.27〜0.70MB）。上限は 1.5MB |
| P0-13 | **D1 `batch()` のクエリ計上方法** | 実アカウントで、`batch()` 内の各ステートメントが「1呼び出しあたり50クエリ（Free）」にどう数えられるかを計測 | 1文＝1クエリという最も厳しい前提 |
| P0-14 | **Next.js 16 の実ビルドファイル数** | 直近5シーズンで `output: 'export'` のビルドを回し、`out/` のファイル数を数える | 1ルートあたり2ファイル。CI 閾値 18,000 |
| P0-15 | **Zod の検証コスト** | 実スキーマで Workers 上の CPU 時間を測る | `05` は手書き検証での測定。Zod は数倍遅い（3〜4ms 見込み） |
| P0-16 | **ECE ノイズフロアの実分布での再計算** | 実データの予測確率分布で `01_ece_noise_floor.py` を再実行する | `01` は一様分布での参考値。定数化しない |

> `app/games/[date]` と `app/games/[id]` の衝突は v1.3 で `/schedule/[date]` への分離により解決済みであり、
> 再現検証は不要になった。P0-14 に残るのは**生成ファイル数の測定**のみ。
