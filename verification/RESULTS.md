# Phase 0 の測定結果

設計の前提を実機で確かめた結果をここに記録する。**この表が埋まるまで工程1（DDL確定）へ進まない。**

## 使い方

1. 測定したら、その行の「状態」を `未測定` → `測定済` にし、測定日と結果を書く
2. 結果が設計の前提と違う場合、**先に該当文書を直してから**「設計への反映」に反映先を書く
3. 前提より緩い結果が出ても、**測定するまでは設計を緩めない**（`docs/design-basic.md` 9.1）
4. 取得できないと判明した項目は、該当する特徴量を無効化して先へ進む。工程は止めない（`docs/design-detail.md` 9章）

数値は生の測定値を書く。「問題なし」とだけ書かない。後から前提を再評価できなくなる。

## 構造上の発見（2026-09-21・v1.6 で反映済み）

**確認対象**: `https://www.bleague.jp/game_detail/?ScheduleKey=505497&tab=2`
（2026-05-03 三遠ネオフェニックス 93–79 名古屋ダイヤモンドドルフィンズ）

**事前確認**: `robots.txt` を取得して設計書 5.1 の記述と照合した。`User-agent: *` の制限はなく、
`Disallow` は SEO 解析ボット（SemrushBot / MJ12bot / serpstatbot / SEOkicks-Robot / dotbot /
BLEXBot）のみ。`msnbot` と `bingbot` に `Crawl-delay` が設定されている。**一般クローラーへの
制限は引き続き存在しない。** 確認は手作業で計2リクエスト。

### 分かったこと

| 項目 | 結果 |
|---|---|
| ボックススコアの表（`<table>`） | **HTML に存在しない。** 列見出しは JS のテンプレート文字列の中にあり、実行時に組み立てられる |
| 選手スタッツの実データ | **`<script>` 内の JSON として埋め込まれている**（JS で取りに行くのではなく、初回のHTMLに入っている） |
| ページサイズ | 約 894 KB（gzip 転送は約 184 KB）。設計の 5MB 上限には収まる |
| 遅延読み込みの AJAX | `season-result` / `club-leader` / `match-result` / `recent-match` / `shot-chart` の5種。**ボックススコアは含まれない** |
| 余分に含まれるデータ | プレイバイプレイ 703 件（`ActionCD` `PlayText` `X` `Y`）、審判名、シュートチャート座標 |

### 埋め込みJSONと設計の列の対応（すべて揃っている）

| 設計の列 | サイトのフィールド | | 設計の列 | サイトのフィールド |
|---|---|---|---|---|
| `minutes` | `PlayTime`（`"09:02"` 形式） | | `stl` | `ST` |
| `fg2m` / `fg2a` | `PT2M` / `PT2A` | | `blk` | `BS` |
| `fg3m` / `fg3a` | `PT3M` / `PT3A` | | `pf` | `FOUL` |
| `ftm` / `fta` | `FTM` / `FTA` | | **`fd`** | **`FOULON`** |
| `oreb` / `dreb` | `RB_OFF` / `RB_DEF` | | `plus_minus` | `PLUSMINUS` |
| `ast` | `AS` | | `pts` | `Point` |
| `tov` | `TO` | | `started` | `StartingFlg` |
| `player_id` | `PlayerID` | | `club_id` | `TeamID` |

恒等式の検算も通った（`Point=25` に対し `PT2M×2 + PT3M×3 + FTM = 25`、`RB_TOT = RB_OFF + RB_DEF`）。

### 注意すべき構造

- **`PeriodCategory` でレコードが分かれている。** 1〜4 がクォーター別、15 / 16 が前後半、
  **18 が試合通算**。取り込むのは 18 のみ。全カテゴリを入れると7倍の行数になる
- 各カテゴリ27件のうち **4件は `PlayerID` が空のチーム集計行**（`TeamID` が null の行も2件ある）。
  選手行と集計行を取り違えると `team_game_stats` と `player_game_stats` が汚染される
- 数値が `0` ではなく**空文字 `""` で入っている**フィールドがある。`0` と「データなし」の
  区別が必要で、値域検証の前に正規化が要る

### 取得してはならないもの

同じ JSON に**審判名**（特徴量 #30 は見送り）と**プレイバイプレイ**が含まれる。
要件 5.3「予測に不要な属性は取得対象から除外する」に従い、**必要なフィールドだけを抜き出して
保存する**。JSON 全体をそのまま保存しない。

## クラブ対応関係（2026-09-21・P0-5）

**確認対象**: `https://www.bleague.jp/schedule/?year=YYYY&mon=10&tab=1`（`year` = 2016〜2026 の11ページ）、
`https://www.bleague.jp/club/`、`https://www.bleague.jp/game_detail/?ScheduleKey=22&tab=2`、
`https://www.bleague.jp/club_detail/?TeamID=703&year=2016&tab=1`。手作業で計15リクエスト、
4秒間隔の逐次取得（並列なし）。取得した本文は保存していない。

### 結論: `TeamID` はシーズン・改称・リーグ再編をまたいで不変

2016-17 の試合（`ScheduleKey=22`、千葉 vs 栃木）の埋め込みJSONで
`HomeTeamID=704` / `AwayTeamID=703` を確認した。この `703` は 2026-27 の一覧では
**宇都宮ブレックス**であり、2019年の改称（栃木→宇都宮）をまたいで同一である。

| 検証した継ぎ目 | TeamID | 結果 |
|---|---|---|
| 改称 | `703` 栃木ブレックス → 宇都宮ブレックス | 不変 |
| 改称 | `726` SR渋谷 → 東京SR | 不変 |
| 改称＋9シーズンのトップリーグ不在 | `718` 西宮（2017-18）→ 神戸（2026-27） | 不変 |
| リーグ再編（B1 → B.PREMIER） | 26クラブすべて | 不変 |

**したがって `club_source_ids` は本ソースでは1:1になる。** それでも表は維持する
（`docs/design-detail.md` 1.2）。公式サイトがID体系を変えた場合、この表が唯一の継ぎ目になる。
旧IDのまま保存しないという規約（取り込み時に `club_id` へ解決する）も変えない。

**`ScheduleKey` も通しの連番である。** 2016-17 の開幕節が 20〜26、2026-27 が 506381。
シーズンごとにリセットされないため、`games.id` にそのまま使える。

```
入力: 愛知県豊橋市神野新田町字メノ割1-3（豊橋市総合体育館の住所）
```

### 1試合あたりの取得ページ数（P0-4 / U-07）

**終了済み試合のスタッツは、試合詳細1ページ（`/game_detail/?ScheduleKey=...&tab=2`）に同梱されている。**
試合・会場・入場者数・選手別・チーム別のすべてが `<script>` 内の1つの JSON に入っており、
追加の AJAX もブラウザ実行も不要だった（終了済み2試合で確認。2016年度と2025年度）。

| 用途 | 1シーズンあたりの見積もり |
|---|---|
| 日程一覧（20件/ページ） | 26〜38 リクエスト（試合数 520〜760 ÷ 20） |
| 試合詳細 | 520〜760 リクエスト（1試合1ページ） |
| 取得前確認（robots / 利用規約） | ジョブごとに2 |
| 選手・会場の補完 | **未測定**（未知の選手・会場の数に依存する） |

3秒＋ジッタで逐次取得すると **1シーズンおよそ30〜50分**で、`backfill` の300分枠と
日次3,000件の上限に収まる。**「1シーズン1日」の制約は維持する**（D1 書込枠の側で決まる）。

**これは「全用途が1試合1リクエストで済む」ことの証明ではない。** 選手・会場の補完、
日程のページング、試合前エントリーの確認は別に必要で、後者は経路そのものが未確認である（C04）。

## `games` の自然キー UNIQUE 違反（2026-09-23）

9試合のうち7件を直した後、2016-17 の再取り込みが `LoaderError: 内部APIが失敗を返した

`UNIQUE (season_id, game_date, home_club_id, away_club_id)` の違反だった。

|---|---|---|---|---|

**これで短い2試合の正体も判明した。** 同じ日・同じカードで直前の試合の後に行われる
決着戦である（得点規模と所要時間が整合する）。「中断・不成立の試合」という当初の推測は
誤りだった。

`id`（公式試合ID）が主キーである以上、同じ試合が二重に入ることはない。
「別IDで同じカードが入る」ことは**正常な事象**であり、制約で禁じてはならなかった。
