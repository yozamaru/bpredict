# Phase 0 の測定結果

設計の前提を実機で確かめた結果をここに記録する。**この表が埋まるまで工程1（DDL確定）へ進まない。**

## 使い方

1. 測定したら、その行の「状態」を `未測定` → `測定済` にし、測定日と結果を書く
2. 結果が設計の前提と違う場合、**先に該当文書を直してから**「設計への反映」に反映先を書く
3. 前提より緩い結果が出ても、**測定するまでは設計を緩めない**（`docs/design-basic.md` 9.1）
4. 取得できないと判明した項目は、該当する特徴量を無効化して先へ進む。工程は止めない（`docs/design-detail.md` 9章）

数値は生の測定値を書く。「問題なし」とだけ書かない。後から前提を再評価できなくなる。

## 構造上の発見（2026-09-21・v1.6 で反映済み）

**確認対象**: `https://www.bleague.jp/game_detail/?ScheduleKey=505497&tab=2`
（2026-05-03 三遠ネオフェニックス 93–79 名古屋ダイヤモンドドルフィンズ）

**事前確認**: `robots.txt` を取得して設計書 5.1 の記述と照合した。`User-agent: *` の制限はなく、
`Disallow` は SEO 解析ボット（SemrushBot / MJ12bot / serpstatbot / SEOkicks-Robot / dotbot /
BLEXBot）のみ。`msnbot` と `bingbot` に `Crawl-delay` が設定されている。**一般クローラーへの
制限は引き続き存在しない。** 確認は手作業で計2リクエスト。

### 分かったこと

| 項目 | 結果 |
|---|---|
| ボックススコアの表（`<table>`） | **HTML に存在しない。** 列見出しは JS のテンプレート文字列の中にあり、実行時に組み立てられる |
| 選手スタッツの実データ | **`<script>` 内の JSON として埋め込まれている**（JS で取りに行くのではなく、初回のHTMLに入っている） |
| ページサイズ | 約 894 KB（gzip 転送は約 184 KB）。設計の 5MB 上限には収まる |
| 遅延読み込みの AJAX | `season-result` / `club-leader` / `match-result` / `recent-match` / `shot-chart` の5種。**ボックススコアは含まれない** |
| 余分に含まれるデータ | プレイバイプレイ 703 件（`ActionCD` `PlayText` `X` `Y`）、審判名、シュートチャート座標 |

### 埋め込みJSONと設計の列の対応（すべて揃っている）

| 設計の列 | サイトのフィールド | | 設計の列 | サイトのフィールド |
|---|---|---|---|---|
| `minutes` | `PlayTime`（`"09:02"` 形式） | | `stl` | `ST` |
| `fg2m` / `fg2a` | `PT2M` / `PT2A` | | `blk` | `BS` |
| `fg3m` / `fg3a` | `PT3M` / `PT3A` | | `pf` | `FOUL` |
| `ftm` / `fta` | `FTM` / `FTA` | | **`fd`** | **`FOULON`** |
| `oreb` / `dreb` | `RB_OFF` / `RB_DEF` | | `plus_minus` | `PLUSMINUS` |
| `ast` | `AS` | | `pts` | `Point` |
| `tov` | `TO` | | `started` | `StartingFlg` |
| `player_id` | `PlayerID` | | `club_id` | `TeamID` |

恒等式の検算も通った（`Point=25` に対し `PT2M×2 + PT3M×3 + FTM = 25`、`RB_TOT = RB_OFF + RB_DEF`）。

### 注意すべき構造

- **`PeriodCategory` でレコードが分かれている。** 1〜4 がクォーター別、15 / 16 が前後半、
  **18 が試合通算**。取り込むのは 18 のみ。全カテゴリを入れると7倍の行数になる
- 各カテゴリ27件のうち **4件は `PlayerID` が空のチーム集計行**（`TeamID` が null の行も2件ある）。
  選手行と集計行を取り違えると `team_game_stats` と `player_game_stats` が汚染される
- 数値が `0` ではなく**空文字 `""` で入っている**フィールドがある。`0` と「データなし」の
  区別が必要で、値域検証の前に正規化が要る

### 取得してはならないもの

同じ JSON に**審判名**（特徴量 #30 は見送り）と**プレイバイプレイ**が含まれる。
要件 5.3「予測に不要な属性は取得対象から除外する」に従い、**必要なフィールドだけを抜き出して
保存する**。JSON 全体をそのまま保存しない。

## クラブ対応関係（2026-09-21・P0-5）

**確認対象**: `https://www.bleague.jp/schedule/?year=YYYY&mon=10&tab=1`（`year` = 2016〜2026 の11ページ）、
`https://www.bleague.jp/club/`、`https://www.bleague.jp/game_detail/?ScheduleKey=22&tab=2`、
`https://www.bleague.jp/club_detail/?TeamID=703&year=2016&tab=1`。手作業で計15リクエスト、
4秒間隔の逐次取得（並列なし）。取得した本文は保存していない。

### 結論: `TeamID` はシーズン・改称・リーグ再編をまたいで不変

2016-17 の試合（`ScheduleKey=22`、千葉 vs 栃木）の埋め込みJSONで
`HomeTeamID=704` / `AwayTeamID=703` を確認した。この `703` は 2026-27 の一覧では
**宇都宮ブレックス**であり、2019年の改称（栃木→宇都宮）をまたいで同一である。

| 検証した継ぎ目 | TeamID | 結果 |
|---|---|---|
| 改称 | `703` 栃木ブレックス → 宇都宮ブレックス | 不変 |
| 改称 | `726` SR渋谷 → 東京SR | 不変 |
| 改称＋9シーズンのトップリーグ不在 | `718` 西宮（2017-18）→ 神戸（2026-27） | 不変 |
| リーグ再編（B1 → B.PREMIER） | 26クラブすべて | 不変 |

**したがって `club_source_ids` は本ソースでは1:1になる。** それでも表は維持する
（`docs/design-detail.md` 1.2）。公式サイトがID体系を変えた場合、この表が唯一の継ぎ目になる。
旧IDのまま保存しないという規約（取り込み時に `club_id` へ解決する）も変えない。

**`ScheduleKey` も通しの連番である。** 2016-17 の開幕節が 20〜26、2026-27 が 506381。
シーズンごとにリセットされないため、`games.id` にそのまま使える。

### ジオコーディングの実測

```
入力: 愛知県豊橋市神野新田町字メノ割1-3（豊橋市総合体育館の住所）
出力: 愛知県豊橋市神野新田町メノ割１番地  [137.323517, 34.754406]
```

### 1試合あたりの取得ページ数（P0-4 / U-07）

**終了済み試合のスタッツは、試合詳細1ページ（`/game_detail/?ScheduleKey=...&tab=2`）に同梱されている。**
試合・会場・入場者数・選手別・チーム別のすべてが `<script>` 内の1つの JSON に入っており、
追加の AJAX もブラウザ実行も不要だった（終了済み2試合で確認。2016年度と2025年度）。

| 用途 | 1シーズンあたりの見積もり |
|---|---|
| 日程一覧（20件/ページ） | 26〜38 リクエスト（試合数 520〜760 ÷ 20） |
| 試合詳細 | 520〜760 リクエスト（1試合1ページ） |
| 取得前確認（robots / 利用規約） | ジョブごとに2 |
| 選手・会場の補完 | **未測定**（未知の選手・会場の数に依存する） |

3秒＋ジッタで逐次取得すると **1シーズンおよそ30〜50分**で、`backfill` の300分枠と
日次3,000件の上限に収まる。**「1シーズン1日」の制約は維持する**（D1 書込枠の側で決まる）。

**これは「全用途が1試合1リクエストで済む」ことの証明ではない。** 選手・会場の補完、
日程のページング、試合前エントリーの確認は別に必要で、後者は経路そのものが未確認である（C04）。

（500 / games）` で失敗した。**書き込み枠ではない**（`Rows written` 65.27k / 100k）。

`UNIQUE (season_id, game_date, home_club_id, away_club_id)` の違反だった。

| 試合ID | 日付 | ホーム | アウェイ | 状態 |
|---|---|---|---|---|
| `1329` | 2017-05-20 | 727 | 706 | 取り込み済み |
| `1330` | 2017-05-20 | 727 | 706 | 26–18。**同じ自然キー** |
| `1332` | 2017-05-21 | 703 | 728 | 取り込み済み |
| `1333` | 2017-05-21 | 703 | 728 | 14–12。**同じ自然キー** |

**これで短い2試合の正体も判明した。** 同じ日・同じカードで直前の試合の後に行われる
決着戦である（得点規模と所要時間が整合する）。「中断・不成立の試合」という当初の推測は
誤りだった。

`id`（公式試合ID）が主キーである以上、同じ試合が二重に入ることはない。
「別IDで同じカードが入る」ことは**正常な事象**であり、制約で禁じてはならなかった。

SQLite は UNIQUE 制約を単体で削除できないため、テーブルを作り直した（`0010`）。
in-memory で 224試合 + 子テーブル4つ（計8,960行）が無傷で、`PRAGMA foreign_key_check` も
問題なし、同一日・同一カードの2試合目が入ることを確認してから本番に適用した。

**500 は Worker のコードが返さない値ではない**（`app.onError` が返す）。ただしアプリの
ログには型名しか出ておらず、**メッセージを出すよう直した直後にこの原因が1回で特定できた**。
1つ前の教訓（件数だけでは調査できない）がそのまま効いた。

`event=3`（CS）の `index=0` に、行の器が `<a>` ではない行があった。
`EVENTS = (3, 2)` が CS を先に辿るため、**シーズン全体が失われた**（CS は1ページで、

| 行 | `.data-game` | 状態欄 | 得点欄 | 可視の文字 |
|---|---|---|---|---|
| `4134` `4137` `4143`（QF第3戦） | **`<div>`**（href なし） | 空 | **要素そのものが無い** | 操作ボタンに `試合中止` |

### 直した内容と、直さなかったこと

| したこと | しなかったこと |
|---|---|
| 器をタグで絞らず、`<a>` のときだけ `ScheduleKey` と行のIDの一致を検査する | リンクのない行を無条件に許す（照合が静かに消える。**中止・延期に限って許す**） |

| 得点がある行は状態が空でも飛ばさない | — |

**DB の内容は変わらない。** backfill は `FINISHED` 以外を書き込まないため、
これらの行を `CANCELLED` と解釈しても飛ばしても結果は同じである。同じなら推測しない。

## 特徴量生成を 43分 → 3.4分 にした（2026-10-02）

**工程8の次の手（検証区分の特徴量を足して Brier を測る）に入る前に、全試合の
特徴量生成が43分かかる状態を直した。**

| 段階 | 全体（6,270試合） | 1試合あたり | 倍率 |
|---|---:|---:|---|
| 改善前 | **2,580秒**（43分） | 411ms | 1.0× |
| 選手行の索引を入れた | 798秒（13.3分） | 127ms | 3.2× |
| **降順索引 ＋ 記憶を入れた（採用）** | **207秒（3.4分）** | **33ms** | **12.5×** |

スナップショットの読み込みは 0.2秒で、ほぼ全部が特徴量生成だった。

### 値は完全一致している

**改善前の43分の実行が書いたキャッシュ**（`batch/cache/training-matrix.parquet`）と、
索引を入れた実行の行列を全件照合した。

| 検査 | 結果 |
|---|---|
| 試合の並び | 一致（6,270件） |
| 比較した列 | 16（`FEATURE_KEYS` の全部） |
| 値が違う列 | **なし** |
| 最大の絶対差 | **0.0** |

**丸め誤差すら出ていない。** 索引は「いつ計算するか」だけを変えており、絞り込みの
比較も並べ替えの順序も同じ結果になっている。

### 何が遅かったか（profile の実測）

改善前の内訳は、**同じ前処理を試合ごとに繰り返していた**ことである。特徴量の
定義とは無関係で、**方法ではなく実装の問題だった**。

| 繰り返していたもの | 1試合ごと | 全体 |
|---|---|---|
| `player_game_stats` の `game_id.isin(当季の試合)` | 146,463行 × 4回 | **37億行** |
| `team_ratings` の走査と並べ替え（`elo_home` / `elo_away`） | 12,532行 × 2回 | 1億5千万行 |
| `club_history` の切り出しと2キーソート | 12,540行 × **34回** | 全体の54% |
| `finished_at` の時刻パース | 12,540行 | 7,800万回 |

**`club_history` が34回呼ばれて引数は4通りしかなかった**（クラブ2 × 当季かどうか2）。
17個の特徴量が同じ過去試合を見るためで、**同じ切り出しを8回ずつ繰り返していた**。

### 直したときに踏んだこと

**時刻の単位がずれて、`as_of` の絞り込みが静かに全件通った。** `pd.to_datetime` が
返す解像度は入力で変わり（pandas 3 では `datetime64[us]` になった）、
`astype("int64")` の値がマイクロ秒になる。一方 `Timestamp.value` は常にナノ秒で、
**比較の片方だけが1000倍小さかった**。

```
team_times : 1728111900000000      （マイクロ秒）
cutoff     : 1728104700000000000   （ナノ秒）
```

**1試合目で過去試合が5件見つかり、`winrate_l5_diff` が 0.0 ではなく -0.4 になった。**
リーク検証（`test_future_game_mutation_does_not_change_features` /
`test_as_of_is_actually_applied`）が落ちて気づいた。**既存のテストが関門として
働いた**が、単位の一致そのものを見るテストは無かったため追加した
（`batch/tests/test_features_prepared.py`）。

**方法を変えるべきかを先に問い直した。** 43分かかるからといって「一度に全特徴量を
入れる」方針に変えるのは順序が逆である。制約は統計ではなく性能であり、
**特徴量を1つずつ足して測る規約（要件 6.2）は変えない。**

## 検証区分 #05（ORtg / DRtg）を測って残した（2026-10-02）

工程8の続き。**検証区分を1つも入れていない状態**から、要件 6.2 の #05
「オフェンス/ディフェンスレーティング」を入れて測った。

### 測定の土台に穴があった（先に閉じた）

学習行列のキャッシュの鍵が**スナップショットの MANIFEST のハッシュだけ**だった。
**特徴量を1つ足しても MANIFEST は変わらないため鍵が一致し、古い16列の行列が
そのまま読まれる。** `load_cached` は列名ではなく位置で特徴量を取り出すため、
**何の異常も報告せずに「増やす前の数字」が出る。**

工程8は「1つ足して測る」を繰り返す工程であり、ここが抜けていると測定そのものが
無意味になる。鍵に `FEATURE_KEYS` の**並び込み**のハッシュを足した。

### 結果

| 構成 | LightGBM Brier | Elo単体との差 | 95%CI |
|---|---:|---|---|
| 16列（基準） | 0.2026 | +0.00015 | −0.0019〜+0.0023 |
| 17列（`ortg_diff` のみ） | 0.2024 | +0.0004 | −0.0017〜+0.0025 |
| **18列（#05 = ORtg + DRtg）** | **0.2021** | +0.0007 | −0.0013〜+0.0028 |

**片方だけでは増分が出にくい。** 既にある `margin_season_diff`（得失点差）が純収支を
持っているためで、要件 6.2 が #05 を**1項目**として扱っているのと整合する。

**全体の Brier だけでは1項目の採否を判断できない。** 改善 0.0005 は walk-forward の
CI の半幅（約 0.002）より小さい。付録B は「Brier を有意に改善するのは30項目のうち
5〜8項目」と見込んでおり、**1項目あたり 0.0005 はむしろ「効く特徴量」の見え方に近い**。
0.003（モデル差し替えの最小実質差）を1項目の基準に使うと、積み上げる前に全部捨てる。

### 寄与度（gain）で判断した

|---|---:|---|---|---:|

## リークテストが1つ、ずっと空振りしていた（2026-10-02）

`test_features_exclude_in_progress_game`。**撹乱対象の選び方が対象試合自身を
選んでいた。**

```sql
SELECT id FROM games WHERE finished_at > ? ORDER BY tipoff_at LIMIT 1
```

**対象試合は `finished_at > as_of` を満たす**（自分の開始時刻の時点では終わって
いない）ため、この条件だけだと自分が選ばれる。つまりこの検査は「他の進行中の試合が
集計に入らないこと」を**一度も試していなかった**。

気づいたのは #27 の実装中である。`tipoff_hour` が「リーク」と判定されて落ちたが、
実際には撹乱が対象試合の `tipoff_at` を書き換えていただけだった（本番では
`as_of` = 対象試合の `tipoff_at` であり、片方だけが動く状態は起こらない）。

**自分を除外したら、撹乱対象が無くなって skip になった。** `_target()` の既定は
**最終試合**で、後続の試合が存在しない。

直したのは3点。

1. 対象試合を除外する（`AND id <> ?`）
2. 対象を終盤から30試合ずらす（後続の試合が存在するようにする）
3. **撹乱対象が無いときは skip ではなく失敗にする** — 黙って空振りするのを止める

**落とした特徴量の副産物として、関門が1つ直った。**

## 工程12 と P0-11 を測った（2026-10-02）

得点差（Margin）と合計得点（Total）の回帰を実装し、**P0-11（勝率の導出経路 A / B の
比較と σ の実測）を消化した。**

### 予想スコア

| 指標 | 実測 | 設計の見立て |
|---|---:|---|
| 得点差 MAE | 10.27点 | — |
| 合計得点 MAE | 14.17点 | — |
| **チーム得点 MAE** | **8.84点** | **付録B「8〜10点」** |

**得点差の MAE（10.27点）と混同しない。** 要件 6.4 と付録B が言う「予想スコアの MAE」は
**チーム得点**である。`home = (total + margin) / 2` なので一致しない。

**付録B の見立ての範囲に入った。** 要件 8.3 が「予想スコアを小数第1位まで表示しない
（精度の誤認を招く）」と定める根拠が、実測で裏づけられた形である。

### P0-11: 経路 B を採用する

| 経路 | Brier | Accuracy | ECE |
|---|---:|---:|---:|
| A: Winner 直接 | 0.2020 | **0.6895** | **0.0201** |
| **B: `Φ(margin / σ)`（採用）** | **0.2013** | 0.6866 | 0.0265 |

**判定規則は要件 6.1 が定めている** — 「B の Brier が A より 0.003 以上悪ければ A を
採用する。差が 0.003 未満なら整合性が保証される B を採用する」。

**B − A = −0.0006。** B が Brier で上回っているため、規則のどちらの枝でも B になる。

| 項目 | 値 |
|---|---|
| **実測した σ** | **12.93点**（out-of-fold の残差） |
| 設計の記述 | 「12〜13点というのは他リーグからの見当であって本データの実測値ではない」 |

**見当は当たっていたが、当たっていたことも測るまで分からなかった。** 要件が
「実測前に定数として書かない」と定めていたのは正しい。`win_prob_from_margin` は
σ に既定値を持たず、正の有限値でなければ例外を投げる。

### B を採用する意味（Accuracy と ECE は A のほうが良い）

**A は Accuracy と ECE で上回っている**（0.6895 / 0.0201 対 0.6866 / 0.0265）。
それでも B を採るのは、**要件 6.1 の判定が Brier を軸にしているから**である。

- Accuracy は**採用ゲートに使わない**（要件 6.4。検出力がない）
- ECE はどちらもノイズフロアの閾値（0.0415）の内側
- **B は勝率と予想スコアが定義上一致する** — 「ホーム68%」なのに「82–85でアウェイ勝ち」
  が原理的に起こらない（要件 6.1 / 受け入れ基準 A-11）

A を採った場合は `test_win_prob_and_score_agree` で矛盾を検出して丸める運用になるが、
**B ならその運用自体が不要になる。**

| **回帰の結果に分類の指標を呼べないようにした** | `Evaluation` を共用する以上、`brier` / `ece` を得点差の評価に対して呼ぶと**意味のない数字が黙って返る**。実測値が 0/1 でなければ落とす。回帰には `mae` と `residual_sigma` を足した |

### 読み取れること

**試投の配分（2PA / 3PA）はよく当たる。** `fg3a` 30.7% / `fg2a` 24.2% は、チームの
スタイル（3Pをどれだけ打つか）がシーズンを通して安定していることの反映である。

**成功率3項目はほぼ当たらない。** `fg3_pct` は平均ベースラインに対して **0.1%**、
`ft_pct` 1.3%、`fg2_pct` 4.1%。**1試合の成功率はほとんどノイズである**という
よく知られた性質が、そのまま出ている。

**この帰結を承知しておく。** 整合化の前段（詳細設計 2.4）は、成功率3項目に**共通の
ロジットシフト**を入れて予想スコアに合わせる。シフトは共通なので、**3項目の
「相対的な差」はモデルの出力がそのまま残り、「水準」は Margin / Total が決める。**

したがって保存されるチーム目標は、実質

> **リーグ平均に近い 2P / 3P / FT の配分を、予想スコアに合わせて上下させたもの**

である。**「このプロダクトはチームのシュート成功率を予測している」とは言えない。**
画面に出す率は `FGM / FGA` の導出値で、必ず分数と併記し、試投数が閾値未満なら
出さない（要件 6.8.2 / 8.3）という既定の扱いと矛盾はしない。

**整合化そのものは影響を受けない。** 目標が実行可能（`成功数 ≤ 試投数`）であることは
「試投数 × 成功率」という持ち方から構造的に保証され、精度とは独立である。

## A-09 を満たす構成を見つけた。勝率モデルを差し替える（2026-10-04）

**運営者の承認を得た設計変更である。** 要件 1.25 / 基本設計 1.44 / 詳細設計 1.84。

### 測定（n=3,031 / 22列 / 同一 walk-forward / `brier_difference` は本番と同じ関数）

| モデル | Brier | Elo単体との差 | 95%信頼区間 | 0.003以上 | 有意 | **A-09** |
|---|---:|---:|---|---|---|---|
| **全特徴ロジスティック回帰** | **0.198699** | **+0.004045** | **[0.001822, 0.006169]** | ○ | ○ | **満たす** |
| LightGBM（経路A） | 0.201241 | +0.001503 | [−0.000760, 0.003704] | × | × | 未達 |
| 経路B（それまでの採用） | 0.200807 | +0.001937 | [−0.000045, 0.003944] | × | × | 未達 |

Elo単体は 0.202744。**経路B の信頼区間の下限は −0.000045 で、わずかに 0 を跨いだ。**

### 規則と品質ゲートが衝突していた

要件 6.1 の旧規則は「**B の Brier が A より 0.003 以上悪ければ A、差が 0.003 未満なら
整合性を優先して B**」。B − A = **+0.0021** で 0.003 未満のため、**規則は B を強制する**。
しかし **B は A-09 を満たさない**。品質ゲート（12章）は A-09 を絶対条件にしている。

**「A-09 を満たす経路だけを候補にする」段を1段目に足した**（要件 6.1）。
規則は「両方が品質ゲートを満たす場合の決め方」である。

### 予想スコアは勝率から導く（向きを逆にした）

経路A では勝率とスコアが別モデルから出るため、符号が食い違う。**実測。**

| 項目 | 件数（n=3,031） | 割合 |
|---|---:|---:|
| 符号が食い違う（整数に丸めた後） | **142** | **4.7%** |
| 丸めて同点になる | 167 | 5.5% |

食い違う試合は際どいものが多い（勝率の中央値 0.484、得点差の絶対値の中央値 0.97点）が、
**勝率 12.3%（アウェイ優勢）なのにスコアはホーム勝ちという例もある**（勝率の範囲
0.123〜0.617、得点差の絶対値の最大 3.3点）。

旧版は「勝率側を正としてスコアを丸める」としていたが、**丸め方を定めていなかった**。
10.2% の試合に関わるため、決め方が画面に出る。**向きを逆にして回避する。**

```
margin = σ · Φ⁻¹(p)     p は勝率（[0.05, 0.95] にクランプ済み）
```

**精度は落ちない。むしろわずかに良い。**

| 予想スコアの作り方 | チーム得点 MAE | 得点差 MAE | 符号の食い違い |
|---|---:|---:|---|
| Margin 回帰から（旧） | 8.839 | 10.257 | 4.7% |
| **勝率から導く（採用）** | **8.832** | **10.214** | **0件（構造的）** |

## 取り込みが会場の座標を消していた（2026-10-05 / 本番のバグ）

**ステップ1（前日の結果取得）を実装する前に見つけた。** 実装すれば**毎日**起きる
ところだった。

### 何が起きたか

`POST /internal/games` の `venues` の upsert が
`DO UPDATE SET prefecture = excluded.prefecture, lat = ..., lng = ...` であり、
**試合の取り込みは `{id, name}` しか送らない**。したがって取り込みのたびに
座標が NULL に戻る。

| 出典 | 座標あり |
|---|---:|
| `venues_geo.csv`（正本） | **140** |
| D1（2026-10-04 の backfill 後） | **130** |

**失った10会場は、9/28〜10/4 の試合で使われた会場と完全に一致した。**

```
失った: 100034 100045 100046 100054 100069 100087 100101 115 47 526
その期間に使われた会場: 13件 → 上記10件をすべて含む
説明できない失い方: 0件
```

### なぜ気づけたか

**「スナップショットが D1 より古い」を直したときの逆**を探したからである。
基本設計 2.2 は「D1 を更新するジョブは同じ値をスナップショットにも書く」を
定めたが、**その対になる「スナップショットにある値が D1 から消える」経路を
誰も見ていなかった。**

**`test_snapshot_reflects_the_master_csvs` は捕まえられない。** あれは CSV と
スナップショットを比べる検査で、**D1 は見ない**。

### 直し方

`upsertStatements` に `preserve` を足した。挙げた列は
`COALESCE(excluded.col, table.col)` で更新する — 値が来れば更新し、NULL なら残す。

| テーブル | `preserve` | 送る経路 |

### 帰結を承知しておく — **実質の門は 0.003 ではなく約 0.004 である**

| 項目 | 値 |
|---|---:|
| 設計上の最小実質差 | 0.003 |
| in-sample の偏り（実測） | 約 0.001 |
| **実質的に必要な改善** | **約 0.004** |

**付録B は「Elo 差を超える増分は非常に小さく、30項目のうち Brier を有意に改善するのは
5〜8項目」と見込んでいる。** 実際、工程8 で測った1項目あたりの効果は 0.0005 規模で
ある（2.2）。**0.004 を1回の再学習で超えるのは現実的でない可能性がある** —
つまり**モデルが永久に差し替わらない**状態になりうる。

**運営者の判断を待つ。** 選べる道は2つある。

| 案 | 内容 | 影響 |
|---|---|---|
| **A（現状）** | artifact をそのまま再評価する | 設計 4.6 のまま。**約 0.001 の下駄を現行モデルに履かせる** |

**勝手に B へ移さない。** 4.6 は「artifact を取得する」と明示しており、理由も
書いてある（旧実装が残っていない場合に成立しない）。**ただし勝敗モデルは
ロジスティック回帰で、`feature_list` と `params` から完全に再現できる** — その
範囲では B が成立する。

### 見つかった誤り — **`/results?date=` が設計の形を返していなかった**
